## 2. 实施范围与边界

## 3. 已收敛的决策

### 3.1 范围判定

唯一白名单维护在 `.github/workflows/ci.yml` 的范围步骤，计划只记录实施决定，稳定规范和测试不得另建一份运行配置。

只有直接 PR 事件、完整变更路径非空、且全部路径属于 `docs/**`、根 `README.md`、`.agents/**`、`skills/**`，才输出 `docs_only=true`。这些目录当前是内部文档或静态 Skill 输入。该资格不按扩展名或内容猜测；将来若其中增加动态消费资产，必须同步收紧判定。

`framework/**`（含随包文档）、`template/**`（含生成文档和项目 Skill）、`scripts/**`、`.github/**`、根构建/依赖/配置文件和未知路径一律完整 PR 档。重命名按两端路径处理，差异使用 base 到本次实际 checkout SHA，带 `--no-renames`；不使用 `HEAD^`。

无法取得有效 base、差异获取失败或范围不明确，保守取全量；输出只允许 `true` / `false`。范围作业失败、取消或输出缺失时，汇总失败。空差异不享受 docs-only。手动和复用入口不享受 docs-only，继续执行其所选档位；发布保持 full。

### 3.2 聚合与预检接替

- 复用 `template-slice-plan` 增加范围输出，避免新建一台 runner。docs-only 时不产生需要执行的分片。
- 静态 `docs-sync` 始终执行完整 `check-all.ps1`；不使用 workflow 级 `paths-ignore`。
- 保留现有必过汇总检查名。汇总使用 `always()`，明确核对范围、静态以及全部必要动态作业的结果。
- docs-only 通过要求：范围合法、静态成功、动态作业确实按规则跳过。输出“动态验证不适用”，不生成或宣称矩阵回执通过。
- 完整档通过要求：范围合法，静态、打包、Framework 测试、包消费、PG、OIDC、模板分片全部成功，并通过现有场景/阶段/容器回执检查。失败、取消、意外跳过或缺失均不得通过。
- 矩阵新增显式 `-SkipSourcePreflight`，仅 CI 的上述接替链使用；默认人工入口继续在生成前执行 symbols、using-guards、async-boundaries。
- 跳过分支核对 `check-all -List` 中三个实际入口均存在，防止以后删掉总入口中的预检而静默失去保护。这只是清单耦合检查，不能替代失败传播的变异验证。
- 所有作业仍显式 checkout 同一候选 SHA。CI 可以并行预检和生成，但整体质量只有静态预检成功后才可通过；同步更新当前“每片生成前执行”的规范描述。
- 不共享可变生成目录、hive、包解包缓存或数据库；现有 immutable 包 artifact 和隔离边界保持不变。

## 6. 验收矩阵

### 6.1 范围与聚合

正例分别覆盖白名单各入口以及多份内部文档。负例至少覆盖：

- 单个 `framework/docs/*.md`、`template/*.md`、`template/.agents/**` 文件。
- `framework/docs/` 移到 `docs/`，以及反向跨边界重命名；删除动态输入。
- docs+代码混合、多个提交只有最后一次改 docs、未知根路径。
- base 缺失、全零、无法取得、等于 checkout；空差异；差异获取失败。
- dispatch、复用候选入口均不走 docs-only。
- 范围失败/取消/缺输出/非法值；静态失败/取消；完整档任何必要作业失败或意外 skipped。
- docs-only 分支不下载不存在的矩阵回执；完整档缺片、错场景/档位/阶段、零测试、取消、容器责任不足继续由实际检查器拒绝。

至少验证两个缺陷注入：去掉 `--no-renames` 暴露跨边界漏判；移除汇总对静态成功的要求暴露假绿。撤销注入后合法对照恢复成功。

### 6.2 预检接替

逐项注入 symbols、using-guards、async-boundaries 原本可发现的缺陷：旧入口非零；新 CI 总入口非零且聚合拒绝；默认人工矩阵入口依旧拒绝。再验证总入口删除其中一项时，跳过分支的清单耦合检查拒绝。记录实际诊断，不能只用伪造的“已检查=true”证明。

完成源码和文档变更后运行一次完整 `check-all` 和本次范围/聚合回归。检查数量从实际总入口取得，不在规范另复制清单。候选完整 CI 的 PR 档保持 6 场景、全阶段及 Framework/包消费/PG/OIDC 责任；full 保持 10 场景及适用的容器责任。

### 6.3 真实 PR 验证顺序

实施 MR 本身修改 workflow/scripts/template，按规则必然是完整档。不能将其 dispatch、手工 scope 输出或截断 base 的运行当作 docs-only 证明。

为在合入前得到真实 PR 的两条路径证据，使用可删除的验证基准分支和草稿 PR：

1. 验证基准分支包含候选实现，仅临时扩展 PR 触发的目标分支，使 GitHub 能对它执行 workflow；生产触发配置不携带该扩展。
2. 针对该基准创建纯内部文档 PR 和混合改动 PR；实际 base/head、scope 输出、作业状态与日志全部记录。
3. 核对验证 workflow 除触发目标外的作业、步骤、条件和聚合逻辑与交付候选一致，报告该验证条件差异。若平台无法运行该方式，记录 docs-only 远端待验，不声称已完成。
4. 正式实施 MR 针对 develop，再执行原始触发配置的完整 PR CI。合入后的 full 验证绑定实际合入 SHA，作为交付后检查，不用于替代前述 PR 验收。
5. 完成后关闭草稿验证 PR，清理仅本任务创建的验证分支；运行链接保留在报告中。

所有验证都保持真实 PG/OIDC、浏览器和场景责任，不通过人工覆盖范围变量获得绿灯。

## 7. 效率记录与完成判定

| 场景 | 优化前 | 优化后要记录的证据 | 预估与判定 |
| --- | --- | --- | --- |
| 纯内部文档 PR | 动态完整 PR 档；最近完整 PR 观测 514 秒/1760 runner 秒，作为历史参照 | 实际 docs-only PR 的范围/静态/汇总耗时；各动态作业 skipped | 墙钟 1–2 分钟是待测预估，不能作为已实现收益；按跳过的作业列出工作量 |
| 普通代码 PR | 三片各重复三项预检 | 三片日志无这三项重复命令；总入口保留；新增范围/清单检查和依赖等待成本 | 历史 30 个分片预检中位 11.344 秒/片，三片约 34 runner 秒是毛节省；单片墙钟毛收益约 11 秒，净收益以实际 DAG 为准 |
| 小 bug/新模块/跨模块的本地循环 | 已允许收窄，但场景清单不够明确 | 明确各阶段入口、实际选择的测试和构建范围、含准备成本的耗时 | 规范变化不能冒称运行加速；没有同输入前后测量的场景写“未测”，不推导百分比 |
| 合入/发布 full | 10 场景及必要集成责任 | 同合入 SHA 的 full 结果、回执与各作业耗时 | 保持完整兜底；预检去重的净成本如实披露 |

runner 合计使用各作业 `completed_at - started_at` 求和；墙钟从本次 attempt 起点到最后必要质量作业完成，队列、setup、依赖等待和命令执行分别记录。不同 SHA、依赖和缓存条件披露，历史不同输入仅作参照。

docs-only 以责任与真实作业选择验收；去重以删除命令、接替缺陷检测和新增净成本验收，不重复分片重排的噪声实验。每次观察核对 docs-sync 是否早于关键分片结束，规划依赖是否进入关键路径。若新增可归因成本吞掉节省或拖长关键路径，调整实现后复验。

所有真实运行完整披露墙钟和 runner，不因其波动隐藏增长。只有同工作量的调度重排才使用预先登记的固定配对联合门槛；本轮不进行这种重排。代码 PR 的 ≤510 秒中位目标，必须有足够可比实跑才可宣称达成；单次低于预算不等于稳定 SLA。

完成要求：范围/失败传播/接替变异通过；默认人工入口保持保护；完整 PR CI 通过；真实 docs-only 与混合 PR 符合责任；分发规范生成可用；Claude 代码审查必须项关闭；报告不混淆毛节省、净收益和历史参照。若尚缺任何必要证据，保留待办及本计划，不标记本轮完成。
