# 开发规范重构方案（融合实践沉淀 + AI 闭环）

> 目标：把实战项目沉淀的 `practices.md`（mt5-vps-speed-up）整编进模板的开发规范，并结合本项目「AI 协作 + skill 闭环」定位重构规范体系。基于对 practices.md（27 条）与模板现有三份规范（common/backend/frontend-develop.md）的逐条交叉分析（2026-07-10）。**本文是方案，不是最终规范正文；实施前请审。**

---

## 一、分析结论（为什么要重构）

对 practices.md 的 27 个可辨识条目 vs 模板现有规范逐条比对，结果：

| 类别 | 数量 | 含义 |
| --- | --- | --- |
| [已覆盖] | 5 | 模板已有等价条款（1.1 四层职责 / 2.1 洋葱 / 2.2 抽象内层 / 4.4 时钟 / 5.3 映射器） |
| [更强·需吸收] | 5 | 模板有但 practices 讲得更硬（2.3 反向依赖倒置 / 5.1 验证例外 / 6.1 mock 守卫一致 / 6.2 色板 / 7.3 基类） |
| [冲突·需裁决] | 1 | DI 生命周期（mt5=Transient vs leistd 框架 UnitOfWork 需 Scoped——**证明具体值不可移植**） |
| [缺失·价值增量] | ~16 | practices 有、模板全无——重构的主要价值 |

**两个关键发现**：

1. **现有三份规范有实质缺口**（16/27 缺失），practices 的实战条目大量是"踩坑写死"的强约定，正是模板欠缺的。
2. **范式差异**：模板是「`common`(纯通用) + `backend`/`frontend`(纯具体)」的**文件级两层**；practices 是「每条原则自带 `例(本项目)`」的**条目级两层**——后者迁移性更好。模板应吸收条目级"原则 + 例"范式。

**最高价值的缺失增量**（也是 AI 最易违反项）：§0 先找参考链路、§1.2 守卫分层判断、§4.3 契约字段小写、§6.4 连锁字段改全、§3.2 删除幂等。

---

## 二、重构方案

### 2.1 组织范式：引入「原则 + 例」条目级两层

对技术栈无关的工程判断，规范正文写**通用原则**，紧跟一个 `例（.NET）` / `例（Angular）` 落地示范。原则可迁移、例子可替换。这解决模板的内在矛盾：既要具体到能照做（如 `GetPagedListAsync`），又要服务任意业务项目。

### 2.2 体系切分：整编进现有 4 份，不新增第五份

**不**把 practices.md 作为独立"补充规范"搬进模板（那会再造一份交叉重叠的文件）。而是拆解整编进现有体系：

```
docs/standards/code-standard/
├── common-develop.md    【L0 技术栈无关·工程铁律】
│     现有 common + 从 practices 上提的"纯原则"条目（用"原则+例"范式）：
│     §0 参考链路 · §1.2 守卫分层判断 · §2.x 洋葱依赖方向(强化)
│     · §2.3 反向依赖倒置 · §2.4 值对象归一 · §3.1 扩抽象不旁开
│     · §3.2 删除幂等 · §3.3 统一开关 · §5.1 入口验证内层信任(补例外)
│     · §5.4 枚举边界转换 · §1.3 接口实现签名同步 · §4.1 禁内联全限定名
│
├── backend-develop.md   【L1 .NET/EF/DDD 具体】= common 原则的「.NET 例」
│     现有 backend + practices 后端条泛化并入：
│     枚举字符串持久化(HasConversion<string>) · 契约字段小写 · 时间单位+UTC边界
│     · DI生命周期(只写"遵循项目统一约定"原则，不写死值) · DTO 一用途一文件
│     · 表现层目录按功能域(7.1) · 后台服务 Initializer/Worker/Job 三分(7.2)
│     · 表现层红线+授权常量+越层白名单(7.3)
│
├── frontend-develop.md  【L1 Angular/PrimeNG 具体】= common 原则的「Angular 例」
│     现有 frontend + practices 前端条并入：
│     mock 守卫逐道一致(6.1) · 有限语义色板(6.2) · 图标文案一致+实测(6.3)
│     · 连锁字段改一路改全(6.4)
│
└── api-standard.md      【已存在·契约 SSOT，维持】
```

### 2.3 冲突裁决（1 条）

**DI 生命周期（practices 4.6）**：practices 例是 mt5 的"业务服务一律 `AddTransient`"。但 leistd 框架的 UnitOfWork 拦截器需 Scoped——**具体值项目间冲突**。裁决：模板只吸收**原则**「DI 生命周期遵循项目统一约定、勿逐处自由发挥；框架强制某生命周期的组件属合理例外」，**不写死默认值**。同类"项目决策项"（映射库 Mapster vs AutoMapper 等）同样只写原则、具体留项目。

### 2.4 mt5 专有内容剥离（不进模板）

- 业务实体名：`VpsNode`/`BrokerAccount`/`QuoteRelay`/`INodeCommandSender`/`VpsNodeController` 等全链路 → 换成模板通用示范或留白。
- 边车 snake_case 契约、云 SDK/dry-run 触达云端 → 泛化为"对不同外部系统按其约定命名""是否触达外部由统一开关决定"，去 mt5 语境。
- `AddTransient` 一律约定 → 见 2.3，只留原则。
- SignalR/WS Realtime、Gateway 反代目录 → 泛化为"表现层按功能域分类"的通用分类思路。

**可泛化保留（换皮为模板技术栈）**：枚举字符串持久化（EF `HasConversion<string>`，正是模板技术栈）、四色语义板（PrimeNG 通用）、mock 三件套、后台服务三分后缀、映射器 Profile 注册结构。

## 三、AI 闭环回连（重构不止于改规范文件）

这是本次重构区别于"普通规范更新"的关键：**规范定义 → skill 逐项核对**要形成闭环。把最易被 AI 违反的硬规则，同步进我们已建的 `coding`/`code-review` 硬规则核对表（`dev-report-template.md §5.1` / `review-report-template.md §3`）。

**Top 硬规则清单**（按 AI 易违反 + 隐蔽危害 + 可勾选 排序，纳入 checklist）：

| # | 规则 | 来源 | 为何进 checklist |
| --- | --- | --- | --- |
| 1 | 对外契约分类字段一律小写 | practices 4.3 ⚠️ | 纯机械可查，AI 极易大写，联调期才炸 |
| 2 | 连锁字段改一路改全（后端 DTO→过滤→前端 DTO→service→mock 处理器→mock 数据） | 6.4 | AI 典型只改一端，可做"六环全改"勾选链 |
| 3 | 先找参考链路（coding 第 0 步前置动作） | 0 | AI 最爱凭空发挥 |
| 4 | 验证只在入口 DTO + 第二条调用路径例外 | 5.1 | AI 要么到处重复校验、要么误删多入口守卫 |
| 5 | 守卫分层判断（单聚合→领域 / 跨聚合→应用） | 1.2 | AI 高频放错层 |
| 6 | 优先扩现有抽象、不旁开第二套 | 3.1 | AI 爱新建接口造第二套路径 |
| 7 | 删除幂等只吞 NotFound、真错误上抛 | 3.2 | 涉外部资源时的孤儿资源风险 |
| 8 | mock 守卫与后端逐道一致 | 6.1 | AI 常写空壳 mock |
| 9 | 接口/实现签名同步、禁内联全限定名 | 1.3 / 4.1 | 轻量机械项 |

其中 **§0「先找参考链路」应上升为 `coding` skill 的第 0 步硬动作**（不只是 checklist 一行）——它是"AI 凭空发挥"这个最大风险的直接对治。

## 四、实施步骤（建议顺序）

1. **common-develop.md** 上提通用原则（§0/1.2/1.3/2.3/2.4/3.1/3.2/3.3/4.1/5.1 例外/5.4），引入"原则+例"范式。
2. **backend-develop.md** 并入后端具体条（枚举字符串/契约小写/时间单位+UTC/DI 原则/DTO 组织/表现层目录/后台服务三分/表现层红线），泛化 mt5 例。
3. **frontend-develop.md** 并入前端条（mock 一致/色板/图标文案/连锁字段）。
4. **回连 skill**：把 Top 9 硬规则补进 `coding` 的 `dev-report-template.md §5.1` 与 `code-review` 的 `review-report-template.md §3` 核对表；§0 参考链路加进 `coding/SKILL.md` 必读顺序作第 0 步。
5. **一致性校验**：跑 `check-docs-api-drift.ps1`（规范里若引用 Leistd API）；人工确认无 mt5 残留、无与 api-standard.md 的新矛盾。

## 五、需要你拍板的决策点

1. **体系切分**：认可"整编进 4 份、不新增第五份"？还是倾向保留一份独立的 practices 式"实战强约定"文件（便于突出"踩坑写死"的高优先级）？
   - 我的推荐：整编进 4 份（避免交叉重叠），但在 common-develop 顶部用醒目标记标出"⚠️ 踩坑写死"的强约定条目，保留其优先级信号。
2. **§0 参考链路的强制度**：只作 checklist 一行，还是上升为 coding skill 第 0 步硬动作（AI 开发任何新需求前必须先读 1-2 个同类链路）？
   - 我的推荐：后者——这是对治"AI 凭空发挥"最有效的一条。
3. **DI 生命周期等项目决策项**：确认模板只写原则、不写死值？

---

## 六、一句话结论

practices.md 是高质量实战沉淀，27 条里 16 条是模板缺失的价值增量、5 条更强需吸收。重构方案：**引入"原则+例"条目级两层范式，把通用工程判断上提 common-develop、具体规则留 backend/frontend 作"例"，整编进现有 4 份而非新增第五份，剥离 mt5 专有内容，并把 Top 9 硬规则回连进 coding/code-review 的 skill 核对表形成闭环**——让规范不只是"写下来"，而是"AI 每次开发/审查被逐项核对"。
