# 个人设置与系统设置重构、账户安全能力补齐

## 已定决策

| 项 | 结论 |
|---|---|
| 个人设置位置 | `/workspace/settings/{面板}`，所有登录用户同一处；管理人员从用户菜单跳入 |
| 新能力范围 | 本轮一次补齐：两步验证、通知偏好、外部账号绑定、登录设备、头像、邮件发送配置、登录锁定、强制两步验证、操作记录保留期 |
| 租户级默认语言 / 时区 | 不加。默认跟随系统，用户可个性化 |
| 主题与语言切换 | 保持现状：顶栏快捷切换、只存本机，不同步到账户 |
| 管理平台"运维"分组 | 改名"审计"，只放操作记录；日志级别留在系统设置的"运维"面板 |

## 一、导航与路由

**工作空间侧边栏**：工作（工作台）/ 业务（示例模块）/ 个人（设置 → `/workspace/settings`）。
不用"其他"组名：`coding-frontend.md §8` 禁止兜底组，"个人"有明确判据（关于我自己的）。

**管理平台侧边栏**：工作（仪表盘）/ 身份与访问（用户、角色、租户）/ 开发者（开放应用）/ 审计（操作记录）/ 系统（系统设置）。
落地组沿用"工作"而不是"概览"：§8 要求两个区的落地页同名。

**用户菜单**：切换区域、个人设置（→ `/workspace/settings/profile`）、退出。去掉"个人信息""修改密码"两个弹窗，内容迁入面板。

**设置页拆成两个外壳**，共用设置行组件：
- 个人设置 `/workspace/settings/{profile|security|preferences|notifications}`
- 系统设置 `/platform/settings/{分组}`：**一个后端设置分组就是一个面板**，面板名与顺序来自后端，URL 是分组标识的短横线写法。

两者都按参考项目的写法：左侧面板列表、窄屏收进抽屉；面板名进 URL，刷新与分享都落在同一面板。
系统设置不在前端另列面板清单（原设置页的既有原则：漏登记的设置会从界面上消失且查不出来）；
按受众裁剪也由后端完成——进程级分组只在宿主上下文下发。

## 二、个人设置面板

| 面板 | 内容 |
|---|---|
| 个人资料 | 头像、显示名、邮箱（验证状态 + 重新发送验证）、手机、用户名（只读） |
| 账户与安全 | 修改密码、两步验证、已绑定的外部账号、登录设备 |
| 偏好 | 语言、时区（沿用现有用户级设置） |
| 通知 | 按类别 × 渠道（站内 / 邮件）的开关 |

## 三、系统设置面板

面板即后端分组：

| 分组（面板） | 层级 | 内容 |
|---|---|---|
| Registration（注册验证） | 租户 | 注册策略（已有） |
| Security（登录安全） | 租户 | 登录失败锁定阈值与时长；是否强制两步验证（阶段 4、5 新增） |
| Email（邮件发送） | 宿主 | SMTP：主机、端口、加密方式、账号、密码（只写）、发件人；"发送测试邮件"（阶段 7） |
| Operations（运维） | 宿主 | 日志级别（已有；分组由 Logging 更名） |
| Audit（审计） | 宿主 | 操作记录保留期（阶段 9） |

## 四、各能力设计

### 1. 头像
- 现状更正：个人资料里**已有**头像上传，但原样存最大 1 MB 的 data URL，并内联在 `/auth/me` 与用户列表的 DTO 里。本阶段改的是体积与输出方式。
- 仓库没有文件存储组件，不为头像新建一套。沿用 `User.Avatar`（text 列）存图片数据。
- 浏览器端裁剪缩放到 256×256 再上传；服务端校验图片魔数与大小上限（约 200 KB），不在服务端做图像处理（避免引入有许可证约束的图像库）。
- 列表与 DTO **不内联图片**：经 `GET /api/v1/users/{id}/avatar` 输出，带 ETag 缓存；DTO 只给带版本号的地址。否则一页用户列表会背几十个图片。

### 2. 邮箱变更再验证
- 修改邮箱后 `EmailConfirmed` 置假，复用注册的验证码发送与校验链路补一个"验证当前邮箱"。

### 3. 登录设备（会话登记）
- 新表 `UserSession`（会话 Id、用户、租户、创建时间、最近活跃、IP、UA 摘要、撤销时间）。
- 登录时登记并把会话 Id 写进 `sid` 声明；Cookie 校验时检查会话是否已撤销（带短缓存），最近活跃按分钟节流更新。
- 用户可查看设备、撤销单个或"退出其他所有设备"。**修改密码、启用 / 停用两步验证后自动撤销其他会话。**
- OpenIddict 签发的访问令牌不在此列（到期失效），文档写明边界。
- 落地时的取舍（阶段 3）：
  - **撤销即删除**，不设"已撤销"列：撤销的历史由操作记录承载，表里只留有效会话；登录时顺手删掉本人已过期的会话，不另起清理作业。
  - 校验挂在会话 Cookie 的 `OnValidatePrincipal`，结果缓存 1 分钟（缓存时长即最近活跃的更新间隔）。认证先于多租户中间件，校验按主体的租户声明自行切换上下文；租户已不可用时放行，交给 `TenantSessionRecoveryMiddleware` 带 `X-Tenant-Invalid` 处理。
  - 没有 `sid` 的旧 Cookie 一律无效（上线后所有人重新登录一次），不留免检口子。
  - 账号停用、删除时撤销该用户的会话与令牌，认证阶段即拒绝；会话校验在缓存未命中时顺带确认账号仍可用（`User.AllowsExistingSessions`），兜住绕过应用直接改库的情形。
  - Cookie 被整体换掉时结束旧会话：模拟登录进入时结束发起人的会话，退出模拟时结束模拟会话。模拟会话记下发起人名称，被模拟账号的设备列表里可见。
  - 管理员重置密码同样撤销该用户的全部会话。
  - 会话空闲时限与 Cookie 滑动过期同值，在 `Program.cs` 只定一次（`UserSessionOptions`）。
- ~~留给阶段 4~~（已处理）：原先对"锁定"一律逐请求拒绝，失败锁定上线后别人反复输错就能把已登录的本人踢下线；现已区分无截止时间的锁定与失败锁定。

### 4. 登录失败锁定（现状：计数方法存在但从未调用，没有自动锁定）
- 密码校验失败累加失败次数，达到阈值锁定一段时间，成功登录清零；阈值与时长是租户级设置（默认 5 次 / 15 分钟）。
- 管理平台用户管理补"解除锁定"。
- 锁定与解锁进操作记录。
- 落地时的取舍（阶段 4）：
  - 锁定中的账号**不校验密码**直接报锁定：否则锁定期间照样能按"锁定 / 密码错"两种回应试出正确密码。代价是连续输错后能看出"这个账号存在"，与通行做法一致。
  - 触发锁定的那一次就报锁定（不是再报一次密码错）；锁定时失败计数清零，到期后重新给满次数；过期锁定在下一次失败时清掉。
  - 只经外部登录、没有密码的账号输错不计数：那里没有可猜的密码，计数只会让别人能把它锁住。
  - 失败锁定只挡新的登录，已在线的会话不受影响；无截止时间的锁定让已有会话失效。
  - 锁定提示只说"还要等几分钟"，不带截止时刻（服务端时刻要按用户时区换算才有意义）。
  - 阈值 0 表示不锁定；区间 0–100 次、1–1440 分钟，经 `SettingConstant.NumericRanges` 与写入校验、界面上下界同源。
  - 记录：`auth.locked-out`（租户可见，一个锁定期至多一条）、`user.unlocked`（未锁定时解锁不留记录）。

### 5. 两步验证（TOTP）
- 按 RFC 6238 在模板领域层自己实现（HMAC-SHA1、30 秒步长、容忍前后一步），不引入包——实现只有几十行，与"小工具不单独建包"一致。
- 用户字段：是否启用、密钥（DataProtection 加密存储）、恢复码（只存哈希，一次性）。
- 流程：生成密钥 → 展示二维码与手输密钥 → 输入一次验证码才启用 → 一次性展示 10 个恢复码；停用需密码 + 验证码；可重新生成恢复码。
- 登录：密码通过后若已启用两步验证，不发会话 Cookie，只发短时"待验证"凭据，第二步 `POST /api/v1/auth/two-factor` 提交验证码或恢复码后才完成登录。外部登录同样走第二步。
- 强制启用：租户开启后，未启用的用户登录后只拿到受限会话，只能访问两步验证设置相关接口，前端直接带到设置面板。
- 二维码在前端渲染（`qrcode` 依赖），同时提供手输密钥。
- 落地时的取舍（阶段 5）：
  - **强制设置改为独立页 `/auth/two-factor-setup`，不带去个人设置面板**（与原计划不同）：受限会话调不了设置之外的接口，放进主布局的话，布局自带的通知、菜单等请求会一路 403。服务端只拦 `/api` 与 `/connect`，页面照常下发，由路由守卫把受限用户带去设置页。
  - 第二步凭据只放缓存、浏览器拿随机令牌，不发 Cookie；单个挑战最多试 5 次，**每次输错同时计入账号的登录失败次数**——知道密码的人可以反复走第一步领新挑战，只靠挑战上限挡不住 10⁶ 空间。
  - 同一步的验证码只认一次（记下最近用掉的步序号）；启用时校验通过的那一步随即记为已用。
  - 恢复码 80 位随机、只存 SHA-256：这个长度下快速哈希也无法离线穷举，登录时逐个比对十个慢哈希会拖成秒级。
  - 密钥用 Data Protection 加密（与会话 Cookie 共用密钥环）；待启用的密钥放缓存（同样加密），半途放弃不改账号。
  - 身份验证器里的发行方取项目名（模板里是 `CompanyName.ProjectName`，生成后替换），账号名在租户下带 `@租户名`，同名账号在应用里分得清。
  - 管理平台补"重置两步验证"：给丢了手机又没了恢复码的人用，同时作废其全部会话。
  - 启用与停用都让本人其他设备退出；组织要求两步验证时不能停用。
  - 布尔型设置改由后端标注（`SettingConstant.BooleanSettings` → DTO `isBoolean`），写入校验与界面开关读同一份；此前前端单列清单，新加的布尔设置漏登记就渲染成要手打 `true` 的文本框。
  - 依赖：`qrcode` 与 `@types/qrcode`；同时把 `istanbul-lib-instrument` 显式列为开发依赖——它原本只是 `@angular/build` 的可选对等依赖、在锁文件里标为 extraneous，npm 11 重算依赖树时会把它删掉，`ng test --code-coverage` 随之失效。两份 `package.json`（普通与多语言变体）同步更新。
  - 登录第二步按用户加分布式锁、锁内重读挑战，与图形验证码、邮箱验证码同一做法：输错次数记在缓存里，不加锁时并发请求读到同一个次数，能在一个挑战上试出远超上限的次数。
  - 复制与下载沿用共享工具（`shared/utils/clipboard.ts`、`download-file.ts`），开放应用的密钥弹窗与操作记录导出一并改用。

### 6. 外部账号绑定
- 列出当前用户的 `ExternalLoginConnection`；解绑前校验"至少还剩一种登录方式"（有密码或其他绑定）。
- 绑定：外部登录流程增加"绑定到当前用户"模式，回调时挂到当前用户而不是登录 / 建号。
- 只在启用外部登录的模板形态里生成。
- 落地时的取舍（阶段 6）：
  - 绑定走独立端点（`link-url` / `link`，需已登录），state 缓存里记下"绑定、由谁发起"：登录回调拿到绑定 state、或绑定端点拿到登录 state，一律按无效拒绝，互不通用。外部授权回来只能带 state，前端在出发前把提供商记进 sessionStorage，回调页据此走绑定端点。
  - 一个外部身份只属于一个用户：已绑在别人名下时拒绝，不改绑；同一提供商每人只绑一个。
  - 解绑前校验"至少还剩一种登录方式"（有密码或还有别的绑定）；界面对最后一个绑定直接不给解绑按钮。
  - **修了一个既有缺陷**：`ExternalLoginConnections` 是软删除，但 `(Provider, ProviderUserId)` 唯一索引没排除已删除行——解绑后同一外部账号再绑定会撞唯一约束。索引过滤条件加上 `NOT "IsDeleted"`，并入基线迁移。
  - **未处理、需要留意**：既有的外部登录"按邮箱关联已有用户"不校验外部账号的邮箱是否已验证。若某提供商允许未验证邮箱，就能借它登录进同邮箱的本地账号。这超出本轮范围，建议单独评估（例如只在提供商声明邮箱已验证时才按邮箱关联）。

### 7. 邮件发送配置
- SMTP 配置从 `appsettings` 改为宿主级运行期设置，配置文件仍作为未设置时的回落。
- 框架 `Leistd.Email.Smtp` 的发送器改为经可替换的配置提供方取参数（默认仍读 Options），模板提供读设置的实现。
- **设置组件新增"加密存储、只写"的定义标志**：值落库前加密，接口永不回传明文，只回"已设置"。SMTP 密码用它。
- 落地时的取舍（阶段 7）：
  - 框架 `Leistd.Settings`：`ISettingDefinition.IsEncrypted`。加解密直接用宿主的 `IDataProtectionProvider`（与多租户连接串同一做法：只引用抽象包、沿用宿主密钥环、用途字符串固定并带设置名），不设自己的加密接口——换密钥设施在 Data Protection 这一层换（密钥存储与密钥加密都可替换）。曾先做过一版 `ISettingValueEncryptor`，按评审意见删掉。只在读取某个机密设置的值时才解密：批量读取（界面列表、客户端可见设置）不受密钥环问题牵连；没注册 Data Protection 时读写机密设置抛异常，不悄悄存明文。顺带修正：`ISettingManager` 写入后作废同一作用域 `ISettingProvider` 的记忆化结果，同一请求里先写后读读到新值。组件文档原先写着"不做加密设置"，改为"只给管理员要在运行期维护的第三方凭据，部署期密钥仍属配置"。
  - 框架 `Leistd.Email.Smtp`：发送器改为每封信取 `IOptionsMonitor<SmtpOptions>.CurrentValue`（原为 `IOptions`，启动后不再读新值），重算出的值经同一套 `IValidateOptions` 校验。曾先做过一版可替换的 `ISmtpOptionsProvider`，后按 .NET 官方做法撤掉：运行期可改的值应经配置源流进 `IOptionsMonitor`，而不是每个 Options 另立一个提供方接口。
  - 模板：发信参数是**宿主级**设置（「邮件发送」面板），默认值取配置文件（与日志级别同口径），口令是机密设置、默认值留空、未设置时回落到配置里的口令。宿主级设置作为优先级最高的配置源（`Api/Configuration/HostSettingsConfigurationProvider`），由一个通用应用器（`HostSettingsConfigurationApplier`）按映射表 `HostSettingBindings` 把设置值（机密设置解密后）推成配置键并触发重载；写入后本进程立即生效、其它实例由周期刷新跟上。新增一项运行期可改的部署配置只需定义宿主级设置、在映射表加一行、消费方用 `IOptionsMonitor<T>`。这些设置的默认值取部署基线（`HostSettingDefaults`，取值时跳过宿主设置配置源本身），否则设置加载后默认值会变成覆盖后的值，「重置」回不到基线。`IOptionsMonitor` 在重载回调里就重算并校验，不合规的新值（例如只填了用户名还没填口令）让重载抛出，此时配置源换回上一组并记错误。
  - 界面：机密设置渲染成口令框（`autocomplete=new-password`，防浏览器把登录口令自动填进去），占位符只说"已设置 / 未设置"。「邮件发送」面板底部可发测试邮件，失败原因原样显示。

### 8. 通知偏好与邮件通道
- 偏好存为用户级设置（`Notifications.{类别}.{渠道}` 布尔值），复用设置组件，不新建表。
- 框架通知组件的发布器增加"是否投递"判断的扩展点（默认全部投递）；模板按用户偏好实现。
- 模板新增邮件通道：只投给已验证邮箱。
- 新增"安全提醒"类别及事件：新设备登录、密码已修改、两步验证状态变更、账号被锁定。安全提醒的站内通知不可关闭，邮件可关。
- 落地时的取舍（阶段 8）：
  - 框架 `Leistd.Notifications`：`INotificationChannel` 增加 `Name`（站内通道为 `InApp`），新增可替换的 `INotificationDeliveryFilter`（默认全部投递；契约与默认实现放 `Filters/`，模板的按偏好过滤器同样放 `Api/Filters/`）。发布器对每个收件人先问站内：不投就既不落库也不推送；其余通道按名字逐个问。
  - 偏好是**纯用户级**设置，没有租户默认值：安全提醒邮件默认开、系统通知站内默认开、系统通知邮件默认关。没登记偏好的类别（业务自定义类别）一律投递，新增类别不会因漏登记而静默丢失。安全提醒的站内通知在过滤器里写死为投递，界面上也就没有这一项。
  - 邮件通道只发已验证邮箱，经模板既有的进程内后台队列（`IBackgroundTaskQueue`，队列满时放弃这一封）发送，SMTP 慢或失败不拖住触发提醒的请求；提醒发布失败只记日志，不让登录、改密码失败。
  - 提醒文案按**收件人**的界面语言渲染（本人设过语言用它，否则用本次请求的语言）。
  - "新设备"的判定：非模拟登录、上次登录 IP 已知且与本次不同、且本人没有同一 User-Agent 的有效会话。首次登录不提醒。

  - 顺带修正：布尔设置的开关此前只看本层的值，本层未覆盖时一律显示为关——默认开启的项会被误读为未开启（此前唯一的布尔设置默认为关，没暴露）。改为显示继承来的生效值。
  - 顺带修正：`appsettings.json` 的发件人名称写成了 `CompanyName ProjectName`（带空格，模板不替换），生成项目发出的信署名就是这串占位符；改为 `CompanyName.ProjectName`，生成时替换为项目名。

### 9. 操作记录保留期
- `OperationRecordRetentionOptions` 改为宿主级设置，归档后台任务每轮读取；配置文件作为回落。
- 落地时的取舍（阶段 9）：
  - 只把「是否归档」与「保留天数」做成宿主级设置（系统设置新增「审计」分组），默认值取配置文件，与日志级别同口径；执行时刻与批大小是部署调优参数，仍只在配置里。
  - 归档任务启动时不再因为"关着"就退出（那样打开后要重启才生效），改为照常排期、每轮取 `IOptionsMonitor<OperationRecordRetentionOptions>` 的当前值，关着就跳过本轮。是否归档与保留天数经宿主级设置配置源覆盖配置节（同发信参数，一行映射），执行时刻与批大小在构造时取一次；绕过接口写进库的越界天数由 Options 的区间校验拒绝，这一轮失败记日志、不搬记录。
  - 所有形态都有操作记录，因此 `BooleanSettings` / `NumericRanges` 与写入端的布尔、区间校验从"仅本地身份"改为全形态可用。
  - 顺带修正：Mock 数据里日志设置的分组写成了 `Logging`，与后端分组标识 `Operations` 不一致，Mock 下该面板拿不到图标。

    - 以 `Filter` 结尾的类型统一放 `Filters/`（框架与模板规范已补）。
    - 框架不再提前定义业务性的常量清单：删掉 `Constants/`（`NotificationChannels`、`NotificationTypes`）。站内渠道名是框架自己的契约，改为 `INotificationChannel.InAppName`；默认类型改为 `NotificationInputDto.DefaultType`；`DataChange`、`Workflow` 这类业务类别删除。模板的通知类别与渠道名放在应用层 `Application/Notifications`（`AppNotificationTypes`、`AppNotificationChannels`），通知偏好的设置名由它们拼出，不再手写字面量；前端铃铛的图标按类型查表，未登记的用通用图标。

    - 宿主级设置统一经配置源进 Options（见第 7、9 节）；原有的日志级别也并入：最小级别映射到 Serilog 自己订阅重载的 `Serilog:MinimumLevel`（标量与对象两种写法都写），请求日志级别成为 `RequestLoggingOptions`，删掉 `LoggingSettingState` / `LoggingSettingApplier` / `LoggingBaseline`。外部登录提供方改读已有的 `ExternalAuthOptions`，不再直接读 `IConfiguration` 的键。
    - 两步验证密钥的加解密并入 `TwoFactorAuthenticator`（后改名 `TwoFactorDomainService`），直接用 `IDataProtectionProvider`，删掉 `ITwoFactorSecretProtector` 及其实现。
    - 目录按规范归位：周期任务 `HostSettingRefreshJob`、`OperationRecordArchiveJob` 进 `HostedServices/BackgroundJobs`，启动一次性任务改名 `ApplicationInitializer`；刷新周期的 Options 拆到 `Api/Options`；登录编排与主体装配进 `Application/Auth/SignIn`，两步验证挑战存储进 `Application/Auth/TwoFactor`，手写 Base64Url 换成 `System.Buffers.Text.Base64Url`；前端外部绑定的暂存键改为 `app.auth.*` 命名。
    - 宿主级设置的应用时机按官方配置提供程序的语义收紧：首次应用在托管服务启动路径上完成（Web 服务器的托管服务排在最后，宿主开始接请求前值已就位）；写入后改为发布 `HostSettingChangedEvent`，事务提交后由处理器应用，回滚的写入不会先进配置；组合校验不过的一组整组不生效、沿用上一组，而不是保留坏值让每次取值都抛异常。
