# 文档即索引 —— 文档发现与防漂移的架构方案评估

> 面向 leistd-net **整个框架**的文档分发与 skill 发现机制的长远演进方向。本文只做方案评估（现状诊断 → 问题 → 目标架构 → 迁移路径 → 取舍），不含实现代码。是否采纳、何时采纳由维护者决定。
>
> **核心原则：文档即索引**——用 AI 能直接读的 markdown（入口页 + 文内表格 + 相对链接）承载导航与能力映射，**绝不引入需要解析的旁路清单文件（如 `index.json`）**；机器只做两件事：生成给 AI 读的 markdown、以及 CI 校验。理由见 §3.2。

---

## 1. 背景与触发

近期一系列审查暴露出三类反复出现的问题，它们的根因是**同一个**：

1. **文档描述与源码漂移**——组件文档写了源码里不存在的机制（event-bus 的 LogError/EventId、tracing 的 `IProxyGenerator`），或漏了真实公共 API（security 的 `IsSuperAdmin`、exception 的 `ConflictException`、di 的 `OnRegistrationProcessed`）。全部靠人工二次核对源码才发现。
2. **skill 索引与文档/源码漂移**——框架 skill 里手写的"组件清单""能力分工表""未覆盖能力清单"需要人肉维护，容易与真实包集合脱节。
3. **文档粒度与包粒度不对齐**——ddd-struct 一份文档跨 4 个包，只装 `Leistd.Ddd.Domain` 的消费者会看到需要 `Infrastructure` 的内容（如"挂载拦截器"引用了不在其包内的 `AuditSaveChangesInterceptor`）。

共同根因：**文档与 skill 索引都是"手写的、与源码结构硬耦合又不自动校验"的产物**。skill 的定位配方靠"手工拼固定文件名"，索引靠人肉维护，文档正确性靠人肉核对——规模一大就必然漂移。

---

## 2. 现状机制（已勘察）

### 2.1 文档打包（`framework/common.props`）
- 按**项目目录的父目录名** `_LeistdParentDir` 决定打哪份文档：
  - components：打 `docs/components/<父目录名>.md`（`Exists` 保护）。
  - ddd-struct：父目录名 == `ddd-struct` 时统一打 `docs/ddd-struct/ddd-struct.md`。
- 结果：**同家族每个包都内置同一份家族文档**；4 个 ddd 包都内置同一份 `ddd-struct.md`。

### 2.2 skill 定位配方（`skills/leistd-net-framework/SKILL.md`）
- 手工拼路径：`<缓存根>/<小写包名>/<版本>/docs/<家族>.md`，家族名与文件名**硬编码**在 skill 的索引表里。
- 组件清单、能力分工表、未覆盖能力清单：**全部手写**。

### 2.3 已具备的有利条件
- `GenerateDocumentationFile=true` 已全局开启——**每个包已产出 `<包名>.xml`**（精确到方法签名的 API 元数据），随 dll 同目录分发。这是"生成式索引"的现成数据源。
- 打包逻辑已是"按目录约定映射"，具备扩展成"按清单映射"的结构基础。

---

## 3. 目标架构（不考虑代价的理论最优）

三个支柱，从"手写硬耦合"转向"清单驱动 + 生成校验"。

### 3.1 支柱一：文档粒度对齐包粒度

每个包只带**讲自己**的聚焦文档；跨包的整体叙事由一份"总览"承担。

| 文档 | 打进哪个包 | 边界 |
| --- | --- | --- |
| `<家族>.md`（现状，components） | 该家族每个包 | 保持不变——components 本就一族一文件，已对齐 |
| `ddd-domain.md` | `Leistd.Ddd.Domain` | Entity/审计基类/IRepository 抽象/DataFilter/AddLocalEvent(登记) |
| `ddd-application.md` | `.Application` / `.Application.Contracts` | IAppService/DTO/分页/BaseAppService/MapPagedResult |
| `ddd-infrastructure.md` | `.Infrastructure` | AddDddInfrastructure/EfCoreRepository/BaseDbContext/挂拦截器/软删除过滤/事件发布装配 |
| `ddd-struct.md`（总览） | 打进 4 个 ddd 包 | 四层如何协作、端到端搭建路径，cross-link 到上面三份 |

收益：包自包含（只装 Domain 不会看到 Infrastructure 专属类型），彻底消除"文档引用包外类型"。

### 3.2 支柱二：稳定入口文档 + 文内导航（不引入旁路清单）

> **修正**：早期草案曾设想每包放一份机器可读的 `docs/index.json` 供 skill 解析。**已否决**——它与 AI 索引方式相悖：(a) AI 靠读自然语言 + 顺链接跳转来索引，解析自定义 json schema 是多一层间接、更易读漏；(b) json 声明的能力/文档列表与 `.md` 正文是**两处需保持一致的事实源**，制造了新的漂移面（正是我们要治的问题的同类）；(c) markdown 是 AI 的母语，结构化清单不是。**结论：文档即索引，不造旁路清单。**

正确做法——让文档本身成为好索引：

- **一个稳定入口文档 + 文内导航**：skill 只指向**一份**稳定 markdown（家族/基座的入口页，如 `ddd-struct.md` 总览、`components/README.md`）。入口页用自然语言 + markdown 表格 + 相对链接，列出"哪块能力看哪篇、每篇属于哪个包、哪些是某层专属"。AI 读入口、顺链接跳——这是 AI 最擅长的路径。
- **文档拆分/改名时只改这份入口页的链接**，skill 配方不动——入口页承担了原本想让 index.json 承担的"导航"职责，但它是 AI 能直接读、人也能读的形态。
- **能力→组件映射写进 markdown 表格**（就是现有 skill 与 README 里的"能力分工表""包归属表"），不写进 json。

skill 定位配方随之简化为：**解析缓存根 → 读该家族/基座的入口 markdown → 顺文内链接加载所需分篇**。没有解析层、没有旁路元数据。

### 3.3 支柱三：能力索引由源码/XML 生成，而非手写

skill 里的"组件清单 / 能力分工表 / 未覆盖能力清单"若要防漂移，可选**构建时生成**——但生成产物必须是 **markdown（AI 直接读的形态），而非结构化元数据**：

- 数据源：各包已产出的 `<包名>.xml`（公共 API 签名）+ 源码里的能力标注。
- 构建步骤：脚本扫描 XML + 标注，生成 `skills/leistd-net-framework/generated-index.md`（**markdown** 组件表、能力→组件映射、API 摘要）。skill 正文保留定位机制 + 使用约束，索引部分引用这份 md。
- **关键区分**：机器只做两件事——(1) 生成给 AI 读的 markdown；(2) CI 校验。**机器不产出给 AI 解析的 json/yaml**。防漂移的正解是 **CI 校验**（下条），不是造一份元数据。
- **CI 漂移校验**（本方案最高性价比的一环，可脱离其它阶段独立上）：脚本扫描文档正文里出现的 `Leistd.*` 类型名/方法名，与各包 `<包名>.xml` 比对——文档写了源码没有的（臆造）或漏了公共 API，CI fail。event-bus 的 `LogError`、tracing 的 `IProxyGenerator` 这类漂移会被直接拦下，无需人肉核对。

## 4. 迁移路径（分阶段，每阶段独立可交付）

| 阶段 | 内容 | 依赖 | 独立收益 |
| --- | --- | --- | --- |
| P0（即时） | ddd-struct.md 加「四层与包归属」表 + Infrastructure 专属节标注所需包 | 无 | 立刻消除 §1.3 的困惑，零机制改动 |
| P1（高性价比） | CI 漂移校验脚本：文档正文的 `Leistd.*` API 名 vs 包 XML，不一致 fail | 无 | 根治 §1.1/§1.2 的臆造/遗漏，独立可上 |
| P2 | 强化"入口文档 + 文内导航"：家族/基座入口页用 markdown 表格 + 相对链接承载导航与包归属；skill 只指向入口页 | P0 | skill 与文档结构解耦，且全程 markdown（AI 友好） |
| P3 | ddd 文档按层物理拆分（Domain/Application/Infrastructure + 总览入口页） | P2 | 包自包含 |
| P4（可选） | 能力索引生成脚本：从 XML + 标注生成 **markdown** 索引；skill 引用之 | P1、P2 | 索引不再手写、随源码更新 |

关键：**P0、P1 可立即做且各自独立收益**，其余是长期演进，任何一阶段停下都不破坏现状。**全程无旁路清单文件——AI 始终只读 markdown。**

---

## 5. 取舍与建议（诚实评估）

### 5.1 这套方案真正解决什么
- **漂移根治**（P5）：文档/索引与源码不一致会被 CI 拦截，不再靠人肉核对——这是我们这几轮反复在打的问题的根解。
- **skill 与文档结构解耦**（P3）：文档拆分/改名不再牵动 skill 配方。
- **包自包含**（P4）：消除跨包文档引用包外类型。

### 5.2 为什么"不考虑代价"也未必全上
- **规模匹配问题（非代价问题）**：15 components + 4 层 ddd，这个规模手工索引 + 单文档**目前 hold 得住**。`index.json` + 生成式索引是给"包数量多到人工维护不过来"准备的解药；现在上，是**用规模复杂度的药治一个还没到那个规模的病**——架构上的过度设计。
- **ddd 的强内聚特性（非代价问题）**：ddd 四层是"搭一个 DDD 项目"的单一心智模型，不是四个可独立取用的能力。物理四拆（P4）虽让"包自包含"，却把**初学者的学习路径切成四篇**——清单机制解决"skill 找得到"，但解决不了"人读起来割裂"。而 ddd 文档的首要受众正是初次搭建者。

### 5.3 分层建议
- **强烈建议现在做 P0**：包归属表，即时收益、零风险、不动机制、不动 skill。
- **建议现在做 P5 的轻量版**：即使不上 index.json，也值得先加一个**"文档 API 引用 vs 源码"的 CI 校验脚本**（扫描文档里的 `Leistd.*` 类型/方法名，与 XML 比对，漂移即告警）——这单独就能拦住 §1.1/§1.2 那类漂移，且不依赖其它阶段。
- **P1-P4 暂缓**：等到出现"包数量显著增长"或"消费者频繁只装 ddd 子集"的真实信号，再启动清单化与物理拆分。届时 P0 的包归属表已是拆分的现成蓝图。
- **ddd 物理四拆（P4）需单独权衡**：即便走到清单化，也要评估"包自包含"的收益是否值得牺牲"整体叙事连贯"——对 ddd 这类强内聚基座，我倾向**保留单份总览 + 聚焦文档并存**，而非纯四拆。

---

## 6. 一句话结论

最优方向是"**文档即索引**：聚焦文档 + 稳定入口页（markdown 导航）+ CI 漂移校验 +（可选）生成式 markdown 索引"，**不引入 `index.json` 之类旁路清单**（它与 AI 索引方式相悖、且制造新漂移面，见 §3.2）。对**当前规模**和 **ddd 的强内聚特性**，物理拆分与生成式索引暂非必需；**务实最优 = 立刻做 P0（包归属表）+ P1（文档-源码漂移 CI 校验），其余按真实规模信号渐进启动**。
