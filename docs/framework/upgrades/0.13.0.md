# 从 0.12.0 升级到 0.13.0

本指南适用于 0.13.0 正式版及其全部预发布版本（`0.13.0-beta.N`、`0.13.0-preview.<日期>.<序号>`）。
分两部分：

- **[框架](#框架)**：先读[跨家族变化](#跨家族变化)，再只读项目引用的组件家族小节。
- **[模板（生成项目）](#模板生成项目)**：由 0.12.0 模板生成、需要同步模板改动的项目阅读。

每条按四项书写：受影响的是什么、原来怎么写、现在怎么写、必须执行的迁移动作。不兼容类型：

- **二进制**：源码不改也能编译，但已编译的调用方必须重新编译；
- **源码**：必须改代码或配置才能编译、启动；
- **行为**：照常编译，运行结果变化，需要核对或改数据。

迁移顺序：先处理包级动作（[包改名](#包改名与移除)），再改版本与 `using`，然后逐条处理其余条目；有数据库模型变化的按条目生成并检查迁移。

## 框架

### 成员清单的来源

本指南不是从提交脚注回忆的：两个版本的公共成员清单都取自 Release 的随包 XML
（`<member name="…">` 逐条），再逐包比对得出，结果见[公共表面逐条对比](0.13.0-api-diff.md)（212 条，按包分组）。

0.12.0 当时 `NoWarn` 里含 CS1591，随包 XML 并不完整，因此：

- **删除与搬迁是可信的**——当时记录在案、现在没有，就是真的变了；
- **"新增"不列**——里面会混入"0.12.0 时就有、只是没写 XML 注释"的成员，噪声大于价值。
  新能力看 GitHub Release Notes 的「新增」小节。

0.13.0 之后不再有这个问题：CS1591 已经是 Release 下的错误，随包 XML 从此完整。

### 跨家族变化

#### 包改名与移除

- **类型**：源码
- **受影响**：引用下列包的项目文件（`PackageReference` 或 CPM 的 `PackageVersion`）。
- **原来 → 现在**：

  | 0.12.0 | 0.13.0 |
  | --- | --- |
  | `Leistd.Exception.Core` | `Leistd.ExceptionHandling.Core` |
  | `Leistd.Exception.AspNetCore` | `Leistd.ExceptionHandling.AspNetCore` |
  | `Leistd.UnitOfWork.EfCore` | `Leistd.UnitOfWork.EntityFrameworkCore` |
  | `Leistd.ObjectMapping.AutoMapper` | 已移除，改用 `Leistd.ObjectMapping.Mapster`（见[对象映射](#对象映射)） |

  `Leistd.RealTime.AspNetCore.SignalR` 里与通知无关的通用 Hub 基建移到了新包 `Leistd.AspNetCore.SignalR`；
  `Leistd.Security.Core` 与 `Leistd.Ddd.Domain` 各有一个通用原语（`IDisposable` 辅助类型）下沉到 `Leistd.Core`。
  分页契约移到新包 `Leistd.Data`（见[数据](#数据)），租户管理用例移到新包 `Leistd.MultiTenancy.Management`（见[多租户](#多租户)）。
- **迁移**：按表改包名；`Leistd.Authorization.Resource.AspNetCore` 的变化见[资源实例授权](#资源实例授权)。

#### 包依赖的变化

- **类型**：源码（项目文件、锁文件与许可清单）
- **受影响**：锁文件、许可清单，以及在架构门禁里限制"应用层/领域层能引用什么"的项目。
- **原来 → 现在**：本版有若干包新增了直接依赖（例如远端租户连接解析为路由缓存引入了
  `Microsoft.Extensions.Caching.Hybrid`，`Leistd.Email.Smtp` 新增依赖 `Leistd.Core`，
  `Leistd.Authorization.EntityFrameworkCore` 新增依赖 `Leistd.MultiTenancy.Core`、`Leistd.UnitOfWork.EntityFrameworkCore`、
  `Leistd.DependencyInjection`，`Leistd.OperationRecords.Core` 直接依赖 `Leistd.ExceptionHandling.Core`）。
  **这里不列完整清单**：人工抄的清单会错，也会漏。
- **迁移**：按打出来的 `nuspec` 逐包对比——那才是真正进入消费者依赖图的东西：

  ```bash
  # 两个版本各解开一份，比较 <dependencies> 节
  unzip -p Leistd.MultiTenancy.Core.0.12.0.nupkg '*.nuspec' > old.nuspec
  unzip -p Leistd.MultiTenancy.Core.0.13.0.nupkg '*.nuspec' > new.nuspec

  # ① 直接依赖的包名增删
  diff <(grep -o 'id="[^"]*"' old.nuspec) <(grep -o 'id="[^"]*"' new.nuspec)

  # ② 版本约束与目标框架分组也变了的话，比整节
  diff <(sed -n '/<dependencies>/,/<\/dependencies>/p' old.nuspec) \
       <(sed -n '/<dependencies>/,/<\/dependencies>/p' new.nuspec)
  ```

  ① 只看**直接依赖的包名增删**，版本约束升降与 `targetFramework` 分组变化它看不出来，那些要用 ②。
  内部的项目引用变动不必逐条关心——只有出现在 `nuspec` 里的才会传递给消费者。
  架构门禁的白名单按这份对比结果更新；框架侧的 Core 包一律只依赖抽象（`Microsoft.Extensions.*` 与 `*.Abstractions`），
  见 `docs/architecture/design-principles.md` §1.1。

#### 取包时的版本陷阱

- **类型**：源码（项目文件）
- **受影响**：用浮动版本或 `--prerelease` 引用预发布包的项目。
- **原来**：`dotnet add package Leistd.Core --prerelease` 或浮动预发布版本。
- **现在**：nuget.org 上存在 `1.0.0-beta.22` 与 10 个 `1.0.0-preview.*`，SemVer 排序高于 `0.13.0-*`，浮动解析会取到它们。
- **迁移**：在它们被 unlist 之前，**预发布依赖必须写全称**（如 `0.13.0-beta.170`），不要用 `--prerelease`。
  成因见[版本规范](../versioning.md)的「nuget.org 上存在版本号虚高的历史预发布包」。

- **受影响**：扣掉命名空间纯搬迁后，仍有 **212 条**成员是真正删除或签名改变的。按包排列的前几位：

#### 宿主级组件的注册入口统一为 `AddX(configure?, configSectionPath?)`

- **类型**：源码、行为
- **受影响**：`AddUnitOfWork`、`AddMultiTenancy`、`AddGlobalExceptionHandler`、`AddSmtpEmailSender`、`AddRedisDistributedLock(connectionString, …)`
  的 `IConfiguration` 重载（`AddServiceUserContext` 的同类重载随服务间用户委托一并删除，见[服务客户端](#服务客户端)），
  多租户与工作单元注册类上的 `ConfigurationSection` 常量，以及 `AddDddInfrastructure(configure)`。
- **原来**：`AddXxx(builder.Configuration)` 绑定配置节；委托重载**不绑定**配置节，写在 appsettings 里的值静默不生效。
- **现在**：统一从容器里的 `IConfiguration` 绑定默认配置节，委托在绑定之后应用（代码覆盖配置）。
  `AddDddInfrastructure(configure)` 经此同样绑定 `Leistd:UnitOfWork`。
- **迁移**：调用处去掉 `builder.Configuration` 实参；配置节不在默认路径时传 `configSectionPath`。
  `ConfigurationSection` 常量改用 `MultiTenancyOptions.SectionName`、`UnitOfWorkOptions.SectionName`。
  无主机的 `ServiceCollection`（测试、工具）需自行注册 `IConfiguration`。
  只用委托重载的宿主核对 appsettings 里的值，它们升级后开始生效。

#### 末尾新增 `configSectionPath` 参数

- **类型**：二进制
- **受影响**：`AddInProcessBackgroundJobs(configure?, configSectionPath?)`（进程内调优取其下的 `InProcess` 子节）、
  `AddNotificationRetention<T>(configure?, configSectionPath?)`、`AddOperationRecordRetention<T>(configure?, configSectionPath?)`、
  `AddHostSettings(bind, configSectionPath?)`、`AddRemoteTenantConnectionResolution(configSectionPath?)`。
- **原来**：没有该参数，固定读默认配置节。
- **现在**：源码兼容，按位置传参的调用不受影响；校验消息按实际路径报键；同一入口重复调用换用另一配置节时抛 `InvalidOperationException`。
- **迁移**：已编译的调用方重新编译。

#### 没有新增必填配置项

- **类型**：行为
- **受影响**：0.12.0 已有组件的配置。
- **原来 → 现在**：这些配置在 0.13.0 都保持可选并带默认值。新增的是两处**启动期校验**（Redis 锁的租约与重试间隔、
  链路标识的请求头名），越界值从"运行期静默异常"改成启动失败，见[锁](#锁)与[链路与关联标识](#链路与关联标识)。
  0.13.0 新增的组件家族（多租户、操作记录、后台任务、设置、本地化、邮件、资源与数据范围授权、服务客户端）
  按各自组件文档第一节接入，不是升级动作。
- **迁移**：原先配的是合法值就不受影响。

### 核心原语

#### 新增脱敏入口 `TextRedactor`

- **类型**：行为（新增公共入口，供日志口径调整使用）
- **受影响**：需要在日志或对外展示中脱敏联系方式的代码。
- **原来**：没有框架入口。
- **现在**：`Leistd.Redaction.TextRedactor`（`Leistd.Core`，纯静态方法、无需注册、无新依赖）：
  `RedactEmail(address)` → `al***@example.com`（保本地部开头几位 + 完整域名：从第一个字母或数字起最多 3 位且不超过一半——
  `zhangsan@`→`zha***@`、`alice@`→`al***@`、`bob@`→`b***@`）；`RedactPartially(value, keepStart, keepEnd)` → `158***90`
  （位数由业务定：手机号常用 `(3,2)`，卡号按 PCI DSS 最多 `(6,4)`，证件号 `(0,4)`）。写日志与对外展示共用。
  **只提供形态，不维护数据类型目录**——不要期待框架为每种业务数据加方法。
- **迁移**：自己写的日志按"联系方式（邮箱、手机号）不进日志"的口径核对，需要时经它脱敏。
  框架没有引入脱敏组件（`Microsoft.Extensions.Compliance.Redaction`），理由与对派生项目有用的两条实测结论见[模板的日志口径](#日志不再出现邮箱原文)。

### 数据

#### 分页契约上移到新包 `Leistd.Data`

- **类型**：源码
- **受影响**：使用分页 DTO 的应用层与组件消费者。此前漏写提交脚注的一条。
- **原来 → 现在**：

  | 0.12.0 | 0.13.0 |
  | --- | --- |
  | `Leistd.Ddd.Application.Contracts.Dtos.PagedRequestDto` | `Leistd.Data.Paging.PageRequest` |
  | `Leistd.Ddd.Application.Contracts.Dtos.PagedResultDto<T>` | `Leistd.Data.Paging.PagedResult<T>` |

  同时换了三样：**包**（`Leistd.Ddd.Application.Contracts` → `Leistd.Data`）、**命名空间**、**类型名**（去掉 `Dto` 后缀）。
  分页不是 DDD 应用层的概念，组件（多租户、操作记录）也要用它，留在 DDD 契约包里会让纯组件消费者被迫依赖 DDD 分层。
  `Leistd.Data` 同时承载连接串契约（`Leistd.Data.Connections.ConnectionStringNames` / `IConnectionStringResolver` /
  `ConnectionStringNameAttribute`），这些在 0.12.0 尚不存在。
- **迁移**：引用 `Leistd.Data`，按表改类型名与 `using`。

### 依赖注入与动态代理

#### `AddInterceptor` 按类型去重

- **类型**：行为
- **受影响**：组件的 `AddXxx` 被调用两次的宿主。
- **原来**：同一拦截器被织入两层。
- **现在**：按类型去重，只织入一层。`ServiceRegistrationCallbackFactory.CreateBuilder` 改为 `virtual`，派生工厂可覆写；
  `DynamicProxyServiceRegistrationCallbackFactory` 在此登记 `DynamicProxyWeavingMarker`（工作单元的启动检查依赖它，见[工作单元要求代理工厂](#工作单元要求代理工厂)）。
- **迁移**：无需改代码；依赖重复织入效果的宿主核对行为。

### 异常处理

#### 异常类不再携带 HTTP 语义

- **类型**：源码
- **受影响**：`BadRequestException`、`NotFoundException`、`ConflictException`、`UnauthorizedException`、`ForbiddenException`、
  `UnprocessableEntityException`、`UnsupportedMediaTypeException`、`InternalServerException`、`ServiceUnavailableException`，
  以及 `Leistd.Core.CommonException`、`GenericErrorCodes` 与旧的 `ValidationError`——全部已移除。
  `StatusCode`、`Details`、`WithCode`、`WithDetails` 不再是异常 API。
- **原来**：`new NotFoundException(message).WithCode(code)`，异常类决定 HTTP 状态。
- **现在**：

  - 参数、对象状态、基础设施或传输失败优先用 .NET 内置异常，如 `ArgumentException`、`InvalidOperationException`、
    `HttpRequestException`。这些异常默认对外只产生通用 500，不会泄露内部消息。
  - DTO 输入校验使用 DataAnnotations 与 `[ApiController]`；显式调用 `Validator` 产生的
    `System.ComponentModel.DataAnnotations.ValidationException` 也映射为 400。
  - 可预期业务规则失败统一使用 `new BusinessException("Order:NotFound", "The order was not found.")`。第二个参数必须是
    可安全展示的回退文案；需要本地化占位符时继续调用 `WithData`。
  - `BusinessException` 未命中宿主映射时返回 400；422 只在宿主需要表达更精确的内容处理语义时按错误码显式映射。
- **迁移**：`new NotFoundException(message).WithCode(code)` 改为 `new BusinessException(code, message)`，并在宿主注册时用
  `options.MapCode(code, 404)` 映射传输状态；400、401、403 与 409 同理（回退到 400 的错误码无需登记）。
  业务项目将错误码常量放在实际拥有它的 Domain/Application 模块，而不是统一堆入 Shared。

#### 组件默认映射由组件自行登记

- **类型**：源码
- **受影响**：宿主的异常映射配置；`GlobalExceptionOptions`、`ExceptionDescriptor` 的命名空间；各组件的映射类。
- **原来**：宿主逐个调用组件 `*ExceptionMappings.Configure`；映射类位于各自的 `*.AspNetCore` 包。
- **现在**：组件拥有的非默认 HTTP 语义由组件在自己的 `AddXxx` 里登记（`MapDefaultCode` / `MapDefaultException`），
  **宿主不需要逐个调用**，宿主 `MapCode` / `MapException` 始终可覆盖，调用顺序无关；HTTP 状态映射只在代码里声明，不提供配置文件入口。
  `GlobalExceptionOptions` 在 `Leistd.ExceptionHandling.Options`，`ExceptionDescriptor` 在 `Leistd.ExceptionHandling.Descriptors`，
  两者都由 `Leistd.ExceptionHandling.Core` 提供（只有状态码、错误码、文案与日志级别，与响应序列化形式无关）。
  各组件的默认映射成为 Core 包的内部实现，不再公开。
- **迁移**：宿主的 `ApiExceptionMappings` 只列项目自己的错误码，以及需要覆盖组件默认值的那几条；删掉逐个调用
  组件 `*ExceptionMappings.Configure` 的那几行。已按 0.13.0 早期形态适配过的项目：两个选项类型此前在
  `Leistd.ExceptionHandling.AspNetCore.Options` 与 `.Descriptors`，只需改 `using`。
  定制宿主对精确类型调用 `MapException<TException>()`（委托可按异常属性分支）；需要完全接管某类异常时按 ASP.NET Core 方式
  再注册一个 `IExceptionHandler`；要替换整个失败响应的序列化形状，注册 ASP.NET Core 的 `IProblemDetailsWriter`。

#### 全局异常处理的启用开关已删除

- **类型**：源码、行为
- **受影响**：`GlobalExceptionOptions.Enabled` 与配置键 `Leistd:GlobalException:Enable`。
- **原来**：0.12 的 `Leistd:GlobalException:Enable` 默认为 `false`：注册了处理器却没打开它时，处理器不接管异常。
- **现在**：调用 `AddGlobalExceptionHandler()` 并挂上 `UseGlobalExceptionHandler` 就会接管——0.12 里注册了但没打开 `Enable`
  的宿主，升级后异常响应会变成 Problem Details。旧的 `Enable` 配置键不再被读取。
- **迁移**：删掉对 `Enabled` 的赋值与配置里的 `Enable` 键；临时关掉全局异常处理时不注册它，排查时不挂 `UseGlobalExceptionHandler`。

#### 业务异常处理器按实现去重

- **类型**：行为
- **受影响**：重复调用 `AddGlobalExceptionHandler` 的宿主。
- **原来**：业务异常处理器重复登记。
- **现在**：按实现去重。
- **迁移**：无需改代码。

#### `ExcludePatterns` 已删除

- **类型**：源码、行为
- **受影响**：`GlobalExceptionOptions.ExcludePatterns`（配置键 `Leistd:GlobalException:ExcludePatterns`）。
- **原来**：命中路径跳过全局处理。
- **现在**：已删除——命中路径只会丢掉业务映射、仍返回同一种问题详情，健康检查也不需要它（检查项异常由健康检查服务自行捕获）。
- **迁移**：删掉该配置；个别路径需要其他错误格式时，在 `AddGlobalExceptionHandler` 之前注册自己的 `IExceptionHandler`，按路径判断后返回 `true`。

#### 默认失败响应改为 Problem Details

- **类型**：行为、源码
- **受影响**：全部失败响应、`BusinessMessageExposure`、`Error:*` 词条与 `ProblemTypes.SystemError`。
- **原来**：自定信封（`message`/`details`/`code`），输入校验、未预期异常也带 `Error:*` 码；`BusinessMessageExposure` 控制业务文案是否外露。
- **现在**：默认失败响应为 RFC 9457 Problem Details，稳定业务码在字符串 `code` 扩展字段；所有失败响应统一经 ASP.NET Core
  `IProblemDetailsService` 写出，定制只走 `ProblemDetailsOptions.CustomizeProblemDetails`：

  - 只有 `BusinessException` 带 `code` 扩展与 `detail`；输入校验、未预期异常和上游故障不再返回 `Error:*` 码，依据 HTTP 状态分支。
    `Error:*` 词条与 `ProblemTypes.SystemError` 已删除。
  - `BusinessMessageExposure` 已移除：业务异常的安全文案始终可展示，未预期异常始终回退为通用系统错误。
  - 如宿主显式调用 `AddResponseWrapper()`，成功与失败都使用可选数字信封：数字 HTTP/业务状态放在 `code`，稳定业务错误码放在 `errorCode`；
    MVC 的 `NotFound()`、`Problem()` 等错误结果与状态码页同样输出信封。
  - 框架判定的请求错误 `BadHttpRequestException`（Minimal API 请求体解析失败、请求体过大等）按异常自带的状态码返回，不再报 500。
    框架只写状态码、不写响应体的失败（生产环境的请求体解析失败、415、未匹配路由、认证质询、限流）默认没有响应体。
    这类协议层失败只带状态码、本地化标题与 `traceId`，不合成业务错误码。
  - 客户端取消的判断移出异常组件：官方 `ExceptionHandlerMiddleware`（.NET 8+）在调用处理器之前直接返回 499，行为不变。
- **迁移**：删掉对 `BusinessMessageExposure`、`Error:*` 码与 `ProblemTypes.SystemError` 的引用，客户端按 HTTP 状态分支；
  需要协议层失败的标准响应体时，在 `UseGlobalExceptionHandler()` 之后用 `UseWhen` 把 ASP.NET Core 的 `UseStatusCodePages()`
  限定到 API 路径。前端读取字段的改法见下一条。

#### 失败响应的字段变化（前端要改的地方）

- **类型**：行为
- **受影响**：解析失败响应的客户端（默认不套信封的形态）。
- **原来 → 现在**：`message`/`details` 是本框架自定的扩展字段，`detail`/`errors` 是 RFC 9457 的标准字段。
  前端按旧名读会拿到 `undefined`，界面上通常表现为"错误提示是空的"，不是报错——**这条漏改是静默的**。

  | 旧（自定信封） | 新（Problem Details） | 说明 |
  | --- | --- | --- |
  | `message` | `detail` | 可展示的错误文案。只有 `BusinessException` 有；协议层失败为空，改读 `title` |
  | `details` | `errors` | 字段级错误数组，元素形状不变（`detail` / `field` / `code`） |
  | `code` | `code`（扩展字段） | **不变**，仍是稳定业务错误码。前端的分支逻辑不用动 |
  | — | `title` | 新增：按状态码本地化的标题。没有 `detail` 时用它做兜底文案 |
  | — | `status` / `type` / `instance` | 新增：RFC 9457 标准字段 |
  | `traceId` | `traceId`（扩展字段） | 不变 |

  **启用了 `AddResponseWrapper()` 的宿主不受影响**：数字信封的 `message` 保持原样，它的 `errorCode` 承载业务码。
- **迁移**：一处收口，不要散在各个请求里：解析错误响应的那一个函数按 `detail ?? title` 取文案、按 `errors` 取字段错误、按 `code` 分支。
  模板前端的对应改动见[错误解析认官方字典形 `errors`](#错误解析认官方字典形-errors)。

#### 自动 400 的字段名与 `IValidatableObject` 文案

- **类型**：行为、源码
- **受影响**：`ConfigureApiValidation` 产生的 `errors[].field`；`IValidatableObject.Validate` 的实现。
- **原来**：查询参数等逐属性绑定的来源沿用绑定时的 C# 属性名（`?roles=` 校验失败报 `Roles`）；`Validate` 的错误与特性错误口径不同。
- **现在**：字段名在这些来源上也跟随 JSON 命名策略，报 `roles`；带参数名前缀绑定的报 `input.roles`。
  `Validate` 的错误与特性错误同一口径：`MemberNames` 写 `nameof(...)`，字段名换成 JSON 名（含嵌套前缀）；宿主启用
  `AddDataAnnotationsLocalization` 时，`ErrorMessage` 作资源键，经 `DataAnnotationLocalizerProvider`（以该 DTO 类型为参数）翻译。
  未设命名策略的宿主不受影响。
- **迁移**：按大小写敏感比对旧字段名（`Roles`、`RedirectUris`）的客户端改用 JSON 名；`Validate` 里手写 camelCase 成员名、
  从 `ValidationContext` 取 `IStringLocalizer` 的写法删除，改回 `nameof(...)` 与固定英文句，并在资源中备该句词条
  （模板四个输入 DTO 已按此简化）。

### 响应包装

#### `ExceptionResult` 与控制器失败辅助方法删除

- **类型**：源码
- **受影响**：`ExceptionResult`；`ControllerExtensions.FailResult` / `FailResultWithErrors` 与 `ErrorResult`。
- **原来**：控制器构造失败信封返回。
- **现在**：可选数字信封统一使用 `Result`；失败一律抛业务异常，由异常处理管道写出；启用 `AddResponseWrapper()` 时同样得到带
  `traceId` 与 `errorCode` 的信封。
- **迁移**：直接引用 `ExceptionResult` 的改为构造 `Result` 并填充 `Code`、`Message`、`TraceId`、`ErrorCode` 与可选 `Errors`；
  仍需在代码里构造信封时用 `Result.Fail(code, message) with { Errors = … }`；其余改为抛 `BusinessException`。

### 工作单元

#### `IUnitOfWork` 收敛

- **类型**：源码、二进制
- **受影响**：自己实现过 `IUnitOfWork` 或使用实现类的代码。`Leistd.UnitOfWork.Core` 的 53 条变更里绝大多数是内部实现类型的公开面收敛。
- **原来**：`IUnitOfWork.SetOuter` 在接口上；实现类名为 `UnitOfWork`。
- **现在**：`SetOuter` 移出接口，只留在实现类上；实现类改名 `DefaultUnitOfWork`；接口新增 `Disposed` / `Failed` 两个事件。
  接口本身的 `Id` / `IsCompleted` / `CompleteAsync` / `RollbackAsync` / `Initialize` / `AddPendingEvents` 保持不变。
- **迁移**：自定义实现补两个事件、去掉接口上的 `SetOuter`；引用 `UnitOfWork` 类的改为 `DefaultUnitOfWork`。

#### 工作单元要求代理工厂

- **类型**：行为
- **受影响**：调用 `AddUnitOfWork()` 但没有接 `DynamicProxyServiceRegistrationCallbackFactory` 的宿主。
- **原来**：漏接时 `[UnitOfWork]` 不生效、事件处理器在提交前后各执行一次，且不报错。
- **现在**：`AddUnitOfWork()` 注册启动检查，宿主未接代理工厂时启动失败。
- **迁移**：`WebApplicationBuilder` 用 `builder.Host.UseServiceProviderFactory(...)`，`HostApplicationBuilder` 用 `builder.ConfigureContainer(...)` 接上该工厂。

#### `BeginAsync` 改为同步的 `Begin`

- **类型**：源码
- **受影响**：`IUnitOfWorkManager.BeginAsync` 的调用方与自定义实现。
- **原来**：`using var uow = await manager.BeginAsync(...)`。
- **现在**：`using var uow = manager.Begin(...)`，返回 `IUnitOfWork`。原方法本就没有异步操作。
- **迁移**：改调用与自定义实现的签名。**工作单元由使用它的那个方法自己开启**：当前工作单元存放在 `AsyncLocal` 里，
  在 `async` 辅助方法里开启后返回，调用方拿到的不是它的当前工作单元，写入会各自提交，且没有任何报错。

#### 工作单元日志分级

- **类型**：行为
- **受影响**：依赖工作单元日志做告警的运维配置。
- **原来**：取消与回滚都按较高级别记录（回滚记 Warning）。
- **现在**：调用方主动取消（取消异常且令牌已取消）且发生在提交开始之前：事务型改记 Debug（什么都没提交），非事务型记 Warning
  （已保存的部分不会回滚）；提交开始之后的失败、令牌未取消的取消异常（如数据库超时）与其余提交失败仍记 Error。
  回滚日志由 Warning 改为 Debug：每次业务拒绝都会回滚，原因已由异常处理记下。
- **迁移**：依赖这两条日志做告警的，改为按提交失败的 Error 告警。

#### 声明式工作单元把方法的取消令牌交给提交

- **类型**：行为
- **受影响**：带 `[UnitOfWork]` 且声明了 `CancellationToken` 参数的方法。
- **原来**：`UnitOfWorkInterceptor` 以不可取消的令牌调用 `CompleteAsync`；客户端断开后事务照常提交。
- **现在**：以方法声明的第一个 `CancellationToken` 参数调用 `CompleteAsync`（按参数类型取，object 参数里装箱的令牌不算），
  BeforeCommit 处理器收到同一个令牌；客户端在提交开始前断开时，事务型工作单元不再提交，取消按调用方取消记 Debug，
  不再记成 Error "commit failed"。提交开始之后不响应取消，语义不变。
- **迁移**：依赖"请求已中止仍要落库"的方法，不要把请求令牌传进带 `[UnitOfWork]` 的方法，或在方法内自行开启不可取消的工作单元。

#### 工作单元选项校验

- **类型**：行为
- **受影响**：`UnitOfWorkOptions` 的 `Timeout`、`IsolationLevel` 配置与 `Begin(options)` 的单次选项。
- **原来**：不足 1 秒的 `Timeout` 被截成 0（等于不限时）。
- **现在**：默认选项在启动期校验，单次选项按同一规则在创建工作单元前校验。`Timeout` 只能为空或在 1 秒到 `int.MaxValue` 秒之间，
  `IsolationLevel` 只能为空或已定义值；配置错误抛 `OptionsValidationException`（按实际配置节报键），方法参数错误抛
  `ArgumentOutOfRangeException`；非整秒值改为向上取整。`AddUnitOfWork` 重复调用换用另一配置节时抛出。
- **迁移**：修正越界配置。

#### 提交后处理失败不再中断后续事件

- **类型**：行为
- **受影响**：工作单元 AfterCommit 队列的事件处理器与其调用方。
- **原来**：某个事件分发失败即中断。
- **现在**：某个事件分发失败后继续处理后续事件，全部分发完再上抛：单个异常保留原实例、类型与堆栈，多个异常聚合。
  事务已经提交，不再回滚；诊断区分提交失败与已提交后的处理失败。
- **迁移**：调用方不能将该异常当作事务未提交而盲目重试；按聚合异常处理的代码核对异常类型。

### DDD 基座

#### `BaseDbContext` 单参构造已删除

- **类型**：源码
- **受影响**：派生自 `BaseDbContext` 的上下文。
- **原来**：`BaseDbContext(DbContextOptions)` 单参构造，曾让租户过滤退化为宿主视角、审计与运行时开关失效。

- **受影响**：只改了子实体或只登记了事件的聚合根。
- **原来**：聚合根保存时为 `Unchanged` 时，它登记的事件被静默清掉。
- **现在**：这些事件会发布。
- **迁移**：核对依赖"不发布"的处理器。

#### 无当前用户时 `LastModifierId` 置空

- **类型**：行为
- **受影响**：后台作业、机器主体的修改。
- **原来**：沿用上一次的修改人。
- **现在**：置空。
- **迁移**：按修改人统计或筛选的查询核对空值。

#### `AddDddInfrastructure()` 注册本地事件总线

- **类型**：源码
- **受影响**：单独调用 `AddLocalEventBus()` 的宿主；直接构造 `LocalEventSaveChangesInterceptor` 的代码。
- **原来**：需单独注册事件总线；缺事件总线时解析 DbContext 抛异常。
- **现在**：`AddDddInfrastructure()` 自带本地事件总线（重复调用无害，注册已幂等）；`LocalEventSaveChangesInterceptor` 的两个构造参数改为必需。
- **迁移**：可删掉单独的 `AddLocalEventBus()`；直接构造拦截器的代码补齐参数。

#### `AddDddInterceptors` 删除，由 `AddDddDbContext<T>()` 挂载保存拦截器

- **类型**：源码
- **受影响**：`AddDbContext` 回调里的 `options.AddDddInterceptors(sp)`。
- **原来**：手工挂载；漏挂时审计、领域事件与并发标记三项静默失效。
- **现在**：派生自 `BaseDbContext` 的上下文登记时自动挂上这三个拦截器，与注册先后无关；其他上下文不挂载。
- **迁移**：删掉 `options.AddDddInterceptors(sp)`，改用 `AddDddDbContext<T>()` 登记。

#### `ConfigureByConvention()` 删除，改为 EF Core 约定 `DddEntityConvention`

- **类型**：源码、行为（模型变化）
- **受影响**：实体配置里的 `b.ConfigureByConvention()`；覆写 `BaseDbContext.ConfigureConventions` 的上下文；所有实现审计或并发标记契约的实体。
- **原来**：约定只作用于调用了 `ConfigureByConvention` 的实体。
- **现在**：`BaseDbContext` 自动注册 `DddEntityConvention`，对所有实现审计或并发标记契约的实体生效，显式 Fluent 配置优先。
  `BaseDbContext.ConfigureConventions` 已封闭。**会改变模型，两处**：① 此前未调用 `ConfigureByConvention` 的审计实体，
  审计人列（`CreatorId` / `LastModifierId` / `DeleterId`）列长变为 64；② **`ConcurrencyStamp` 变为限长 40、必填、并作为并发令牌**，
  未 opt-in 的实体都需要迁移。
- **迁移**：删掉 `b.ConfigureByConvention()`；原 `ConfigureConventions` 覆写改为 `ConfigureModelConventions`（无需调 `base`）；
  不继承基类的上下文如需同一约定，自行 `configurationBuilder.Conventions.Add(_ => new DddEntityConvention())`。
  升级后按 ddd-struct 文档"迁移快照检查"一节确认并生成迁移（接入该检查后它会报出这处模型差异，没接入的项目要自己核对）。
  旧库里若有 `ConcurrencyStamp` 为空或超过 40 字符的行（来自绕过保存拦截器的写入——手写 SQL、批量导入，或 EF 自己的
  `ExecuteUpdate`/`ExecuteDelete`；走 `SaveChanges` 的拦截器一直写 32 位值），迁移会失败：先把这些行补齐或截断，再执行。
  表现是会报错的迁移失败，不是数据错误。

#### DDD 基础设施的服务生存期

- **类型**：行为
- **受影响**：`LocalEventSaveChangesInterceptor`、`IQueryableAsyncExecuter`、`IDataFilter`、`IDataFilter<>` 的注册。
- **原来**：拦截器为 Scoped；三个服务直接注册，覆盖宿主先登记的实现。
- **现在**：`LocalEventSaveChangesInterceptor` 改为 Transient；三个服务改为 `TryAdd`，宿主先登记的实现保留。
- **迁移**：依赖被覆盖的宿主核对实际生效的实现。

### 锁

#### `ILock` 不再注册；内存锁与 Redis 锁可共存

- **类型**：源码、行为
- **受影响**：注入 `ILock` 的代码；同时注册内存锁与 Redis 锁的宿主。
- **原来**：`ILock` 可注入；两者同时注册时总是内存锁生效。
- **现在**：`ILock` 不注册；`AddRedisDistributedLock` 替换 `AddMemoryLocalLock` 的 `IDistributedLock` 兜底（与顺序无关）；
  宿主自行注册的 `IDistributedLock` 不被覆盖。
- **迁移**：改注入 `IDistributedLock` 或 `ILocalLock`；核对原先以为在用 Redis、实际用的是内存锁的场景。

#### Redis 锁选项启动期校验

- **类型**：行为
- **受影响**：Redis 锁的租约与重试间隔配置。
- **原来**：越界值在运行期静默异常。
- **现在**：越界值启动失败。
- **迁移**：修正越界配置；合法值不受影响。

### 链路与关联标识

#### `[CorrelationId]` 特性与拦截器、`Create()` 删除

- **类型**：源码
- **受影响**：`[CorrelationId]` 特性与拦截器（没有使用方）、`ICorrelationIdProvider.Create()`。`Leistd.Tracing.Core` 不再依赖动态代理。
- **原来**：特性标注建立关联标识；`Create()` 生成新值。
- **现在**：非 HTTP 入口用 `IAmbientContext.Begin(principal, correlationId)` 建立作用域，进程内后台队列自动捕获还原；
  还原关联标识时同时打开日志作用域 `leistd.correlationId`。
- **迁移**：删掉特性；需要新值时用 `ActivityTraceId.CreateRandom().ToHexString()` 再 `Change(...)`。

#### 注册入口与选项改名

- **类型**：源码
- **受影响**：`AddCorrelationIdCore` / `AddCorrelationId`；`CorrelationIdOptions`。
- **原来**：`AddCorrelationId(builder.Configuration)`；`HeaderNames`（多个）、`IncludeInResponseHeaders`。

- **迁移**：`AddCorrelationId(builder.Configuration)` 改为 `AddCorrelationId()`；改选项名与配置键；无主机的 `ServiceCollection`

#### 入站关联标识优先于 Activity

- **类型**：行为
- **受影响**：跨服务关联与日志检索。

- **现在**：合法的入站 `X-Correlation-Id`（不超过 64 字符，只含 ASCII 字母、数字、`-`、`_`）优先；没有时取 `Activity.TraceId`，
  再没有则新建。超长值丢弃。显式 `Change()` 仍优先于当前 `Activity`；W3C 追踪上下文使用 `traceparent`。
- **迁移**：上游按此约束生成标识。

#### 日志键与错误响应 `traceId`

- **类型**：行为、源码
- **受影响**：日志检索、`CorrelationIdConstants.TraceIdLogKey` / `InboundTraceIdLogKey`、`RequestTraceId`、错误响应的 `traceId`。

- **迁移**：日志检索改新键；引用两个删除常量的改 `LogKey`；前端只展示 `traceId` 的无需改动。

#### 后台队列工作项接上入队时的链路与关联标识

### 安全与当前用户

#### `ICurrentUser` 成员收敛

- **类型**：源码、行为
- **受影响**：`ICurrentUser` 的调用方与自定义实现。
- **原来**：`GetRoles()`、`IsInRole()`、`FindClaims()`、`GetAllClaims()`、`PhoneNumber`；原 `IsInRole` 同时认 `role` 与 `ClaimTypes.Role`、
  角色名不区分大小写。
- **现在**：`GetRoles`、`GetAllClaims`、`PhoneNumber` 删除；`IsInRole(role)` 保留但只看主体身份、按其 `RoleClaimType` **精确匹配**
  （区分大小写；服务间调用时机器身份上的角色不算，与官方整个主体的语义不同，差异写在 XML 注释）；`FindClaims(claimType)` 跨全部身份读多值 claim。
  新增 `SubjectId`（主体标识原始值）；`CurrentUser` 构造函数新增 `IOptions<ClaimTypeOptions>` 参数。
- **迁移**：删掉的成员经 `ICurrentPrincipalAccessor.Principal.Claims` / `Identities` 读取，或改用官方 `ClaimsPrincipal.IsInRole`、
  授权策略 `RequireRole`、`FindClaim`。**比较方式不同**：调用若落到官方 `ClaimsPrincipal.IsInRole`，编译照样通过而结果可能变化，
  逐处核对角色名大小写与 claim 类型。自定义 `ICurrentUser` 实现补 `IsInRole`、`FindClaims`、`SubjectId`。

#### 主体标识与租户的 claim 类型收归 `ClaimTypeOptions`

- **类型**：源码、行为
- **受影响**：`MultiTenancyOptions.TenantClaimType`、`HubIdentityOptions.UserIdClaimTypes`、`OperationRecordOptions.ActorIdClaimType`（已删除）；
  自行签发主体的代码（登录、令牌、服务间还原）。
- **原来**：claim 类型分散在各组件选项里。
- **现在**：唯一配置处 `ClaimTypeOptions`（Security.Core）：`UserIds`（默认 `sub` → `NameIdentifier`）与 `TenantId`（默认 `tenant_id`），
  经 `services.Configure<ClaimTypeOptions>(...)` 设置；读取规则 `FindUserId` / `ReadTenant` 也在这里。**带 `ValidateOnStart`**：
  选项配错（如某项配成空集合）会在启动时失败；默认配置总是通过。`AddAmbientContext()` 的该验证器按实现去重，重复调用时同一配置错误只报一次。
- **迁移**：配置节里删掉三个旧键，改到 `ClaimTypeOptions`；写 claim 时用同一选项的类型。模板签发令牌时始终写协议要求的 `sub`，
  `UserIds` 不含 `sub` 时按 `UserIds[0]` 同值再写一条（`SubjectClaims.Set`），机器令牌同理；浏览器不持有令牌，前端从
  `/api/v1/auth/me` 的 `tenantId` 取租户（服务端按本选项读 claim），改 `TenantId` 不需要同步前端。

#### 用户标识与租户取自同一个身份；租户 claim 非法一律失败关闭

- **类型**：行为、源码
- **受影响**：多身份主体（服务间还原、合并凭据）；`FindUserId`；`ICurrentUser` 的 `Username`、`Name`、`Email`、`TenantId`；
  `UseTenantSessionRecovery`；`AmbiguousTenantClaimException`。
- **原来**：`FindUserId` 按 claim 类型跨全部身份取第一个；名字可能取到调用方机器令牌上的；非法租户 claim 静默当作宿主，
  开启注册表校验时非 GUID 的 claim 被当成租户名去查；Hub 与后台作业里抛 `InvalidOperationException`。
- **现在**：用户标识与租户取自同一个身份——按顺序第一个带用户标识的身份（主体身份）；同一身份内多条（即使值相同）或非 GUID 为非法；
  其他带用户标识的身份带着与主体身份不同的租户（含主体身份为宿主）为非法，这样同一请求携带的两份用户凭据拼不出"甲的标识 + 乙的租户"；
  不带用户标识的身份（服务间调用只委托租户时还原出的身份）只在主体身份没有租户时提供租户；带用户标识而无租户 claim 的其他身份
  （如服务间调用方的机器身份）不参与判定。新增 `FindSubjectIdentity` 公开主体身份。`Username`、`Name`、`Email` 只在主体身份上读取
  （没有带标识的身份时仍按整个主体）；`FindClaim` 仍跨全部身份。`UseTenantSessionRecovery` 改按 `ReadTenant` 判定，租户声明非法时
  保留原始错误、不再注销。`ICurrentUser.TenantId` 遇非法 claim 抛 `InvalidOperationException`。
  `AmbiguousTenantClaimException` 改名 `InvalidTenantClaimException`，继承 `BusinessException`（错误码 `Tenant:AmbiguousClaim` → `Tenant:InvalidClaim`）。
- **迁移**：宿主覆盖过译文的同步改键；按 `InvalidOperationException` 捕获的代码改按新类型，把非法租户声明当基础设施故障处理的重试/告警逻辑也要跟着调。

#### "是否匿名"统一为任一身份已认证

- **类型**：行为
- **受影响**：`ICurrentUser.IsAuthenticated`、租户解析与多租户中间件、租户会话恢复、租户环境上下文、SignalR 复评、
  `RecordDeniedOperationAsync` / `RecordFailedOperationAsync`；自定义 `ICurrentUser` 实现。
- **原来**：各处只看第一个身份，首身份未认证、后续身份已认证的主体被当成匿名，而授权管线放行了它：租户可被请求头改写、
  失效租户会话不被收回、环境上下文不建立租户、Hub 不复评、操作记录不记或操作人为空。
- **现在**：统一为官方 `DenyAnonymousAuthorizationRequirement` 的口径，新增 `ClaimsPrincipal.HasAuthenticatedIdentity()`（`Leistd.Security.Core`）。
  标识、名字、租户仍只取自带标识的主体身份；服务间调用的机器身份判定仍只看第一个身份（有意）。
- **迁移**：自定义 `ICurrentUser` 实现按同一口径调整。

- **受影响**：`IResourceAuthorizationHandler<T>`、`ResourceAuthorizationContext<T>`、`ResourceAuthorizationDecision`、
  `DefaultResourceAuthorizationService`、`AddResourceAuthorizationHandler`（全部删除）；`IResourceAuthorizationService.IsGrantedAsync` 的调用方。
- **原来**：自定义处理器接口，`context.Allow()` / `Deny()`；EF 入口注册判定服务；`IsGrantedAsync` 带 `CancellationToken`。
- **现在**：规则写为 `AuthorizationHandler<OperationAuthorizationRequirement, TResource>`，注册为 `IAuthorizationHandler`；
  新包 `Leistd.Authorization.Resource.AspNetCore` 提供 `AddResourceAuthorization()`（EF 入口不再注册判定服务）。
  同名包曾在预发布期间因只装一个异常映射类被删除，这次内容完全不同。`IsGrantedAsync` 删除 `CancellationToken` 参数
  （官方授权管线不接收取消令牌）。没有经过认证的当前主体一律拒绝（任一身份已认证即算，与官方一致）；ACL 处理器执行与功能权限相同的
  主体租户规则：租户声明非法、或显式判定的主体不属于当前租户时失败关闭。
- **迁移**：`context.Allow()` → `Succeed(requirement)`，`Deny()` → `Fail()`，操作名取 `requirement.Name`，主体取 `context.User`；
  宿主增加 `AddResourceAuthorization()`，Web 宿主需 `AddSecurity()` 提供当前主体；`IsGrantedAsync` 调用处去掉最后一个实参。

#### 资源 ACL 存储改为 Transient

- **类型**：行为
- **受影响**：`IResourceGrantStore` / `IResourceGrantManager`；宿主预先以 Scoped 登记的 `EfCoreResourceGrantStore<T>`。
- **原来**：Scoped。
- **现在**：Transient（两者无状态，上下文经工作单元共享）；宿主预先以 Scoped 登记时注册即报错。
- **迁移**：删掉宿主自己的 Scoped 登记。

### 多租户

#### 租户管理用例移到新包 `Leistd.MultiTenancy.Management`

- **类型**：源码
- **受影响**：`ITenantManagementService`、`ITenantConnectionManagementService`、`AddTenantManagement()`、管理用 DTO、开通契约与事件；
  调用 `AddMultiTenancyEfCore<T>()` 并提供租户管理界面的宿主。
- **原来**：位于 `Leistd.MultiTenancy.Core`；`AddMultiTenancyEfCore<T>()` 同时注册管理用例；`MultiTenancy.Core` 依赖工作单元与事件总线。
- **现在**：上述类型移入新包——管理用 DTO 在 `Leistd.MultiTenancy.Management.Dtos`，`ITenantProvisioner` / `ITenantActivationGuard` /

#### 创建租户的指定标识重载删除

- **类型**：源码
- **受影响**：`ITenantManager` / `ITenantManagementService` 的 `CreateAsync(..., Guid id)` 重载与自定义 `ITenantManager` 实现。
- **原来**：可指定租户标识。
- **现在**：创建租户一律由组件生成标识。
- **迁移**：删掉调用与自定义实现里的该重载。

#### 租户名须是单个 DNS 标签

- **类型**：行为
- **受影响**：创建与改名租户；`CreateTenantInputDto.Name`。绕过 `ITenantManager` 直接写租户表的代码不受这条校验保护。
- **原来**：只校验非空与长度，能建出 `Invalid Name!` 这类名字，配置 `DomainFormat` 后它们拼不成主机名、经子域名访问不到且不报错。
- **现在**：`TenantConfiguration.NamePattern`：字母、数字与连字符，不以连字符开头或结尾，≤63；创建与改名（名称变化）时校验，
  不合法返回 400 `Tenant:NameInvalid`（占位 `Name`、`Pattern`）。`CreateTenantInputDto` 的 `Name` 长度上限由 64 改为 63；
  `UpdateTenantInputDto` 仍按存储容量 64（`TenantConfiguration.MaxStoredNameLength`），名称原样不变时照常接受。
- **迁移**：**不做数据迁移**：已有的不合规租户照常解析（请求头、查询串与令牌声明不受影响），编辑其他字段也照常保存
  （名称逐字不变就不校验，含 64 个字符与首尾空白的旧名）；只有改名时须符合新规则。启用了子域名解析的部署，可查出名字含空格、下划线、
  点或非 ASCII 字符、以连字符开头或结尾、或恰为 64 个字符的租户，择机改成合规名字并告知其用户。

#### 远端租户连接存储启动时校验控制面地址

- **类型**：行为
- **受影响**：`AddRemoteTenantConnectionStore` 的宿主。
- **原来**：地址缺失或非法时运行期失败。
- **现在**：`Leistd:ServiceClients:{serviceName}:BaseAddress` 缺失或不是绝对地址时启动失败并报出键名。
- **迁移**：补齐配置。注册入口的签名变化见[服务客户端注册入口收敛](#服务客户端注册入口收敛)。

#### 远端路由缓存改用 `HybridCache`

- **类型**：源码、行为
- **受影响**：`TenantRouteResolutionCoordinator`（删除）；`AddRemoteTenantConnectionResolution()`；路由缓存配置。
- **原来**：自建单飞协调器；配置节 `TenantRouting`，`CacheLifetime` 必填。
- **现在**：`AddRemoteTenantConnectionResolution()` 调用 `AddHybridCache()`，只用进程内一级（连接串不进分布式缓存）。
  取消语义随官方：单个等待者取消只影响自己，全部取消时回源取消；失败不缓存。配置节改为 `Leistd:MultiTenancy:Routing`
  （`TenantRouteCacheOptions.SectionName`），`TenantRouteCacheOptions.CacheLifetime` 改为非空 `TimeSpan`，默认 10 分钟，
  仍校验大于 0 且不超过 1 小时。`AddRemoteTenantConnectionResolution()` / `AddLocalTenantConnectionResolution<T>()` 自带多租户核心服务
  （调用 `AddMultiTenancyCore()`，TryAdd，宿主先注册的替换实现照旧保留）；此前单独使用（如只注册持久化的迁移作业）缺 `ICurrentTenant`，
  开发环境在容器构建期失败。
- **迁移**：删掉对协调器的引用；环境变量 `TenantRouting__CacheLifetime` 改为 `Leistd__MultiTenancy__Routing__CacheLifetime`。
  旧键不再读取，留着也不报错，只会让改过的 TTL 静默回到默认 10 分钟——升级时搜索配置文件、部署清单与 compose 文件。
  宿主已显式调用 `AddMultiTenancyCore()` 的无需改动。

#### 有独立库租户时每个宿主都要注册租户连接路由

- **类型**：行为
- **受影响**：有独立库租户的系统中的每个宿主。
- **原来 → 现在**：不注册路由时 `DbContext` 一律沿用宿主连接，独立库租户的数据会静默写进共享库。
- **迁移**：每个宿主都注册路由；多宿主时把路由注册放进共用的组合方法，见多租户组件文档"解析租户连接"。

#### 租户解析与会话

- **类型**：行为、源码
- **受影响**：匿名租户提示头、租户会话自恢复、租户日志作用域、`by-host` 探测。
- **原来 → 现在**：
  - 匿名租户提示头默认改名 `X-Tenant`：`MultiTenancyOptions.HeaderName` 默认 `X-Tenant`（`DefaultHeaderName`），值可为租户 Id 或名称；
    与服务间委托头 `X-Tenant-Id`（只带 GUID、须受信调用方）分开。
  - 租户会话自恢复按主体的租户 claim 判定：改过租户 claim 名的宿主，自恢复现在才会生效（claim 类型见 `ClaimTypeOptions`）。
  - 租户切换自动写入日志作用域：`ICurrentTenant.Change` 同时打开日志作用域 `TenantLogKeys.TenantId`（`leistd.tenantId`，宿主为 `null`）；
    多租户中间件不再单独开作用域。
  - `by-host` 探测跑宿主配置的解析链：此前固定 new 一个 `DomainTenantResolveContributor`，宿主替换或定制域名解析时探测与真实请求答案不一致。
    **答案不再只由主机名决定**：请求若带着会话或租户提示（Cookie、`X-Tenant-Id` 等），答案会随之变化——这与真实请求一致；
    它的设计场景是登录页在未登录、未选租户时调用。
- **迁移**：前端或网关按旧名发租户头的同步改名，或把 `HeaderName` 配回旧值；不要把 `by-host` 当成"纯按域名查租户"的接口。

#### 迁移目标报出失败租户

- **类型**：源码、行为
- **受影响**：`ITenantConnectionConfigurationStore`、`ITenantMigrationTargetProvider`、`ITenantConnectionManagementService` 的实现与调用方；
  `GET {prefix}/migration?name=` 的 HTTP 消费方。
- **原来**：返回连接清单；单个租户失败挡住其他租户；HTTP 返回裸数组。
- **现在**：
  - `ITenantConnectionConfigurationStore.GetListAsync` 返回 `TenantMigrationConnectionListResult(Connections, FailedTenants)`；
  - `ITenantMigrationTargetProvider.GetDedicatedTargetsAsync` 返回 `TenantMigrationTargetSet(Targets, FailedTenants)`；
  - `ITenantConnectionManagementService.GetMigrationListAsync` 返回 `TenantMigrationConnectionListOutputDto`。
  失败项沿用运行时的 `TenantDatabaseFailure` / `TenantDatabaseFailureOutputDto`（租户标识 + 原因，不含连接串）。
  名字解析不出与连接串解不开都归入失败项；控制库查询失败、远端回源失败、取消照常抛出。
  HTTP 线协议从裸数组改为 `{ connections, failedTenants }`，不兼容，没有双协议。
- **迁移**：自行实现这些接口的宿主或测试替身按新签名修改；Identity 与依赖它的 Resource（远端连接存储）、各服务的 DbMigrator 必须一起升级。
  模板 DbMigrator 的对应变化见[DbMigrator 报出失败租户](#dbmigrator-报出失败租户)。

### 设置

#### 设置存储宿主键 `h:` 改为 `host:`

- **类型**：行为（数据迁移）
- **受影响**：`EfCoreSettingStore` 已有的宿主级设置行。
- **原来**：宿主行 `ScopeKey` 为 `h:t`。
- **现在**：`ScopeKey` 与其他按租户隔离的键统一经 `CurrentTenantKeyExtensions.ScopeKey`：宿主行 `host:t`，租户行不变。
  新版本读不到旧键时不报错，宿主级设置静默回落为定义里的默认值。
- **迁移**：**必须在新版本开始服务之前执行**：

  ```sql
  UPDATE <schema>."SettingRecords" SET "ScopeKey" = 'host' || substr("ScopeKey", 2) WHERE "ScopeKey" LIKE 'h:%';
  ```

  按实际表名与数据库方言调整；随 EF 迁移发布时新建一个空迁移，在 `Up` 里 `migrationBuilder.Sql(...)` 执行它，`Down` 反向执行
  `'h' || substr("ScopeKey", 5) WHERE "ScopeKey" LIKE 'host:%'`，由部署时的迁移步骤保证先于新版本生效。

#### `AddHostSettings` 的绑定声明在登记时执行

- **类型**：行为
- **受影响**：`Settings.Hosting` 的 `AddHostSettings` 调用方。
- **原来**：bind 委托在首次解析 Options 时执行；两次相同绑定在解析时抛 already bound。
- **现在**：bind 在 `AddHostSettings` 调用时执行；相同绑定（设置名、有序配置键、兜底值、选项类型）不重复生效；
  同名不同绑定在该次调用即抛 `InvalidOperationException`。
- **迁移**：去掉为避免重复调用的变通；bind 委托不得依赖 `AddHostSettings` 之后才赋值的状态。

### 操作记录

#### 操作人与所属租户的口径

- **类型**：行为（数据迁移）、源码
- **受影响**：操作记录的 `ActorId`、`ActorTenantId`；`OperationRecordVisibilityScope.ForTenantReader`；"本人可见"判定。
- **原来**：操作人标识默认读 `sub`、缺失时回落 `ICurrentUser.Id?.ToString()`；`ActorTenantId` 是操作发生时的上下文租户
  （宿主管理员进入租户操作——模拟登录、代管——时记成该租户）；定义为 `targetIsActor` 的动作在匿名请求里记录时 `ActorId` 为空，
  租户用户看不到自己的登录、注册记录（`Actor` 层只对本人放行）。
- **现在**：操作人标识改读 `ICurrentUser.SubjectId`，一律记按 `ClaimTypeOptions.UserIds` 读到的原始值（只有非 GUID 的 `NameIdentifier` 时
  此前记 `null`、现在记原值；GUID 若非标准 `D` 格式此前被规范化、现在保持原样；只实现 `Id` 而不提供对应 claim 的自定义 `ICurrentUser`
  不再有回落）。`ActorTenantId` 取自主体的租户 claim（匿名请求取请求所在的租户上下文）。匿名自证动作的 `ActorId` 取目标。
  `ForTenantReader` 新增 `actorTenantId` 参数，`Actor` 层要求 `ActorId` 与 `ActorTenantId` 都相同：主体标识只在签发它的那一层内唯一，
  宿主主体在租户里留下的记录不再被租户里同标识的主体认领。`ActorIsTarget` 只在 `ActorId == TargetId` 时成立。
- **迁移**："本人可见"按操作人标识判定，有历史数据时核对新旧标识格式。**已有数据须迁移**，否则此前的自证记录仍不属于任何人：

  ```sql
  UPDATE <schema>."OperationRecords" SET "ActorId" = "TargetId"
  WHERE "ActorId" IS NULL AND "Outcome" = 'Succeeded' AND "Action" IN (<各 targetIsActor 动作码>);
  ```

  模板为 `'auth.login.succeeded'`、`'auth.password.changed'`、`'auth.registered'`；归档表同样处理。
  此前宿主主体在租户里留下的记录 `ActorTenantId` 已记成该租户，无从还原。

#### 失败原因参数改为字典，JSON 由组件序列化

- **类型**：源码
- **受影响**：`OperationFailure.FromCode(string code, string dataJson)` 与 `Create(string, string, string)` 的调用方。漏改是编译错误，不会静默。
- **原来**（0.13.0 早期形态）：

  ```csharp
  OperationFailure.FromCode(code, JsonSerializer.Serialize(new { Limit = limit }));
  ```

- **现在**：第二个入参为 `IReadOnlyDictionary<string, object?>`：

  ```csharp
  OperationFailure.FromCode(code, new Dictionary<string, object?> { ["Limit"] = limit });
  // 已有 BusinessException 时，两个组件经 BCL 字典对接，不必互相引用
  OperationFailure.FromCode(exception.Code, exception.LocalizationData);
  ```

  手拼 JSON 串没有转义，值里出现引号就产出坏 JSON、展示端整行原因渲染不出来。
- **迁移**：按上例改写。值只能是标量（字符串、布尔、数值、日期、`Guid`）；传对象不会被摊开，只会写下类型名——这一列租户管理员直接可读、还会进导出。

#### 组件端点的业务拒绝留痕

- **类型**：行为
- **受影响**：映射了组件端点、需要记录业务拒绝的宿主；同时在应用服务里调 `RecordFailedAsync` 的代码。
- **原来**：只有授权阶段被拒才记；约定"挂了注解的端点，应用服务不要再调 `RecordFailedAsync`"。
- **现在**：新增 `HttpContext.RecordFailedOperationAsync(failure)`（`Leistd.OperationRecords.AspNetCore`），与 `RecordDeniedOperationAsync` 对称：
  授权通过之后被业务规则拒绝时，按端点上的 `[OperationRecordAction]` 补一条失败记录。失败记录按动作码与目标去重（作用域级）：
  同一动作与目标在本次请求里已经记过时跳过，**保留先记的那条，不覆盖也不替换**；同一请求里多条不同动作、或同一动作不同目标的失败照常都记
  （前者如"改口令失败"之后紧跟"账号被锁定"，后者如批量删除里逐个目标失败）。兜底推不出目标时（端点没声明目标路由键、或某段路由值缺失）
  退回只按动作码判，这类端点上同一动作的第二次失败不会被兜底补记。写库失败时不登记，兜底仍会补记。
  上面那条旧约定随之作废。
- **迁移**：在宿主**紧接 `UseAuthorization()`** 的中间件里捕获、调用、原样重抛；不要放进 `IExceptionHandler`（租户作用域已退出，
  租户内的失败会写进宿主层）。**推荐写法：应用服务照常在拒绝处调 `IOperationRecorder.RecordFailedAsync`，中间件只作兜底**（它手里有业务目标名，
  而兜底只拿得到错误码与路由值）。**注解声明的目标（含 `TargetIdPrefix`）要与应用服务记录的目标逐字一致**。要逐条留痕由应用服务按目标逐条记。
  不需要按端点类型把控制器排除在中间件之外，已经这么绕过的项目可以撤掉，回到全量挂中间件。
  记录消息参数时，异常作者只把可公开展示的值放进 `LocalizationData`（`WithData`），排查用的内部信息放日志；基类 `Exception.Data`
  与异常文本不要带进记录。模板中间件见[业务拒绝留痕中间件](#业务拒绝留痕中间件)。

#### 失败原因由后端本地化

- **类型**：行为、源码
- **受影响**：`OperationRecordOutputDto`、导出 CSV、自备失败词条的前端与宿主资源。
- **原来**：只返回 `FailureCode`/`FailureData`，前端按 `operationRecords.failures.<码>` 自备词条。
- **现在**：`OperationRecordOutputDto` 新增 `FailureMessage`，导出新增 `FailureMessage` 列；新增 `LocalizationPlaceholders.Fill`
  （`Leistd.ExceptionHandling.Core`），`Leistd.OperationRecords.Core` 因此直接依赖该包。查询服务用容器里的非泛型 `IStringLocalizer`
  按 `FailureCode` 取文案、用 `FailureData` 填 `{Name}` 占位符，与错误响应同一条词条、同一套填充规则；审计要与接口报错措辞不同时
  （如记录多带了次数、时长），备一条 `{码}:Record`，它优先于码本身（两步各走本地化器的文化回落，审计键在整条回落链上都没有才查码本身，
  因此只在默认语言备了审计键时其他语言也显示它）；没有本地化器或缺词条时为空。`Error:Forbidden` 的中英译文由 `Leistd.OperationRecords.Core` 随包提供。
- **迁移**：自定义 DTO 或前端直接显示 `failureMessage`，缺失时回落到码；前端自备的失败词条可以删掉，改在后端资源里为码备文案
  （键不再把冒号换成下划线）；宿主资源中的同名 `Error:Forbidden` 词条删除。导出 CSV 的仅宿主列因此后移一列，按列序解析导出文件的脚本要调整。

#### 注册入口合并，保留天数启用时必填

- **类型**：源码、二进制、行为
- **受影响**：`AddOperationRecords(services)` 与 `AddOperationRecords(services, configureOptions)`；`OperationRecordRetentionOptions.RetentionDays`。
- **原来**：两个重载；`RetentionDays` 为 `int`（默认 365）。
- **现在**：合并为 `AddOperationRecords(configure?)`；`RetentionDays` 改为 `int?`，不再有默认值，`Enabled=true` 而未配置天数时启动失败，
  报 `{节}:RetentionDays is required when Enabled is true.`。
- **迁移**：以命名参数 `configureOptions:` 调用的改为 `configure:`，已编译的调用方重新编译；启用保留时显式配置天数（模板 `appsettings.json` 已写 365）。

#### 存储拆为读写两侧

- **类型**：源码、行为
- **受影响**：已消费 0.13.0 预发布版操作记录契约的项目（该组件不属于 0.12.0 的既有 API）。
- **原来 → 现在**：

  | 原用法 | 最终用法与迁移 |
  | --- | --- |
  | 自定义存储实现并注册 `IOperationRecordStore` | 改为 `IOperationRecordWriter`；可回读历史时同时实现并注册 `IOperationRecordReader`，再显式注册 `AddOperationRecordQueries()`。EF 适配注册两者及查询；Core 注册不再自动附带查询 |
  | 所有宿主都映射操作历史接口 | 仅有读侧存储时映射 `MapOperationRecords()`；日志写入模式不映射历史接口、不注册归档，缺少查询注册时映射立即报错 |
  | 不需要历史产品，但仍必须记录安全操作 | 引用并注册 `Leistd.OperationRecords.Logging` 的 `AddOperationRecordsLogging()`，与 EF 写入适配互斥；保留动作定义、记录器和安全调用链。必要的 UoW、事件总线及日志类别前置见[组件文档](../../../framework/docs/components/operation-records.md) |

  数据库模式只有在同一业务事务和存储内记录，才提供原子持久化；提交后处理器中的记录另行持久化。日志模式在真实提交后输出成功，
  回滚不输出成功，失败立即输出，仍有提交后进程退出的丢失窗口。采集、保留和访问策略由宿主日志平台负责。
- **迁移**：按表逐行改写。

### 通知

#### 通知持久化按租户分区（数据库迁移）

- **受影响**：0.12.0 已在用的 `Leistd.Notifications.EntityFrameworkCore` 表 `NotificationRecord`。

- **类型**：源码、行为
- **受影响**：前端 `connection.on(...)`；直接使用 `SignalRNotificationChannel` 的宿主；只想用一条 Hub 连接的宿主。

### 服务客户端

#### 服务客户端异常分类与超时

- **类型**：行为、源码
- **受影响**：`ServiceClientException`、`RemoteServiceException` 的捕获代码；`ServiceClientOptions.Timeout`（配置键 `Leistd:ServiceClients:<名称>:Timeout`）。
- **原来**：组件设置 `HttpClient.Timeout`；非 2xx 信封的数字 `code` 被当作业务码；官方字典形 `errors` 被忽略。
- **现在**：`ServiceClientException` 直接继承 `Exception`，`RemoteServiceException` 继承前者；注册任一服务客户端即登记安全的 500/502/503/504 分类：
  本地观测的无效响应、传输不可用、等待超时分别映射为 502、503、504；远端明确返回失败状态默认 502，不依据远端 408/429/503 等状态推断本地响应。
  `Timeout` 已删除，组件不再设置 `HttpClient.Timeout`，它回到 .NET 默认的 100 秒作外层兜底。非 2xx 信封的数字 `code` 是 HTTP 状态，
  业务码从 `errorCode`（或 Problem Details 的字符串 `code`）还原（旧式"非 2xx + 数字业务码"的远端不再得到 `ErrorCode`；2xx 信封的非零 `code`
  仍按业务码处理）。`RemoteServiceException.Errors` 同时还原 Leistd 数组与 `HttpValidationProblemDetails` 字典（键为属性名，每条消息一项，`Code` 为空）。
- **迁移**：宿主可针对已知上游契约覆盖默认映射；超时改由宿主在客户端上叠加弹性管道（如 `AddStandardResilienceHandler()`），
  其超时归类为 `ServiceClientFailureKind.Timeout` 并在 API 边界返回 504；确需改兜底时长时用 `ConfigureHttpClient`，并保持它大于管道的总超时。

#### 服务客户端不再写调用日志

- **类型**：源码、行为
- **受影响**：`ServiceClientLoggingHandler`（改为内部的传输异常统一处理器）、`ServiceClientOptions.LogPayloads` / `MaxPayloadLength` 与 `LoggerCategoryPrefix`（删除）。
- **原来**：组件记录调用摘要与正文。
- **现在**：调用摘要看 `System.Net.Http.HttpClient.<客户端名>` 的官方日志。
- **迁移**：删掉三个选项；要记正文用 `AddExtendedHttpClientLogging`（`Microsoft.Extensions.Http.Diagnostics`，需 `AddRedaction()`），示例见服务客户端文档。

#### 服务客户端注册入口收敛

- **类型**：源码
- **受影响**：`AddServiceClient<TClient, TImplementation, TOptions>`、`AddRefitServiceClient<TApi, TOptions>`、`AddRemoteTenantConnectionStore`。
- **原来**：

  ```csharp
  services.AddRefitServiceClient<IOrdersApi, OrdersClientOptions>("Orders", configuration);
  services.AddRefitServiceClient<IOrdersApi, OrdersClientOptions>("Orders", o => o.BaseAddress = "http://orders");
  services.AddRemoteTenantConnectionStore("Identity", configuration);
  ```

- **现在**：不再接收 `IConfiguration`，统一为 `(serviceName, configure?, configSectionPath?)`，Refit 末尾仍有 `settings?`。
  先绑定 `configSectionPath`（默认 `Leistd:ServiceClients:{serviceName}`），再应用委托：

  ```csharp
  services.AddRefitServiceClient<IOrdersApi, OrdersClientOptions>("Orders");
  services.AddRefitServiceClient<IOrdersApi, OrdersClientOptions>("Orders", o => o.BaseAddress = "http://orders");
  services.AddRemoteTenantConnectionStore("Identity");
  ```

  重复调用的契约写进了 XML：同一服务名的相同登记重复调用不再叠加客户端与处理器，只追加委托并返回同一命名客户端的构建器；
  同一服务名换用其他客户端接口、实现、选项类型或配置节，或一个选项类型用于两个服务名时，注册即抛 `InvalidOperationException`。
  远端连接存储是唯一权威来源：相同参数幂等，换用另一服务名或配置节抛出。`AddServiceClientPipeline<TOptions>` 按命名客户端只装配一次，
  同一客户端换另一选项类型时抛 `InvalidOperationException`（此前静默叠两层管道）。认证入口同样幂等：`AddServiceAuthentication` 以相同配置节
  重复调用不再重复登记验证器与官方客户端处理器（此前每条失败会报两遍），换用另一配置节抛出；`AddClientCredentials` / `AddTokenExchange`
  对同一客户端以同一方式、同一配置节重复调用不再抛出，换用另一方式或配置节仍然抛出。
- **迁移**：调用处去掉 `configuration` 实参；无主机的 `ServiceCollection`（测试、工具）须自行注册 `IConfiguration`。

#### 服务间用户委托改用官方 Token Exchange

- **类型**：源码、行为
- **受影响**：服务间用户委托与机器回源的全部调用方与配置。服务间用户委托改用 OpenIddict 的 Token Exchange；机器回源改用 OpenIddict.Client。
  源码不保留旧委托头协议。只签发 access token 时创建的是令牌记录，不自动创建临时授权记录。
- **原来 → 现在**：

  | 原调用／配置 | 影响与替代方式 |
  | --- | --- |
  | `AddClientCredentials(configuration)` 与旧凭据 Options | 先全局 `AddServiceAuthentication()`，再在命名客户端调用 `AddClientCredentials()`；`Authority/ClientId/ClientSecret` 绑定 `Leistd:ServiceAuth`，机器 `Scope` 绑定 `Leistd:ServiceClients:{Name}`；`ExpirationBuffer` 属性及配置删除，机器缓存固定提前 60 秒失效，用户交换固定提前 10 秒失效 |
  | 生成 Client 包自动安装机器认证 | 注册返回的 builder 不再自动认证。未显式组合的宿主访问受保护端点会稳定返回 401；使用 `services.AddMyProjectClient(configuration).AddClientCredentials()`，或按用户调用选择 `.AddTokenExchange()`（Client 项目注册入口的签名变化见[生成的 Client 项目](#生成的-client-项目注册入口)） |
  | 用户／租户委托头与恢复管道 | Resource 注册 `AddUserAccessTokenAccessor(实际 Bearer 验证方案)`，用户客户端 `AddTokenExchange()`；目标 `Audience/Scope` 绑定 `Leistd:ServiceClients:{Name}:TokenExchange`，身份与租户来自已验证 JWT |
  | 机器调用自动转发 `ICurrentTenant` | 不再转发租户；按租户执行的后台作业若仍只调用 `ICurrentTenant.Change()`，下游可能在宿主上下文执行且不报错。租户必须作为显式参数，例如租户回源使用的路由 tenant ID；下游机器端点自行验证调用权限、租户有效性并建立业务租户上下文 |
  | `Leistd:ServiceAuth:Scope/ExpirationBuffer/TokenEndpoint` 与 `ResolveTokenEndpoint` | 旧全局 scope/buffer 不再读取，scope 改为命名客户端配置，buffer 固定为机器 60 秒／交换 10 秒；手工端点删除，官方客户端按 `Authority` 发现端点并协商认证 |
  | `Leistd:ServiceClients:{Name}:UserContext` 与 `Leistd:ServiceUserContext` | 整个配置节删除；不检测旧配置，也不保留旧协议兼容路径 |
  | Cookie／后台用户上下文 | 单独的 Cookie 或 ambient 主体不提供 Token Exchange 证明；框架默认适配器只读 Bearer 验证方案保存的访问令牌。模板带浏览器会话的 Resource 使用自己的读取器，从已认证服务端票据取得保存的访问令牌。普通后台调用选择机器认证，不能仅设置 ambient 用户来委托 |
  | 收到下游 401 后自动重放 | 仅清本地令牌缓存，下次独立调用重新取令牌；调用方按业务幂等性决定是否重试，分布式删除失败不能覆盖原 401，取消仍传播 |

  已删除或收敛的公共契约（供搜索；不要仅删配置而保留调用）：

  - OAuth：`IServiceTokenProvider`（含 `GetAccessTokenAsync/Invalidate`）、`ClientCredentialsTokenProvider`、`DependencyInjection.ServiceAuthSectionName`；
    旧 `ClientCredentialsOptions.Authority/ClientId/ClientSecret/TokenEndpoint/ResolveTokenEndpoint/ExpirationBuffer`，以及接收 `IConfiguration`
    的旧 `AddClientCredentials` 重载。`ClientCredentialsDelegatingHandler` 从 public 改为 internal，不再直接构造，改用命名客户端的 `AddClientCredentials()`。
  - Core：`ServiceClientHeaders`（`UserId/Username/TenantId`，即 `X-User-Id/X-Username/X-Tenant-Id`）、`ServiceClientScopes.Delegation`（`svc.delegate`）、
    `UserContextForwardingOptions`（含预发布期间新增的 `UserIdHeader`、`UsernameHeader`、`TenantIdHeader`）、`ServiceClientOptions.UserContext`、
    `UserContextDelegatingHandler<TOptions>`、`TenantContextDelegatingHandler<TOptions>`。
  - AspNetCore：`ServiceUserContextOptions`、`ServiceUserContextClaimsTransformation`、`ServiceUserContextMiddleware`、`AddServiceUserContext`、
    `UseServiceUserContext`；内部 `ServiceUserContext` 与 `CompositeClaimsTransformation` 一并删除，相关身份恢复与转换组合不再注册
    （预发布期间"被调方还原用户标识写 `ClaimTypeOptions.UserIds[0]`、租户写 `ClaimTypeOptions.TenantId`"的还原路径随之不存在）。
  - 配置属性：旧 `UserContext.Enabled/ForwardUsername/UserIdHeader/UsernameHeader/ClaimHeaderMap/ForwardTenantId/TenantIdHeader`；
    旧 `Leistd:ServiceUserContext` 下的 `Enabled/UserIdHeader/UsernameHeader/TenantIdHeader/HeaderClaimMap/RemoveUntrustedHeaders/RequiredScope/AuthenticationType`；
    模板派生变量 `ServiceUserContextEnabled` 不再存在。

  交换令牌最多 120 秒，最终 `exp` 不超过来源（源令牌寿命短于 120 秒时，交换令牌随源令牌到期）；角色与超管信息留给下游本地授权，
  用户名、邮箱、显示名由 Identity 回查权威资料。Bearer 缓存只在进程内，按官方客户端返回的到期时间提前失效，机器 60 秒、用户交换 10 秒。
  组件不设置宿主日志过滤；官方客户端脱敏协议中的令牌与密钥字段。
- **迁移**：按表逐行改写。工作负载 client ID 要与来源 API 受众一致（例如 `orders-machine` → `orders-api`）；改名后机器主体变为
  `client:orders-api`，按 client ID／主体写的机器策略、审计筛选与密钥配置均要更新。旧 client ID 与密钥只有在旧应用仍保留、相应
  grant/scope 仍获授权且目标接受机器身份时才能继续取机器令牌；删除／改名应用后不能假定旧密钥可用于新 client ID，须为新应用配置其有效密钥。
  保留旧应用也无法恢复已删除的 `svc.delegate`，不保证旧用户委托链路可用。部署顺序与中断窗口见[混合版本的中断窗口](#token-exchange-的混合版本中断窗口)。
  `AddServiceAuthentication` 的 `DisableTokenStorage` 是官方客户端全局选项，同宿主的 OpenIddict.Client 交互式登录也受影响：
  需要 state 存储的宿主在所有组件注册之后调用 `services.Configure<OpenIddict.Client.OpenIddictClientOptions>(options => options.DisableTokenStorage = false)`，
  并按官方方案接入 Core、令牌存储、证书与交互式宿主集成；覆写须晚于 `AddServiceAuthentication`，其后再次调用组件注册会关闭存储，无需强制分开部署或增加框架开关。

#### OAuth 客户端接管令牌响应解析

- **类型**：行为
- **受影响**：`Leistd.ServiceClient.OAuth` 的日志与错误处理；OpenIddict 依赖版本。
- **原来**：失败时响应原文（含 access_token）可能写进 Error 日志。
- **现在**：OpenIddict 升到 7.7.1（7.7.0 在请求缓存下还原 hint 主体有缺陷），框架 Client 2 个包同步升级。
  `Leistd.ServiceClient.OAuth` 在官方处理器之前接管发现文档、JWKS、令牌响应的解析与状态校验：调用方取消照常抛出，
  失败只记状态、类型与长度，不再把响应原文写进 Error 日志；错误码与官方一致（上游 openiddict/openiddict-core#2558，8.0 提供官方选项后删除）。
- **迁移**：宿主直接引用 OpenIddict 包的，升到同一版本。

### 怎么生成升级迁移

- **类型**：行为（数据库模型）
- **受影响**：使用[权限](#权限持久化按租户分区数据库迁移)与[通知](#通知持久化按租户分区数据库迁移)持久化表的宿主。本节只覆盖 0.12.0 就已经在用的表；
  0.13.0 新增的组件家族各自带表（操作记录表也有一条同样的 `CreationTime` 索引，但它在 0.12.0 的库里根本不存在），属于"接一个新组件"，
  按该组件文档的第一节接入。
- **迁移**：升级包引用后 `dotnet ef migrations add UpgradeTo0130`，**让 EF 按模型差异自己算**，不要照着上表手写 DDL——表上还有审计列、
  长度与必填这类由配置决定的细节，手写会漏。生成后核对 `Up()` 里是否出现上述列与索引；一条都没有说明包还没升到位。
  已有数据的 `TenantId` 全部为 `NULL`，即"这些授予与通知属于宿主"，这对单租户部署就是正确语义；要把既有数据划给某个租户得自己写数据迁移，框架不猜。

## 模板（生成项目）

模板参数决定新生成的工程资产，不会自动迁移已经生成的业务项目，也不能通过关闭开关删除已有生产数据。
已派生的项目按下列条目同步模板改动；框架部分的条目同样适用于生成项目引用的组件家族。
"Identity"指带本地身份与授权服务器的形态，"Resource"指只验证令牌的资源服务形态。

### 生成参数与能力裁剪

#### 能力参数与派生条件

- **类型**：源码
- **受影响**：按 0.12.0 参数生成的项目；通知与业务实时、OIDC 相关的条件块。
- **原来**：通知开关同时开启业务实时；前端与后端令牌验证相关的条件写作 `!LocalIdentity`。
- **现在**：公开参数、默认值及角色生效范围见[根 README 参数表](../../../README.md#用模板创建项目)，有效能力表达式见
  [模板开发规范](../../template/development-guide.md#32-有效能力集中派生)。`IncludeNotifications` 与 `IncludeRealTime` 分别控制，后者默认关闭：
  只开通知使用通知 Hub；只开业务实时使用实时 Hub；都开时 `AddNotificationsSignalR<RealTimeHub>()` + `MapRealTimeHub()`，有前端时共用一条
  `/hubs/realtime` 连接；都关闭时不映射 Hub。前端全部与后端令牌验证相关的 `!LocalIdentity` 改为 `RemoteTokenAuth`，`!LocalIdentity`
  只表示没有本地用户表（当前两者取值相同，生成结果不变）。模拟登录要求本地身份、多租户和可查询历史同时存在；历史关闭时移除模拟登录，
  普通租户管理仍可保留。
- **迁移**：需要业务订阅和事件发布的项目显式开启 `IncludeRealTime`；按业务需要分别设置两个开关。

### 认证、会话与 OAuth

#### 会话 Cookie 的身份按 `role` 设 RoleClaimType

- **类型**：行为
- **受影响**：`SessionSignInService` 构造身份处。
- **原来**：默认 RoleClaimType 是 `ClaimTypes.Role` 而角色写成 `role`，官方 `IsInRole` / `RequireRole` 静默判否。
- **现在**：`new ClaimsIdentity(scheme, ClaimTypes.Name, "role")`。
- **迁移**：按此修改；旧 Cookie 在重新登录后生效。

#### 令牌端点与 userinfo 在令牌主体的租户内加载用户

- **类型**：源码、行为
- **受影响**：`IAuthPrincipalFactory`；租户用户的授权码换令牌、刷新与 userinfo。
- **原来**：这两个端点的请求解析出的是宿主，**租户用户走不通**。
- **现在**：`IAuthPrincipalFactory` 新增 `CreateFromTokenAsync(tokenPrincipal, scopes)`，`CreateUserInfoAsync` 改为只收令牌主体。
- **迁移**：按模板同步。

#### Resource 默认授权策略要求自然人

- **类型**：行为
- **受影响**：用纯机器令牌调用默认策略端点的派生项目。
- **原来 → 现在**：响应从 200 变为 403。
- **迁移**：给纯机器端点显式声明机器策略，不放宽默认自然人策略。

#### 租户相关的缓存与状态键按租户隔离

- **类型**：行为
- **受影响**：登录失败计数、邮箱验证码限流与挑战、外部登录 state。
- **原来**：键不分租户。
- **现在**：统一经 `ScopeKey`；外部登录 state 绑定发起时的租户，回调时租户不一致即拒绝。
- **迁移**：按模板同步。

#### Identity 为下游 API 签发令牌（`OAuth:ApiResources`）

- **类型**：源码、行为
- **受影响**：Identity 的 scope 目录、已有客户端、服务间调用方配置、库里单独登记的自定义 scope。
- **原来**：访问令牌的受众一律是本服务的 `OAuth:Resource`；`OAuth:ApiResources` 为字符串数组。
- **现在**：`OAuth:ApiResources` 列出由本服务签发令牌的下游 API，改为对象，例如
  `{ "Name": "https://api.example/orders", "Scope": "orders.read", "OwnerClientId": "orders-worker" }`，`Scope`/`OwnerClientId` 默认 `Name`，
  重复资源或 scope 启动失败。scope 目录 `OAuthScopes` 成为服务端登记、scope 表、开放应用权限校验与令牌受众的唯一来源；
  访问令牌的受众由授予的 scope 推出，本服务 API 只接受受众是自己的令牌。发起方按所有资源集合验证，允许客户端拥有多个资源；
  不再要求 client_id、scope、audience 字符串相等，授权码 presenter 与资源所有者可不同。委托 scope 仅限机器客户端。
  开放应用新增 `GET /api/v1/open-applications/scopes`，编辑界面的 scope 选项取自它。**启动时按目录对账 scope 表：新建、更新，
  并删除目录之外的全部 scope**（不只是曾由 `ApiResources` 登记的）。删除登记不撤销已签发的访问令牌，它们照常用到过期。
- **迁移**：**已有客户端要调用本服务 API，须补授 `scp:<OAuth:Resource>` 并在取令牌时申请它**；服务间调用方的
  `Leistd:ServiceClients:<服务>:Scope` 写目标 API 的 scope；库里单独登记过的自定义 scope，升级前须改由目录提供（`OAuth:ApiResources` 或 `OAuthScopes`）；
  字符串数组改为对象。

#### Resource 的受众与会话时长配置

- **类型**：源码
- **受影响**：Resource 的 `Authentication:Audience`；`OAuth:CookieExpireDays`；compose 的 `RESOURCE_AUDIENCE`。
- **原来**：受众需经 `RESOURCE_AUDIENCE` 提供；会话时长 `OAuth:CookieExpireDays`，不带授权服务器的形态写死 7 天。
- **现在**：`Authentication:Audience` 默认 `companyname-projectname-api`，与前端申请的 scope 同名；compose 不再要求 `RESOURCE_AUDIENCE`。
  会话时长改为 `SessionCookie:ExpireDays`，各形态都可配。`OAuth` 节只在带授权服务器的形态生成，`Authentication` 节只在 Resource 形态生成。
- **迁移**：在身份服务的 `OAuth:ApiResources` 登记该受众；把 `OAuth:CookieExpireDays` 改为 `SessionCookie:ExpireDays`。

#### 浏览器认证改由后端官方处理器承担

- **类型**：源码、行为
- **受影响**：模板前端的 OIDC 客户端、Resource 浏览器登录、Identity 的客户端登记、会话票据存储。完整当前契约见
  [模板浏览器认证维护规则](../../template/browser-authentication.md)。
- **原来**：自带前端充当 OAuth public client（angular-auth-oidc-client、`environment.oidc`、`/auth/callback` 组件、令牌拦截、SignalR token 注入
  与 Hub query 令牌转换）。
- **现在**：上述前端部分全部移除；带前端的 Resource 整页导航至 `/api/v1/auth/login`，回调与票据由后端处理，前端经 `/api/v1/auth/me` 还原用户；
  纯 API 形态不生成登录导航或浏览器会话，使用 Bearer，不包含浏览器客户端配置与回调。开发代理与同源 Angular 托管保留；第三方 public-client
  授权码能力仍可单独登记。带浏览器会话的 Resource 新增 `Authentication:ClientId/ClientSecret` 必填后端配置（缺失时启动报出键名）；
  登录/退出回调分别 `/api/v1/auth/signin`、`/api/v1/auth/signout`；前端 GET login、GET me、整页 POST logout。
  `SaveTokens` 必须配 `ITicketStore`：所有会话 Cookie 只携引用及版本，完整票据加密留服务器；删除票据立即拒绝旧 Cookie，显式再次登录使旧引用版本失效，
  旧在飞请求的退出或刷新失败仅删除同一引用版本。应用 `SessionCookie:SameSite` 不覆盖官方 correlation/nonce 的 None/Secure Always。
  模板未启用 antiforgery（退出确认表单除外）；默认写请求校验 Origin；浏览器页面与所属 API 必须同源，分进程须经部署代理统一外部源。
  Resource 的 `GET /api/v1/auth/me` 改为返回 `CurrentResourceUserOutputDto`，并删除 `isActive`/`creationTime` 字段。
- **迁移**：读取 `me` 的 `isActive`/`creationTime` 的前端删除这些读取；Identity 为 Resource 登记 web/confidential、授权码、PKCE、refresh token、`offline_access` 和本 API scope 的客户端；
  Resource 配置 `ClientId/ClientSecret`；部署共享缓存与 Data Protection 密钥；前端删除 OIDC 库与相关代码。

#### 会话 Cookie 前缀与跨源写请求

- **类型**：行为、源码（部署）
- **受影响**：三种形态的会话 Cookie；按 Cookie 名转发或剥离的部署代理；依赖同站其他子域无 Origin 提交的前端。
- **原来**：Cookie 名 `<项目名>.Auth`；无 Origin 的跨站写请求放行。
- **现在**：非 Development 环境的会话 Cookie 名改为 `__Host-Http-<项目名>.Auth`，显式 `Path=/`、不带 Domain、Secure=Always；
  Development 保持 `<项目名>.Auth` 与 SameAsRequest。`/api` 下不带 Authorization 头的写请求如果没有 Origin，`Sec-Fetch-Site` 为
  `cross-site` 或 `same-site` 时返回 403；非浏览器调用不受影响。
- **迁移**：升级后所有已登录用户须重新登录；旧缓存票据不会因改名而撤销，旧版本实例在票据过期前仍会接受旧 Cookie，因此滚动部署须一次切完，
  不要让新旧版本同时对外服务。部署代理同步改名；对外源必须是 HTTPS，且不能通过把站点挂在子路径下来改 Path。
  依赖同站子域无 Origin 提交的前端改为同源。

#### 会话绑定、请求缓存与依赖方退出

- **类型**：源码、行为
- **受影响**：开放应用管理 API 与登记；Identity 的授权与退出端点；Resource 的登录挑战与退出；第三方依赖方。
- **原来 → 现在**：
  - **OpenIddict 升到 7.7.1**：模板 4 个包同步升级（7.7.0 在请求缓存下还原 hint 主体有缺陷；框架侧见[OAuth 客户端接管令牌响应解析](#oauth-客户端接管令牌响应解析)）。
  - **开放应用新增必填 `sessionBound`**：创建、更新缺值或为 null 返回 400。已有登记读作未设置（按不绑定处理）。开启后，开启前签发的刷新令牌
    换取时返回 `invalid_grant`，客户端重新授权一次；Identity 会话退出、撤销或空闲到期后，绑定客户端的刷新随之失败，依赖方会话在访问令牌到期时收敛。
  - **授权与退出请求缓存**：`/connect/authorize`、`/connect/logout` 的首个请求先存为 request token（控制库令牌表）再以 `request_uri` 重定向回同一端点；
    控制器只会看到缓存后的请求。重新认证回跳由"删除 `prompt`/`max_age` 参数"改为受保护证明。部署文档原先"第三方顶层 POST 进入授权或退出端点
    需评估 `SameSite=None`"的说法作废：请求缓存后以顶层 GET 重入，Lax 即可。
  - **Resource 改用官方 FormPost 并保留 `id_token_hint`**：登录挑战与退出都返回自动提交的表单而不是 302；`ResourceAuthController.Logout`
    先单独退出本地 Cookie（不带回跳地址），再发起 OIDC 退出。
  - **Identity 退出可能要求确认**：hint 的会话标识与当前会话一致时直接退出；没有 hint 或属于其他会话时，转到新增的 `/auth/logout-confirm`
    由用户确认（RP-Initiated Logout 1.0 §2）。新增 `GET /api/v1/auth/logout-confirmation` 与官方 antiforgery 注册（Cookie 在部署环境带 `__Host-` 前缀），
    只用于这张确认表单；`/api` 写请求的跨源防护仍是 Origin 校验。
  - Cookie `auth_time` 为真实认证时刻，续期不改变它；`prompt=none` 无会话返回 `login_required`，`prompt=login/max_age` 引导重新认证并保留原会话，
    凭据成功后替换会话。
- **迁移**：按模板把 OpenIddict 包升到 7.7.1；调用管理 API 的脚本与集成补上 `sessionBound`；升级后逐个明确选择：Resource 的浏览器登录（BFF）客户端开启，桌面端、原生等离线续期客户端关闭；
  多实例修改登记后滚动重启 Identity（OpenIddict 应用缓存只在本进程失效）。在控制器里读原始查询串或表单改写协议参数的，改为读
  `GetOpenIddictServerRequest()`。多实例 Identity 要共享控制库、令牌证书、Data Protection 密钥环与应用名，以及缓存与锁。
  依赖 302 的反向代理规则或测试改为读取表单；宿主若加内容安全策略，须放行表单的内联提交脚本。不带 hint 的第三方依赖方会看到确认页。
  现存 Cookie 缺 `auth_time` 时，带 `max_age` 的请求要求重新登录。

#### 令牌证书集合与签名公钥轮换

- **类型**：源码
- **受影响**：Identity 的证书配置；Resource 的签名公钥刷新；承载资源服务宿主的测试或工具进程。
- **原来**：`OAuth:SigningCertificatePath/Password`、`OAuth:EncryptionCertificatePath/Password`；验证的 HTTP 抓取超时为 OpenIddict 默认 1 分钟。
- **现在**：`OAuth:SigningCertificates` 与 `OAuth:EncryptionCertificates`，每项 `Path`、`Password`，各至少一项；环境变量写成
  `OAuth__SigningCertificates__0__Path` 等（Compose 文件已改）。旧键不再读取，未迁移时启动失败并指出新键名；任何一项缺路径、无法加载或没有
  RSA 私钥，启动失败并给出带下标的键名。Resource 遇到未知 kid 先刷新再验：新增
  `template/backend/src/CompanyName.ProjectName.Api/Auth/SigningKeyRefresh.cs`（OpenIddict 验证处理器与配置管理器限频），抓取超时改为 10 秒；
  Api 与集成测试项目新增 `RuntimeHostConfigurationOption`：`Switch.Microsoft.IdentityModel.UpdateConfigAsBlocking=true`，只在资源服务宿主设置。
- **迁移**：配置改为集合；轮换按部署文档"令牌证书轮换"的顺序：发布新公钥 → 确认各资源服务已取得 → 新证书生效后重启切换签发 →
  旧的签名与加密证书都保留到授权码、刷新令牌与 request token 全部过期（这些令牌既签名又加密），旧签名证书还要覆盖依赖方保存的 id_token
  不再用作退出 hint。派生项目若另有自己的测试或工具进程承载资源服务宿主，也要设置这一开关，否则刷新只在后台进行、当次请求仍失败。

#### 访问令牌寿命可配置

- **类型**：行为
- **受影响**：Identity 的 `Program.cs` 与配置。
- **原来**：写死 10 分钟。
- **现在**：新增 `OAuth:AccessTokenLifetime`（默认 `00:10:00`），不配置的项目行为不变。它决定撤销、停用与会话退出传到依赖方的最长时延，
  代价是续期频率（取舍见部署文档"生产边界"）。校验（所有环境一致，组合期与启动期复用 `OAuthOptionsValidator`，在开发证书分支之前执行）：
  必须是整秒且长于 1 分钟——资源服务的浏览器会话在令牌剩余 1 分钟时续期，令牌的 `exp`/`iat` 以秒计。两端共用的提前刷新值移到
  `template/backend/src/CompanyName.ProjectName.Domain/Shared/Security/AccessTokenRenewal.cs`。
- **迁移**：按模板同步 `Program.cs`；自定义寿命须满足校验。

#### Token Exchange 的混合版本中断窗口

- **类型**：行为（部署）
- **受影响**：Identity 与各调用方、下游服务的升级顺序；存量开放应用的同意类型。
- **原来**：服务间用户委托使用 `svc.delegate` scope 与委托头。
- **现在**：**混合版本存在中断窗口，不能承诺无中断滚动升级。** 新 Identity 的 `SystemInitializer` 在初始化时立即删除目录中已不存在的
  `svc.delegate` scope，官方 scope 注册也不再包含它。因此 Identity 首先升级后，旧调用方在冷缓存或缓存过期时申请包含该 scope 的令牌即可失败
  （`invalid_scope`）；已缓存的旧令牌也不能使新下游恢复用户身份，访问自然人端点返回 403。`ConsentType` DTO、前端选项与错误码删除，
  服务端固定 implicit；没有同意页与永久授权的第三方场景不支持。
- **迁移**：部署顺序可按 Identity → 调用方 → 下游安排，但不能将最后"清理旧权限"理解为延后删除 scope。不接受此窗口的部署须同步切换相关服务，
  或在部署层将流量切到版本一致的新服务组；代码不增加兼容路径。框架侧的替代方式见[服务间用户委托](#服务间用户委托改用官方-token-exchange)。
  存量应用升级前将其同意类型归一为 implicit：

  ```sql
  UPDATE "<schema>"."OpenIddictApplications" SET "ConsentType"='implicit' WHERE "ConsentType" IS DISTINCT FROM 'implicit';
  ```

#### Resource 会话主体不再被默认 ClaimActions 删声明

- **类型**：行为
- **受影响**：Resource 浏览器会话；按 `acr`、`aud`、`azp`、`iss`、`iat`、`nbf`、`exp`、`nonce` 等声明做判断的派生项目（如以 `acr` 判定近期多因素认证）。
- **原来**：登录时这些声明被删掉，首次续期后又出现，判断结果随会话是否续期过而变。原因是会话主体由 `ResourceSessionRefresher.ValidateAccessTokenAsync`
  按访问令牌构建，登录（`OnTokenValidated`）与续期同源，但官方 `OpenIdConnectHandler` 在 `OnTokenValidated` 之后还会用空载荷对换上的主体执行
  `OpenIdConnectOptions.ClaimActions`，其默认的 `DeleteClaim` 按类型直接删除；续期由模板自行实现，不经过这一步。
- **现在**：Resource 的 `AddOpenIdConnect` 中 `options.ClaimActions.Clear()`，会话主体只由上述构建函数决定；不影响签名、issuer、受众、nonce、PKCE 等协议校验。
  会话主体来自访问令牌，id_token 声明不进会话；`MaxAge`/`Prompt` 只要求重新验证身份，不是多因素或升级认证。新增集成测试断言登录后保留访问令牌的
  `acr`、`aud`，且首次续期前后声明类型一致、不混入 id_token 的声明。
- **迁移**：照此加一行；已自行 `ClaimActions.Clear()` 的保持即可。已存入服务端的会话票据不会立即补回声明，下次续期或重新登录后才按新规则构建；
  无需清空票据库或强制退出。会话里多出的这些声明若参与派生项目的声明判定，请据此复核。

#### 撤销传播窗口（文档）

- **类型**：行为（文档更正）
- **受影响**：依赖"停用即刻生效"的运维与安全假设。
- **原来**：未写明。
- **现在**：停用或删除账号、停用或删除租户：在身份服务立即生效，在只验签的资源服务要等已签发的 Access Token 过期（模板为 10 分钟），之后也刷新不到新令牌。
  撤销会话不撤销 OAuth 令牌：刷新令牌默认滑动续期，持续刷新的客户端对资源服务的访问会一直延续，调短 Access Token 有效期也无济于事。
  内省只能让已撤销的令牌即时失效。见多租户组件文档"注意事项"与模板部署文档。
- **迁移**：按此核对安全假设；需要即时失效的资源服务改用内省。

### 外部登录

#### 外部登录按邮箱关联改为两边都已验证

- **类型**：行为、源码
- **受影响**：外部登录的账号关联与新建；自定义提供商实现。
- **原来**：外部账号的邮箱与本地账号相同就直接关联，任何人在提供商那里填上别人的邮箱即可接管对方账号。
- **现在**：要求提供商确认邮箱已验证（`ExternalUserInfo.EmailVerified`；Google 取 UserInfo v3 的 `email_verified`，GitHub 取 `/user/emails` 的主邮箱）
  **且**本地账号邮箱已确认；不满足而邮箱已被占用时返回 409 `ExternalAuth:AccountExistsSignInToLink`，回调页显示服务端原因，用户先登录原账号
  再在账号设置里绑定。外部登录新建账号时只采用已验证的邮箱，并记为已确认；未验证的邮箱改用占位地址，只留在外部连接上。
  按已验证邮箱关联时关闭软删除过滤，且**被删用户不参与自动关联**：新增错误码 `ExternalAuth:EmailOwnedByDeletedAccount`（映射 409，中英文词条各一条）。
- **迁移**：自定义提供商按其 API 填 `EmailVerified`，不填即按未验证处理；前端若按错误码分支，把新码加进处理。**已部署的派生项目**：升级前按旧规则
  自动关联产生的绑定仍然有效，系统分不清哪些是被利用过的；用户表只记邮箱是否已确认、不记确认时间，仅凭用户与绑定两张表还原不了当时的验证状态，
  保留了足够的邮箱确认与绑定操作记录时，可以用它们辅助排查。

#### 外部登录改用官方远程处理器

- **类型**：源码、行为
- **受影响**：`IOAuthProvider`/`OAuthTokenInfo`、`GetExternalLoginUrlAsync` 与 code/state DTO（删除）；`ExternalLoginConnection` 的令牌列；
  外部登录与绑定的 HTTP 契约；提供商后台的回调登记；GitHub 定制；Google 账号连续性。
- **原来**：前端拿 code/state 调后端完成登录；回调页 `/auth/external-callback?provider=github`（GitHub 连查询串一起比对登记值，极易配错，
  `template/deploy/docker-compose.yml` 的示例还误指向 API 的 POST 端点）；GitHub 用 `AddOAuth`；Google 取 `id`/`verified_email`；外部连接保存访问与刷新令牌。
- **现在**：GET challenge → 官方 `/api/v1/external-auth/{provider}/signin` → POST complete；绑定使用受保护的 GET link/challenge → POST link/complete，
  不再接收前端 code/state。登录与绑定意图受保护，complete 保留一次消费，失败后重新 challenge；第二步凭据只走 JSON/导航状态；
  站内 returnUrl 贯穿受保护票据与第二步验证。提供商 scheme 使用 `AuthenticationSchemeNames.ExternalProviderPrefix + provider` 登记官方远程处理器，
  目录不接受普通 Cookie/Bearer/策略 scheme；`AuthenticationSchemeNames` 移至 `Application.Shared` 命名空间。保留规范化 `ExternalUserInfo` 和业务账号政策。
  `ExternalLoginConnection` 删除 `AccessToken`/`RefreshToken`/`ExpiresAt`、`UpdateTokens`，基线迁移同步删列。GitHub 改用
  `AspNet.Security.OAuth.GitHub` 的 `AddGitHub`，处理器自带的邮箱补取已关闭（`UserEmailsEndpoint = string.Empty`，它只返回地址、不返回 verified，
  且失败会中断登录），主邮箱是否已验证仍由模板在 `OnCreatingTicket` 中查询，查询失败时降级为不按邮箱关联。Google UserInfo 改用官方 v3 的
  `sub`/`email_verified`。新增匿名 `GET /api/v1/external-auth/providers`，登录页据此渲染入口，未配置的提供商不再显示按钮。提供商回调的取消
  （`error=access_denied`，由官方 `OnAccessDenied` 处理）与协议失败不再以 400 问题详情呈现在整页导航上，而是 302 到
  `/auth/external-callback/{provider}?intent=…&error=cancelled|failed`，由前端显示原因与返回入口。
- **迁移**：提供商后台重新登记完整 HTTPS signin 回调 `https://<站点对外地址>/api/v1/external-auth/{github,google}/signin`
  （回调路径由处理器固定，配置里的 `ExternalAuth:{Provider}:RedirectUri` 不再读取，删除即可；预发布期间改成的
  `/auth/external-callback/{provider}` 只是前端的结果页，不再作为提供商回调）；
  `Configure<OAuthOptions>(…"github", …)` 改为 `Configure<GitHubAuthenticationOptions>`（命名选项按类型区分，旧写法会静默不生效）；
  自建提供商的 `OnRemoteFailure`/`OnAccessDenied` 按同样方式重定向；使用 `AuthenticationSchemeNames` 的更新 `using`。
  已有数据库须显式删除三列并覆盖各业务/租户库；若已覆盖模型快照，EF 不会自动推导出删列，需保留旧快照生成迁移或自行编写 `DropColumn`。
  旧 `id`→`sub` 的真实账号连续性尚未验证，已有 Google 外部账号连接的迁移须先实测。

#### 外部登录的本地用户名与账号标签

- **类型**：源码、行为（数据迁移）
- **受影响**：`ExternalUserInfo`；`ExternalLoginConnection.ProviderUsername` 列与输出 DTO、前端字段；自定义提供商实现。
- **原来**：一个 `Username` 同时表示"绑定的是哪个外部账号"和本地用户名，直接采用提供商给的值：`alice@x.com` 与 `alice@y.com` 两个不同的人会撞上
  `Username` 的租户内唯一索引，第二个人首次登录直接失败；值还可能含 `.` `+`。
- **现在**：拆成 `ProviderAccountLabel`（必填，展示用）与 `SuggestedUsername`（可空，**只有真正的公开句柄**才填，由提供商显式给出）。
  GitHub 两个都填 `login`；Google 没有句柄，标签放完整邮箱、`SuggestedUsername` 留 `null`。本地用户名改由外部登录领域服务生成：基底取
  `SuggestedUsername ?? DisplayName`，清洗成 [`UsernameRules`](../../../template/backend/src/CompanyName.ProjectName.Domain/Users/Constants/UsernameRules.cs)
  允许的字符集，裸基底被占用（以及清洗后不可用而回落到 `user`）时加六位随机后缀。邮箱未验证时填的占位地址改为 `{guid:N}@{provider}.local`。
  `ProviderUsername` 改名为 `ProviderAccountLabel`，列名、输出 DTO 字段与前端 `providerAccountLabel` 一并改；模板的基线迁移直接改写，没有新增迁移。
  首次外部登录无法分配用户名时返回 409 `ExternalAuth:UsernameAllocationFailed`（不带数据），此前为 `User:UsernameTaken`（带 `Username`）。
- **迁移**：自定义提供商同步这两个属性，**不要**用邮箱本地部顶替 `SuggestedUsername`。**已部署的派生项目**新增一条迁移改列名，并在新版本开始服务之前执行：

  ```sql
  ALTER TABLE "<schema>"."ExternalLoginConnections" RENAME COLUMN "ProviderUsername" TO "ProviderAccountLabel";
  ```

  表在 `HasDefaultSchema` 指定的业务 schema 里，PostgreSQL 默认搜索路径找不到它，必须限定；用户与外部连接表在**共享库与每个独立租户库里各有一份**，
  逐库执行。用 `migrations add` 让 EF 比对实体时要核对生成结果：它可能给出"删列再加列"而不是 `RenameColumn`，那会丢数据——改成 `RenameColumn`，
  或直接在空迁移里 `migrationBuilder.Sql(...)` 执行上面的语句。基线迁移 Id 未变，存量库不会自动应用，不补则运行时报列不存在。
  用户名与占位邮箱**不回填**：存量行保持原值（新占位地址是随机的，不会与旧值相撞）。按旧码分支的客户端改判新码。

### 用户、角色与账号安全

#### 角色成员关系归入 User 聚合

- **类型**：源码
- **受影响**：生成项目中读取或修改用户角色的代码。
- **原来**：`UserRole` 有独立 DbSet 与 `IRepository<UserRole>`；`UserDomainService.AssignRolesAsync`/`ReplaceRolesAsync` 接收 `Role` 实体直接增删成员关系。
- **现在**：`UserRole` 是 `User` 的子实体，按 `RoleId` 引用角色；DbSet、`IRepository<UserRole>` 与上述两个方法已删除。经 `IUserRepository.GetWithRolesAsync`/`GetQueryableWithRolesAsync` 加载后，用 `user.AssignRoles`/`ReplaceRoles`/`RemoveRole` 修改；整体替换保留未变的成员行，移除的按软删除撤销。
- **迁移**：把直接操作 `UserRole` 仓储与上述领域服务方法的代码改为经 `User` 聚合；`UserRole` 主键改为 `ValueGeneratedNever()`。表结构不变，无需数据库迁移。

#### 用户名与邮箱的可用性判定包含已删除用户

- **类型**：行为
- **受影响**：注册、建用户、改资料。
- **原来**：仓储默认过滤掉软删除行，判定答"可用"，随后落库撞唯一索引（两者的唯一索引都没有排除 `IsDeleted`），用户看到 500。
- **现在**：关闭软删除过滤后查询，答"已被占用"并返回 `User:UsernameTaken` / `User:EmailTaken`。
- **迁移**：派生项目若希望被删用户交还用户名与邮箱，要自行在唯一索引上加 `IsDeleted = false` 过滤并新增迁移（那会改变"删掉再建同一个人"的语义，本次不做）。

#### 用户新增 `SecurityStamp`

- **类型**：行为（数据库模型）
- **受影响**：已部署的派生项目的用户表；登录第二步的挑战。
- **原来**：第一步之后改口令、管理员重置、启用或停用两步验证、解绑外部登录，挑战仍能完成登录。
- **现在**：挑战记下签发时的值，上述操作后挑战即作废（基线迁移已含该列）。
- **迁移**：**已部署的派生项目**新增一条迁移加这一列（`character varying(32)`，非空）；存量行可填任意值（如 `md5(random()::text)` 截取 32 位），
  下次凭据变更时自动轮换。

#### 两步验证、会话与清理作业

- **类型**：行为
- **受影响**：两步验证挑战有效期；"退出其他设备"的返回值；过期会话与 OpenIddict 令牌的保留；撤销令牌。
- **原来 → 现在**：
  - 两步验证挑战的有效期不再被输错延长：此前每次输错都把 5 分钟重新算满，最长约 25 分钟；现从签发起算，到期以注入的时钟为准。
  - "退出其他设备"的返回值只计有效设备：已过期的会话照旧一并删除，但不计入提示数与操作记录。
  - 新增每日过期会话清理作业 `auth.sessions.cleanup`：不再登录的用户的过期会话（连同原始 IP）此前会无限期保留。作业逐库执行、含停用租户的库，
    删除时关闭租户过滤。
  - 新增每日 `auth.openiddict.prune` 集群任务，使用官方管理器，清理早于 14 天阈值创建的无效令牌与授权（并非过期后额外保留 14 天）。
    控制库不按租户重复执行，多副本沿用 Redis 集群锁与共享水位。
  - 撤销令牌改用官方批量接口：`UserAppService` 用 `RevokeBySubjectAsync` 替代逐个 `TryRevokeAsync`；并发撤销失败不再被吞掉，会让整个操作失败。
- **迁移**：多副本部署需 Redis（集群锁），锁键前缀规则同其他周期任务。

#### 只分配给已删除用户的角色可以删除

- **类型**：行为
- **受影响**：角色的"已分配用户数"与删除校验；删除角色的事务边界。
- **原来**：删除用户是软删除、角色关联行保留，这些行也被计入，角色永远删不掉；角色与授权分两次提交，失败后会留下"接口报错但角色已删"的状态。
- **现在**：只数未删除的用户；删除角色时连带删除剩余的关联行。删除角色改为单一工作单元：角色、关联、授权与成功记录一起提交，任一步失败整体回滚。
- **迁移**：按模板同步。

#### 默认管理员口令只在首次创建时校验

- **类型**：行为
- **受影响**：`DefaultAdmin:Password` 的启动期校验、`DefaultAdminOptions.IsPasswordUsable`、compose 的 `DEFAULT_ADMIN_PASSWORD`。
- **原来**：启动期校验口令；compose 以 `:?` 强制 `DEFAULT_ADMIN_PASSWORD`。
- **现在**：两者删除；库里没有超级管理员、需要创建时才校验并报出键名。`appsettings.Development.json` 带公开的本机演示口令；compose 不再强制该变量。
- **迁移**：按模板同步。

### API 契约与错误码

#### 外部账号绑定完成返回空响应

- **类型**：行为
- **受影响**：`POST /api/v1/external-auth/{provider}/link/complete`、`POST /api/v1/external-auth/{provider}/complete` 的客户端。
- **原来**：绑定成功返回 `{ "linked": true }`。
- **现在**：绑定成功返回 HTTP 200 空响应体；`complete` 直接返回登录结果 DTO（JSON 形状不变）。两个控制器共用的最终会话签发收进
  `Api/Auth/SessionCookieIssuer`（构造注入），不再经 `HttpContext.RequestServices` 定位服务或跨控制器调用静态方法；外部票据一次消费、发起者与租户校验、
  两步验证未完成不签发最终 Cookie 的行为不变。
- **迁移**：读取 `linked` 字段的客户端改为按状态码判断成功。

#### 错误码收敛、入参校验与授权拒绝交给管道、删除幂等

- **类型**：行为、源码
- **受影响**：按错误码分支的客户端与自定义词条；引用被删常量或词条的代码；依赖 404 判断"已删除"的客户端。
- **原来 → 现在**：
  - 邮箱占用统一为 `User:EmailTaken`（409，`WithData("Email")`）：`PUT /api/v1/users/{id}` 原 `User:EmailAlreadyUsed`、`POST /api/v1/auth/send-email-code`
    原 `Auth:EmailAlreadyUsed` 均改为该码。发码前的判定与建号一致：被删除用户仍占用的地址现在在发码时即被拒（原先放行、注册时才失败）；
    只差大小写的地址按唯一索引视为不同地址，不再被拒。
  - `POST /api/v1/settings/email/test` 改由策略 `App.Settings` 授权：无权限返回授权管道的标准 403，响应不带 `code`（原 `AppSetting:ManagePermissionRequired`，
    常量、映射与词条已删除）；租户内调用仍为 403 `AppSetting:TestEmailHostOnly`。
  - 删除不可达或零引用的码及词条：`Auth:UnsupportedGrantType`（OpenIddict 已按协议回 `unsupported_grant_type`，未登记处理分支改为 `InvalidOperationException`）、
    `Tenant:ImpersonationRequiresAuthentication`（原 401 映射；未认证请求在授权阶段已被拒）、`ExternalAuth:ProviderNotSupported`。
  - `SecurityErrorCodes` 命名空间由 `…Domain.Shared.Security.Errors` 改为 `…Application.Auth.Errors`（码值不变）；`ExternalAuth:InvalidState`
    改用常量 `ExternalAuthErrorCodes.InvalidState`（码值不变）。
  - 删除不存在的资源一律成功：`DELETE /api/v1/users/{id}` 与 `DELETE /api/v1/open-applications/{id}` 在对象不存在（含已删除）时由 404 改为 200，不写操作记录。
  - 入参校验由业务码改为 400 字段错误（`urn:leistd:problem:validation-error`，不带 `code`）：`OpenApp:ClientIdRequired`、`OpenApp:ApplicationTypeUnsupported`、
    `OpenApp:ClientTypeUnsupported`、`OpenApp:InvalidUri`（字段 `redirectUris`/`postLogoutRedirectUris`）、`Role:NameTooLong`（用户列表 `roles` 查询参数）、
    `Auth:TwoFactorCodeRequired`（字段 `code`）的常量与词条已删除；`PUT /api/v1/auth/me/avatar` 提交非图片 data URL（如外部地址）由 `User:AvatarInvalid`
    改为 400 字段 `avatar`。
- **迁移**：客户端按旧码分支的改判 `User:EmailTaken`、按 HTTP 状态或 `errors[].field` 分支；自定义词条改键；引用被删常量或词条的代码一并删除；
  更新 `SecurityErrorCodes` 的 `using`；依赖 404 判断"已删除"的客户端改按 200 处理。

### 操作记录与审计

#### 业务拒绝留痕中间件

- **类型**：行为
- **受影响**：派生项目的 API 管道。
- **原来**：组件映射的端点（如权限整体替换）被业务规则拒绝（并发冲突、权限未定义、主体不存在）时没有记录，只有授权阶段被拒才记；
  中间件只记码，带占位符的码显示成 `Email '{Email}' is already in use.`。
- **现在**：模板新增 `Api/Middlewares/OperationFailureRecordingMiddleware`，放在 `UseAuthorization()` 之后，调用
  `RecordFailedOperationAsync(OperationFailure.FromCode(exception.Code, exception.LocalizationData))` 连同消息参数一起记；只记 `BusinessException`，
  参数校验失败不记。查询时渲染出与接口报错同一句带具体值的原因。
- **迁移**：照模板加这个中间件。**审计与导出会出现这些值（如邮箱、用户名）**：只把可公开展示的值放进 `LocalizationData`，规则见
  [组件端点的业务拒绝留痕](#组件端点的业务拒绝留痕)。

#### 新增操作记录动作

- **类型**：行为
- **受影响**：自定义了操作记录动作展示的派生项目；前端 `operationRecords.actions` 与 `actionsNoTarget` 词条。
- **原来**：管理员启停用户、重置密码等操作不留记录。
- **现在**：新增动作 `user.enabled`、`user.disabled`、`user.password-reset`（账号类，Notice；状态没变的重复启停不留记录；控制器同时挂上
  `[OperationRecordAction]`，被拒的操作也留痕）；`setting.test-email-sent`（不带目标；成功、授权拒绝、业务失败均记录）；`role.updated`、
  `open-application.created`、`open-application.updated`、`open-application.deleted`、`open-application.secret-reset`（后四个仅 Identity 形态、宿主可见）。
- **迁移**：补这些码的文案与前端词条。

#### 失败原因的词条归后端

- **类型**：行为
- **受影响**：模板前后端的失败原因词条。
- **原来**：前端按 `operationRecords.failures.<码>` 自备词条（如 `Error_Forbidden`）。
- **现在**：删除前端 `Error_Forbidden` 等三条失败词条，前端 `operationRecords.failures` 整节删除；后端资源补 `Error:Forbidden`
  （随后由组件随包提供，宿主资源中的同名词条应删除）；登录失败与锁定两条记录带着错误响应没有的参数，后端资源新增
  `Auth:InvalidCredentials:Record`、`Auth:UserTemporarilyLockedOut:Record`。不含本地化的形态仍内置英文句子，按同样的 `{name}` 占位符填参数；
  操作记录页切换语言时重新拉取列表。框架侧规则见[失败原因由后端本地化](#失败原因由后端本地化)。
- **迁移**：按模板同步。

#### Resource 的首次管理员授权

- **类型**：行为
- **受影响**：依赖前端登录或人工 SQL 授予管理员的 Resource 项目；已用 0.13.0 预发布版命令写过用户级全量授予的项目。
- **原来**：前端登录或人工 SQL 授予。
- **现在**：首次授权使用正式 DbMigrator `--grant-admin <sub> [--tenant <id>]`，默认 dry-run，`--apply` 才写入；授权载体是 Admin 角色成员关系，
  重复运行不恢复已移出的成员关系。
- **迁移**：已用预发布版命令写过用户级全量授予的项目，在明确的数据调整中只收口那次引导写入的全量直接授予、改为 Admin 成员关系；项目另行配置的合法用户级授予保留。

### 数据库、迁移与开发环境

#### 测试与开发只用 PostgreSQL

- **类型**：源码、行为
- **受影响**：`Database:InMemoryName`、`Microsoft.EntityFrameworkCore.InMemory`、`TenantConnectionResolutionOptions`；本机开发流程；集成测试夹具。
  依据与原型实测见[模板开发规范 §9](../../template/development-guide.md#9-测试与开发只用-postgresql为什么不用-inmemory-或-sqlite)。
- **原来**：可回退 EF InMemory；集成测试按 `Database:InMemoryName` 切换新库。
- **现在**：开发、集成测试与运行时只有 Npgsql 一个提供程序。`ConnectionStrings:Default` 必填，缺失时 API 在接流量前（迁移校验创建上下文时）
  启动失败并指明键名。Api 与 DbMigrator 各有一份 `appsettings.Development.json`，指向 `template/deploy/docker-compose.dev.yml` 的本机库；
  DbMigrator 新增 `RunWorkingDirectory`，从 `backend/` 运行也读得到自己的开发配置。Resource 本机开发需要机器身份：开发配置补上
  `Leistd:ServiceAuth:Authority` 与回源地址，DbMigrator 用 `tenant-migration.read`。集成测试跑在真实 PostgreSQL 上，需要本机 Docker：
  新增 `PostgreSqlTestDatabase`（Testcontainers），每次测试运行迁移一次模板库，每个 `ProjectWebApplicationFactory` 克隆一份、释放时删除；
  Resource 测试宿主用共享库替身代替远端租户连接存储。
- **迁移**：删除内存库配置、包与 `TenantConnectionResolutionOptions`；本机开发流程改为 `docker compose … up -d` → `dotnet run --project …DbMigrator -- --apply`
  → 启动 API。Resource 在 Identity 登记 client credentials 客户端，把 `Leistd:ServiceAuth:ClientId/ClientSecret` 写进 user-secrets（缺失时启动失败并指明键名）。
  沿用测试夹具时删除依赖内存库语义的写法（改为克隆新库），批量 `ExecuteUpdate`/`ExecuteDelete` 后的断言换一个作用域读库。

#### 迁移作业只注册持久化

- **类型**：源码
- **受影响**：Infrastructure 的注册方法与 DbMigrator。
- **原来**：迁移作业注册了全部运行期组件，它们依赖只在 API 注册的当前用户与权限主体，开发环境下迁移在容器构建期失败。
- **现在**：Infrastructure 拆出 `AddPersistenceServices`（数据库上下文、租户连接解析、多租户控制库），`AddInfrastructureServices` 在它之上加运行期组件与外部适配器；
  DbMigrator 只调用前者。
- **迁移**：按模板拆分。

#### DbMigrator 报出失败租户

- **类型**：行为
- **受影响**：发布流水线对 DbMigrator 退出码的处理。
- **原来**：单个租户失败挡住其他租户。
- **现在**：租户目标中，取不出连接的租户与迁移出错的独立库都记进报告，其余库照常预演或施加；跑完后逐个报出并以退出码 1 结束（预演同样如此）。
  控制库、OIDC 存储、默认业务库与显式 `MigrationTarget` 出错仍立即结束，取消立即传播。首次安装的判定（只读预演、控制库仍有待迁移、缺表）不变。
- **迁移**：非零退出可能意味着部分库已经迁移、且不会回滚：发布流水线据退出码停下，修好后重跑；新旧 schema 并存期间的兼容性按部署说明的 Expand 阶段要求保证。
  框架契约变化见[迁移目标报出失败租户](#迁移目标报出失败租户)。

#### 生成的 Client 项目注册入口

- **类型**：源码
- **受影响**：Client 项目的 `AddMyProjectClient(configuration)` 调用方。
- **原来**：`AddMyProjectClient(configuration)`。
- **现在**：`AddMyProjectClient(configure?, configSectionPath?)`。
- **迁移**：调用方去掉实参，并按[服务间用户委托](#服务间用户委托改用官方-token-exchange)显式组合 `.AddClientCredentials()` 或 `.AddTokenExchange()`。

#### 测试规范与假时钟

- **类型**：源码（测试项目）
- **受影响**：集成测试项目。
- **原来**：时间相关测试依赖真实时钟。
- **现在**：`TwoFactorTests` 改用 `FakeTimeProvider` 替换容器里的 `TimeProvider`（集成测试项目新增 `Microsoft.Extensions.TimeProvider.Testing` 引用）；
  测试规范补充时间边界用假时钟验证、端到端不等安全窗口，并列出不随假时钟快进的官方组件。新增集成测试 `RequestLoggingTests` 断言请求完成事件进入宿主管道并带关联标识。
  测试名统一英文：后端测试方法名、`DisplayName` 用英文句子，中文只在注释与测试数据里。
- **迁移**：按模板同步。

### 宿主、日志与部署

#### 日志不再出现邮箱原文

- **类型**：行为
- **受影响**：`AuthAppService`（注册）、`UserAppService`（管理员建用户）、`EmailSettingsAppService`（测试发信失败）的日志；派生项目自己写的日志。
- **原来**：记邮箱原文。
- **现在**：记脱敏后的地址（`al***@example.com`），经 `Leistd.Core` 的 `Leistd.Redaction.TextRedactor.RedactEmail`。**账号名照常记，不改**：
  模板的用户名受 `^[a-zA-Z0-9_]+$` 约束、不可能是邮箱，是系统自身的账号标识而非联系方式，换成 GUID 会让排障的人每条都要回库查一次。
  操作记录的参数口径**不变**：审计按设计会显示邮箱、用户名等可公开展示的值，不受本条影响，不要误以为审计也脱敏了。
  框架没有引入脱敏组件：评估过 `Microsoft.Extensions.Compliance.Redaction`（数据分类 + `IRedactorProvider` + 日志脱敏），缺陷是"组件默认把个人数据写进日志"，
  终局修法是默认不写。实测结论见[框架开发规范 §4](../development-guide.md#4-文档注释)。
- **迁移**：派生项目自己写的日志按同一口径核对：**联系方式（邮箱、手机号）不进日志**；不要为此把用户名从日志里去掉。自行接入脱敏的项目注意两点：
  **普通模板日志（`logger.LogInformation("{To}", to)`）永远不会被脱敏**，脱敏只作用于带 `[LoggerMessage]` 与数据分类标注的源生成方法；
  **`builder.Services.AddSerilog(configure)` 与 `EnableRedaction()` 冲突，两者同时存在时日志会全部消失**（不是丢字段）。

#### 请求完成日志走宿主日志管道

- **类型**：行为
- **受影响**：`Program.cs` 的 `UseSerilogRequestLogging`。
- **原来**：宿主 logger 用 `preserveStaticLogger: true` 独立持有，不设置时 Serilog.AspNetCore 的请求日志中间件回落到静态 `Log`（启动期那个只输出纯文本的 logger）：
  请求完成事件丢掉配置里的格式、sink 与 enrich（含关联标识）。
- **现在**：显式设置 `options.Logger` 为容器里的 `Serilog.ILogger`；租户在 `UseMultiTenancy()` 之后写入 Serilog 诊断上下文，请求完成日志也带租户。
- **迁移**：照此加一行。

#### 缺 Redis 的启动告警与部署文档更正

- **类型**：行为
- **受影响**：非 Development 环境未配置 `ConnectionStrings:Redis` 的部署。
- **原来**：静默回落；部署文档写"开发环境以外的单机回落一律启动失败"。
- **现在**：启动日志新增一条 Warning，列出回落到进程内存的状态（会话票据，本地身份还有会话撤销检查、两步验证挑战、图形验证码与邮箱验证码），
  说明只适合单实例；仍不阻止启动。分布式锁的回落仍由锁组件在首次解析时单独告警。部署文档更正：启动失败只对 Data Protection 等列出的项成立；
  `DataProtection:KeysPath` 只替代密钥存储，不替代 Redis。
- **迁移**：多副本部署须配置 Redis。

#### 实时 Hub 的来源检查

- **类型**：行为
- **受影响**：从其他源连接 Hub 的前端。
- **原来**：`BrowserOriginMiddleware` 只覆盖 `/api` 写请求；CORS 不约束 WebSocket，同站其他子域（或会话 Cookie 放宽到 `SameSite=None` 时的任意站点）
  能带着 Cookie 握手并读取推送（CSWSH）。
- **现在**：覆盖扩展到 `/hubs/**` 的全部方法，含 WebSocket 握手：带 Origin 的连接只接受本源与 `Cors:AllowedOrigins`，没有 Origin 时按 `Sec-Fetch-Site` 判定，
  两个头都没有的非浏览器客户端照常连接；Hub 不因带 Authorization 头而跳过检查。
- **迁移**：按文档同源部署不受影响；从其他源连接 Hub 的前端加进 `Cors:AllowedOrigins`。

#### 开发代理与本机跨域

- **类型**：源码
- **受影响**：后端 `SpaProxy` 选项与实现；`Cors:AllowAnyLocalhost`；`/uploads` 静态目录与 compose 的 `feedback-uploads` 卷。
- **原来**：后端 SpaProxy 转发前端；`Cors:AllowAnyLocalhost` 服务本机跨域联调；存在没有写入方的 `/uploads`。
- **现在**：开发代理改为 Angular `proxyConfig`：前端 `proxy.conf.mjs` 转发 `/api`、`/hubs`（WebSocket）以及身份服务的 `/connect`、`/.well-known`，
  浏览器访问 `http://localhost:4200`。三者删除。
- **迁移**：后端不在默认端口时设置 `API_PROXY_TARGET`；前端部署在另一个源时仍用 `Cors:AllowedOrigins`；删除 `/uploads` 与该卷。

#### 镜像以非 root 运行与上手项

- **类型**：行为（部署）、源码
- **受影响**：API 与迁移镜像；compose 文件型 secret 与 Data Protection 密钥目录；`.http`、OpenAPI、compose 镜像名、`TZ`。
- **原来**：root 运行；镜像名写死个人仓库。
- **现在**：API 与迁移镜像 `USER $APP_UID`（UID 1654）。`.http` 改为健康检查与 OpenAPI 端点；新增官方 OpenAPI（`AddOpenApi()`，Development 下
  `MapOpenApi()`，`/openapi/v1.json`）；compose 镜像名改为 `${BACKEND_IMAGE:-companyname-projectname:latest}` / `${MIGRATOR_IMAGE:-…}`；
  `TZ` 默认 `UTC`（进程本地时区，可经 `.env` 覆盖）。
- **迁移**：compose 文件型 secret 保留宿主机权限，证书须对 UID 1654 可读（`chown 1654` 或属组可读）；用文件目录存 Data Protection 密钥时目录须可写。

#### 实时资源订阅改为按持有者生命周期登记

- **类型**：源码
- **受影响**：`SignalRService.subscribeResource(key)` / `unsubscribeResource(key)`（删除）。
- **原来**：

  ```ts
  void this.signalR.connect().then(() => this.signalR.subscribeResource(key));
  this.destroyRef.onDestroy(() => void this.signalR.unsubscribeResource(key));
  ```

- **现在**：`watchResource(key, destroyRef?)`：调用即登记需求，`DestroyRef` 销毁时自动撤销；省略 `destroyRef` 时取当前注入上下文的
  （须在构造期或字段初始化时调用）。服务按"是否仍有持有者"与"当前连接上是否已订阅"的差值，为每个键串行补齐 Subscribe/Unsubscribe；
  首次连接与自动重连后统一重新对账，`reset()` 清空全部登记。修掉的交错：连上之前页面已销毁仍会订阅；订阅在途时退订、晚到的订阅把键加回重连集合；
  旧页面的清理撤掉新页面同一个键的订阅；`reset()` 之后旧页面的操作打到新主体的连接上；重连恢复途中释放的键仍被恢复。后端的租户与权限校验不受影响。
  `resourceSubscribed$` 的语义不变：确认改由对账步骤发出，每个键实际发起的 Subscribe 成功、且仍属于当前连接与有效需求时发出一次
  （首次订阅、自动重连、重建连接各自都会走到）；确认回来时连接已换或已无人持有则不发出。再次登记一个已经订阅着的共享键不另发确认，
  页面照常自己做首次查询，确认流只用于补查。前端规范 §5.1 放宽构造函数，允许需要注入上下文的生命周期接线；§5.8 的订阅写法改为 `watchResource`。

  ```ts
  // 构造期或字段初始化时
  this.signalR.watchResource(key);
  void this.signalR.connect();
  // 注入上下文之外，例如 ngOnInit 里
  this.signalR.watchResource(key, this.destroyRef);
  ```

- **迁移**：按上例改写；组件里为此加的 owner、存活标记一并删除，不要再把订阅放进 `connect().then(...)`。

#### 实时连接的默认日志等级

- **类型**：行为
- **受影响**：`signalr-service.ts` 的 `configureLogging`。
- **原来**：`Information`。WebSocket 传输带不了请求头，令牌只能拼进 URL 查询串（`access_token=`），而 `@microsoft/signalr` 连接成功那条日志以
  `Information` 打印**整个 URL**——令牌原文进浏览器控制台（只有配了 `accessTokenFactory` 的形态真会带令牌，但默认值不按形态分叉）。
- **现在**：`Warning`。代价是失去常规连接信息，`Warning` / `Error` 仍在。**日志等级管不到浏览器自己打的那条**：握手失败时浏览器会输出
  `WebSocket connection to 'wss://…?access_token=…' failed`；要彻底避免只能让访问令牌本身不进入浏览器发起的连接 URL（例如协商阶段换一张短时效的
  一次性连接票据）；**在反向代理层改写没有用**。本模板未实现票据这一层。
- **迁移**：按模板同步；排障可临时调高，调高之后日志里可能带出凭据。

#### 单测迁到 Vitest

- **类型**：源码
- **受影响**：前端单测、Karma/Jasmine 配置与依赖、CI 安装步骤。
- **原来**：Karma + Jasmine。
- **现在**：
  - `ng test` 改由 `@angular/build:unit-test` 驱动 Vitest，在 Playwright 的无头 Chromium 里运行；Karma、Jasmine 及其配置删除
    （`karma.conf.js`、`@types/jasmine`、`istanbul-lib-instrument` 等）。有头运行：`npm test -- --browsers=chromium`。
  - spec 写法：`jasmine.createSpyObj` → 由 `vi.fn()` 组成的对象，类型用 `Pick<MockedObject<T>, …>`；`spyOn` → `vi.spyOn`（**默认调用原实现**，
    要桩掉副作用须显式 `mockReturnValue` / `mockResolvedValue`）；`.and.returnValue` → `.mockReturnValue`；`toBeTrue()` → `toBe(true)`；
    `done` 回调改为 `async` + `firstValueFrom`。
  - 单测专用构建配置 `unit-test`：不做开发构建的 Mock 提供器替换，`template/frontend/_mock/core/providers.ts` 保持部署形态；自定义了 `development`
    配置的项目，单测不再跟着它变。
  - `vitest-base.config.ts` 开启 `restoreMocks`、`unstubGlobals`；`isolate: true`：每条用例开始前自动还原 `vi.spyOn` 替身与 `vi.stubGlobal` 的全局值
    （其他直接修改与假计时器仍需自己还原）；每个 spec 文件在独立页面运行，并发执行的文件之间不共享全局对象上的桩。
  - 测试名统一英文：`describe` / `it` 标题用英文句子，中文只在注释与测试数据里。
- **迁移**：新机器首次运行前执行 `npx playwright install chromium`，CI 同样需要安装（`--with-deps`）。已有项目可先跑官方
  `ng g @schematics/angular:refactor-jasmine-vitest`，再按上述差异与下一条核对。

#### Vitest 迁移的两处静默陷阱

- **类型**：行为
- **受影响**：`_mock` 等 `src` 之外的测试目录；官方 schematic 转换后的 spec。
- **原来 → 现在**：
  - **`_mock` 目录下的 spec 此前从未执行**：`angular.json` 的 `unit-test.include` 原为 `_mock/**/*.spec.ts`，而 include 的 glob 以 `sourceRoot`（`src`）为
    工作目录，它被解析成不存在的 `src/_mock/**`，测试照样全绿。这不是 Vitest 迁移引入的，Karma 时期同样如此。
  - **官方 schematic 的转换要逐文件核对**：`refactor-jasmine-vitest` 是实验性的。已复现会**静默改变测试语义**的形态：
    ① 分离的策略调用——`const spy = spyOn(x, 'm');` 之后另起一行 `spy.and.callThrough();`，会转成 `vi.spyOn(x, 'm').mockReturnValue(undefined)`
    加一句悬空的 `spy;`，测试从"测真实实现"变成"测桩值"（紧跟写法 `spyOn(x, 'm').and.callThrough()` 转成 `vi.spyOn(x, 'm')`，行为等价，不要一律当成错误转换）；
    ② 已有桩值之后再 `callThrough()` 同样丢失切回真实实现；③ `// prettier-ignore` 块被重排、文件末尾注释被丢；④ Vitest 的 `toContain` 不接受
    `objectContaining`；⑤ 未处理的 Promise 拒绝会让整轮失败；⑥ 被其他 spec 导入的"测试辅助 spec"会被重复登记用例。
- **迁移**：include 写成 `../_mock/**/*.spec.ts`；自建了 `src` 之外测试目录的项目用 `ng test --list-tests` 列出实际被发现的文件，与磁盘上的 spec 集合比对，
  不要只看用例总数。在**迁移前的代码与迁移 diff 上**搜 `callThrough`（迁移后它已被删掉）；`expect(` 计数只能作辅助（①②发生时断言数完全可以不变）；
  关键处核对真实副作用或返回值，并用"撤回修复"的变异确认判据真的会红。

#### lint 结果缓存

- **类型**：源码
- **受影响**：默认与本地化前端的 `lint:ts`、`lint:style`、`format` scripts；依赖安装与 Git/格式检查的忽略配置。
- **原来**：无条件重跑。
- **现在**：改为对应工具的官方 content cache，检查范围和规则不变；没有双入口或迁移开关。缓存不随模板生成分发，不加入依赖包或公共 API；现有 `prepare: husky` 保留。
- **迁移**：同步这三个 scripts、依赖安装时删除 `.cache/lint/` 的 `postinstall`，并在 Git/格式检查中忽略该目录。插件更新可能不进入格式检查器的缓存键，
  因此不能只同步 `--cache` 而遗漏安装清理；显式忽略 npm 生命周期脚本安装后，先删除 `.cache/lint/` 再检查。维护与验收口径见
  [模板质量验证](../../template/quality-assurance.md)。

#### Angular 依赖更新到 22.2.0

- **类型**：源码
- **受影响**：默认与本地化前端的两套依赖文件与 lock。
- **原来**：Angular 22.1 系列。
- **现在**：Angular 运行时、CDK、编译器和 CLI/build 统一更新到 22.2.0，以通过既有 high 审计阈值；不修改 lint 缓存、测试隔离或发现范围。
  安全依据见 [Angular Router 官方公告](https://github.com/advisories/GHSA-ff3f-86qr-9cv3)（公告利用路径为 Node SSR）。
- **迁移**：按两套依赖文件更新并重新安装。
