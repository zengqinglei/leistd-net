# 隔离与授权：三种能力的适用场景与验证策略

多租户、基于角色的功能权限、数据范围权限回答三个**不同**的问题。混用会同时得到两个坏结果：该硬隔离的地方被业务规则放宽，该灵活配置的地方被写死在架构里。

| 能力 | 回答的问题 | 判定时机 | 谁能突破 |
| --- | --- | --- | --- |
| 多租户 | 这条数据**属于谁** | 查询构造（EF 全局过滤器） | 没有人。超管也不行，只有显式 `IDataFilter.Disable<IMultiTenant>()` 的系统操作 |
| 功能权限（RBAC） | 能否执行**这类动作** | 请求进入端点前（策略） | 超管跳过授予查询，但**跳不过**权限未定义与侧别不匹配 |
| 数据范围 | 集合里有**哪些条** | 查询构造（谓词并集） | 超管不施加范围 |

三者是 **AND** 关系，且顺序固定：租户过滤器永远生效 → 功能权限先拦 → 数据范围再缩小集合。数据范围的并集只在租户过滤器之内取并，永远不会把别的租户放进来。

实现位置差异同样重要：

| 能力 | Framework | Template | 业务项目需要做什么 |
| --- | --- | --- | --- |
| 多租户 | `Leistd.MultiTenancy.*` 三包 | **已接入**（`IncludeTenancy`） | 实体实现 `IMultiTenant` 即可 |
| 功能权限 | `Leistd.Authorization.*` | **已接入**（`IncludeRoles`） | 写 `IPermissionDefinitionProvider` |
| 数据范围 | `Leistd.Authorization.DataScope.Core` | **未接入** | 必须自行实现 `IDataScopeProvider<T>` 与 `IDataScopeAssignmentProvider` |

---

## 1. 多租户

### 适用场景

| 场景 | 判断 |
| --- | --- |
| 同一套部署服务多个互不信任的客户，数据绝不能互相看见 | 用。这是硬隔离 |
| 需要"宿主管理员管理租户、租户管理员管理自己人"的两级管理面 | 用。侧别（`MultiTenancySides`）就是为此设计 |
| 同一公司内部的部门/子公司，需要上级看下级 | **不要用**。租户之间没有"上级"，跨租户查看只能靠显式关闭过滤器。这是数据范围的场景 |
| 只是想给数据打个"归属"标签用于筛选 | 不要用。租户是不可绕过的硬边界，不是筛选维度 |
| 需要按客户定制表结构 | 本方案不支持（共库共表），需要另做分库分表 |

### 测试策略

隔离缺口的特征是**静默**——漏了过滤器不会报错，只会多返回几行。因此测试必须以"看不见"为断言，且必须在**关系型**数据库上跑：EF InMemory 在内存求值，会让不可翻译的过滤器和唯一索引静默通过。

| 层 | 必须证明 | 用什么 |
| --- | --- | --- |
| 单元（Core） | `Change` 嵌套还原、跨 `await` 与跨 DI scope 流动、解析链顺序与终止语义 | xUnit |
| 过滤器（Sqlite） | 租户与软删双过滤器叠加；`GetByIdAsync` 跨租户不可见；**没有 `DbSet` 声明、只经 `ApplyConfiguration` 入模型的实体同样被过滤** | Sqlite，非 InMemory |
| 中间件（TestServer） | claim 优先于头（防水平越权）；未知 404、停用 403；已删除与不存在同形状 | TestServer |
| 集成（生成项目） | 三路越权矩阵（列表/详情/更新）；同名用户分属不同租户互不可见；停用后在途会话被处理 | 生成项目集成测试 |
| 浏览器 | 见 §4 | agent-browser |

### 测试步骤

1. **先写"看得见"的正向用例**，确认数据确实写进了目标租户——否则后面所有"看不见"的断言都可能因为压根没写进去而假绿。
2. 在租户 A 上下文内断言只见 A 的行；切到 B 断言只见 B；宿主上下文断言只见 `TenantId IS NULL` 的行。
3. **按 Id 直取**也要断言不可见（跨租户拿 Id 访问详情必须 404，不是 403——403 会泄漏"这条存在"）。
4. 唯一索引按宿主行/租户行**成对的过滤索引**验证：可空列直接进唯一索引时 NULL 互不相等，宿主行会失去唯一性兜底。
5. 每加一个租户化实体，同步更新"完整性锁"断言清单。清单只枚举 `IMultiTenant` 类型，**不实现该接口的关联表（如 `UserRole`）必须单独断言**。

## 2. 基于角色的功能权限（RBAC）

### 适用场景

| 场景 | 判断 |
| --- | --- |
| "谁能进这个菜单/调这个接口" | 用。这是它的本职 |
| 权限需要运行期由管理员调整 | 用。定义树在启动时固定，**授予**可随时增删 |
| 需要"能看列表但只能改自己的" | 只用 RBAC 不够，加数据范围 |
| 需要"这一份文档分享给张三" | 不是 RBAC，是资源实例授权（ACL） |
| 想用"拒绝"权限收回某人的能力 | **做不到也不该做**。授予是纯加法（用户 + 各角色取并集），要收回就调整角色构成 |

### 测试策略

RBAC 的坑集中在三处：定义树与授予的归一化、超管旁路的边界、以及前端菜单与后端检查是否同口径。

| 层 | 必须证明 |
| --- | --- |
| 单元 | 未定义/被禁用权限一律拒绝（含超管）；祖先禁用则子孙不可用；权限名全局唯一冲突在启动期抛错 |
| 写时归一化 | 授予子权限自动补齐祖先；写入非法权限抛 `UndefinedPermissionException`（管理器是唯一执行点） |
| 并发 | `expectedRevision` 不匹配抛冲突且**不写入**；版本读两遍防"旧集合 + 新版本" |
| 集成 | 单个权限不能越权（如 `Update` 不能改角色）；删角色连带清授予与版本；`current` 权限集与检查器同口径 |
| 与租户交汇 | 宿主侧权限在租户上下文内对**任何主体含超管**不可用 |

### 测试步骤

1. **先建一个只有单个权限的角色**，用它逐个探测相邻端点——只测超管等于没测。
2. 断言 `GET /permissions/current` 的集合与实际检查结果一致。这条最容易漂移：检查器有侧别边界，而下发端点可能对超管直接给全量，导致前端画出点进去必然 403 的菜单。
3. 授予子权限后断言祖先也被授予（归一化），且**不**授予兄弟。
4. 超管路径单独测：它跳过授予查询，但不能跳过"权限未定义"和"侧别不匹配"。
5. 前端按权限裁剪的菜单/按钮，必须用**不同权限组合的用户**各跑一遍，而不是只跑超管。

## 3. 数据范围权限

### 适用场景

| 场景 | 判断 |
| --- | --- |
| 有后台列表、分页总数、聚合统计、导出或批量操作 | 用。集合关系必须在查询构造阶段翻译成 SQL |
| 可见范围是"本人/本部门/下级部门/负责区域" | 用。这类关系用 ACL 物化会产生大量同步写与孤儿记录 |
| 数据量大，不可能加载候选后逐条判断 | 用 |
| 只按精确 Id 打开单条，几乎没有列表 | 不用，见资源实例授权 |
| 只需判断"能否执行这类动作" | 不用，RBAC 就够 |

**本能力在模板中未接入**：Framework 只定义策略、组合语义与查询扩展点，不内置"部门""组织树"等业务概念。业务项目必须自行提供 `IDataScopeProvider<T>`（每种范围一个）和 `IDataScopeAssignmentProvider`（范围从哪来）。

### 测试策略

数据范围最危险的失败是**放开而不是拒绝**，且组合规则决定了几种反直觉的默认：

| 情形 | 正确行为 |
| --- | --- |
| 主体不可识别 | 空结果集，不是全部 |
| 没有任何分配 | 空结果集 |
| 分配了一个没有对应 Provider 的范围 | 跳过该分配，**不放宽** |
| 多个分配 | 取并集（OR） |
| "全部可见" | 必须显式 `_ => true`；"不贡献可见性"是 `_ => false`。**不存在"什么都不返回"这一态** |

| 层 | 必须证明 |
| --- | --- |
| 单元（关系型！） | 上表五条组合规则；谓词**可被数据库翻译**——InMemory Provider 全部在内存求值，不可翻译的谓词会静默通过，等于没测 |
| 集成 | 列表、总数、导出共用同一入口且三者一致；范围外详情返回 404 而非 403；读范围不蕴含写范围；批量操作整体拒绝而非静默跳过 |
| 与硬边界 | 范围并集永远与租户过滤器、软删过滤器做 AND，不会放宽它们 |

### 测试步骤

1. **在关系型 Provider 上写测试**。这一条是硬性的：InMemory 会让不可翻译的谓词假绿。
2. 给主体分配"组织"范围，断言列表只含该组织；再断言**总数**与**导出**给出同样的集合——三个入口共用同一个范围调用是这个组件最容易破的约定。
3. 分别给 `Read` 与 `Update` 不同范围，断言"能看不等于能改"。
4. 批量操作传入含越权项的 Id 集合，断言**整体拒绝**并且一条都没改。
5. 负向：不给任何分配 → 空集；给一个没注册 Provider 的范围名 → 仍是空集而不是全表。

> 可执行事实来源：`framework/tests/Leistd.Authorization.Pipeline.Tests` 是一个真实 ASP.NET Core 宿主（TestServer + Sqlite + 真实 DI），把功能权限 → 数据范围 → 资源 ACL 三层串起来跑通，覆盖上述全部负向场景。改动这三层的公共行为时连同它一起更新。

## 4. 浏览器端到端的定位

前三节的测试都在进程内。浏览器闭环覆盖的是**它们各自都测不到的接缝**：

| 进程内测试难以覆盖的接缝 | 曾经实际发生 |
| --- | --- |
| 后端判定正确但前端菜单画错 | 租户超管菜单里出现"租户管理"，点进去必然 403 |
| 错误响应导致用户**卡死**而非看到错误 | 租户被停用后用户被锁在 JSON 错误页，登录页与注销端点全部 403 |
| 启动时序 | 租户校验是 fire-and-forget，且校验请求自带失效租户头，形成鸡生蛋 |
| 跨域下响应头被浏览器过滤 | `X-Tenant-Invalid` 未 `WithExposedHeaders`，前端恒读不到 |

最后一条需要说得更准确一些：**直读 TestServer 原始响应头的断言会漏掉它**（头确实发出去了），前端单测手工构造 `HttpHeaders` 同样漏掉；但**带真实 `Origin` 并断言 `Access-Control-Expose-Headers` 的协议级集成测试可以发现**——本仓库现在就有这样一条。浏览器不可替代的地方在后半段：前端**读到**这个头、据此清掉本地租户、完成跳转的整条闭环，进程内测不到。

因此浏览器闭环的选题原则是：**只测跨进程、跨时序、跨浏览器语义的接缝**，不重复进程内已覆盖的判定矩阵。

### 已执行的闭环（2026-08-16，CORS 分离模式）

在一个由模板生成、并补上数据范围特性的验证项目上跑通，浏览器有头运行：

| # | 场景 | 结果 |
| --- | --- | --- |
| 1 | 宿主管理员经界面建租户 | 列表显示 Active——停用态创建 + 种子成功后激活的流程完整 |
| 2 | 宿主超管看订单 | 0 条：**超管旁路数据范围，但旁路不了租户硬边界** |
| 3 | 租户管理员菜单 | 无「租户管理」——宿主侧权限的侧别边界；直接敲 URL 同样 403 |
| 4 | 租户超管看订单 | 5 条全见：租户内超管旁路数据范围 |
| 5 | 经配置页给 Sales 配 `Read=Organization(org-a)` | alice 见 3 条，含**同组织但他人负责**的那条 |
| 6 | 改配 `Read=Own` | alice 见 2 条：同一页面、同一账号，仅因配置变化 |
| 7 | alice 的菜单 | 只剩 Dashboard + Orders；直接访问配置页 403 |
| 8 | 停用租户后 alice 的下一次请求 | 401 + 清空本地租户选择 + 回登录页且租户输入框复位 |

场景 8 验证的是**前端读取 → 清本地状态 → 跳转**这条完整闭环，进程内测不到。至于 `X-Tenant-Invalid` 是否被 `WithExposedHeaders` 正确暴露，协议级测试也能覆盖——只要它带真实 `Origin` 并断言 `Access-Control-Expose-Headers`；仅断言原始响应头存在则会漏掉。

### 这次跑出来的新问题

**新增业务模块时，平台入口白名单要同步改两处**，否则只拥有该模块权限的用户连控制台都进不去（父路由 `/platform` 的 `data.permissions` 与 `AuthorizationService.canAccessPlatform` 各有一份硬编码清单）。演示项目加订单模块时精确踩中：alice 拥有 `App.Orders`、后端放行，前端却在父路由把她挡在 403。

这是任何业务项目接入第一个自有模块都会遇到的，属于模板的既有形态而非缺陷——但值得在此记一笔，因为它的表现（后端通、前端拒）最容易被误判成权限没生效。
