# 撤除本服务内事件，统一异步工作的选型

状态：已完成 · 风险档：高 · 关联：#319（被本规格部分撤回）

## 1. 需求

### 问题与背景

#319 为"API 提交后由 Worker 尽快处理、事件不出服务"新增了 `IInternalDistributedEvent`（发件箱不经传输、同库直接写本服务收件箱），已合入 develop 并进入框架 beta 发布流程。复盘后用户判断：它给"服务内的异步工作"又加了一种写法，与直接调用、本地事件、后台队列、周期任务并存，场景边界变得模糊；同一需求用"业务状态 + 周期任务"就能做到，且秒级排期（`RecurringJobSchedule.Every` 最小 1 秒）已能满足"提交后尽快处理"的时效。最佳实践应是减少写法，而不是为服务内工作再造一条消息通道。

#319 的另一半——"新发件箱/收件箱行只在本进程会立即发送或处理时才留一分钟宽限"——是对既有缺陷的修复，保留。

### 目标与非目标

- 目标：
  - 删除 `IInternalDistributedEvent` 及其全部实现、测试、文档与模板引用；分布式事件回到"只用于跨服务的事实"。
  - 在框架随包文档与模板规范里给出一份唯一的选型：直接调用、`ILocalEventBus`、`IDistributedEventBus`、`IBackgroundTaskQueue`、周期任务各自何时用，以及"提交后必须完成的服务内工作"的标准写法。
- 非目标：
  - 不新增持久化作业队列，不新增"服务内消息"之类的替代机制。
  - 不改宽限期修复、不改分布式事件的其余语义。
  - 不改本地事件、后台队列、周期任务的实现。

### 选型（本规格的核心决定，写入常驻文档）

先问"能不能在请求里做完"，再按下表逐行选第一个满足的：

| # | 场景 | 用 | 失败语义 |
| --- | --- | --- | --- |
| 1 | 请求内就能做完：只动本库、或外部调用快而稳，结果要当场反馈 | **直接调用**应用服务 / 领域方法 | 失败即请求失败，用户重试 |
| 2 | 同一请求、同一进程里解耦副作用（投影、缓存、审计、通知扇出；领域事件转发为分布式事件） | **`ILocalEventBus`**（领域事件 `AddLocalEvent`） | `BeforeCommit` 处理器与业务同事务，失败整笔回滚；提交后处理器失败不回滚、不重试 |
| 3 | 别的服务或外部系统要知道这件事 | **`IDistributedEventBus`**，契约进共享包 | 发件箱 / 收件箱保证至少一次，重试、死信、重放 |
| 4 | 请求外、丢了也只是少做一次（非关键通知、预热） | **`IBackgroundTaskQueue`** | 进程退出即丢，不重试 |
| 5 | 请求外、**提交后必须完成**的本服务工作（外部筛查、激活、批量处理）；以及定期维护 | **业务状态 + `Cluster` 周期任务**：待办状态随业务事务提交；周期任务按状态扫描处理（需要尽快时把扫描排期设到秒级，例如 `Every(5 秒)`，实际开始还受锁与上一轮影响）；本库状态用条件更新推进保证幂等，涉及外部调用时带稳定的业务操作标识，让外部副作用也可安全重试；需要重试时业务表记录尝试次数与下次时间。可选：进程能执行时，提交后再用 `IBackgroundTaskQueue` 立即尝试一次，仅为降低延迟，正确性由状态与周期任务保证 | 状态即真相，任务失败下一轮补做；耗尽重试由业务状态标记，界面或运维处理 |

不做的组合：用分布式事件驱动本服务内的工作；用 `IBackgroundTaskQueue` 承载"必须完成"的工作而没有状态兜底。

周期任务放在启用了调度器的宿主上：生成项目默认只有 Api 宿主（`AddInProcessBackgroundJobs()`），周期任务就在 Api 里执行；拆分出独立 Worker 的部署由 Worker 承担需要集中执行的业务扫描任务，Api 不再运行这些任务。

### 已确认的决策

- 删除 `IInternalDistributedEvent`，不保留过渡（用户 2026-11-25）。框架公共 API 不承诺稳定，下游尚未采用；按破坏性变更标注。
- 宽限期修复保留。

## 2. 方案

### 现状事实

- 内部事件涉及的源码与测试见 #319（`git show c1aba987 --stat`）；搜索 R1 中的名字可列全。
- 订阅视图：#319 第 2 轮已恢复 `TryAddSingleton<IDistributedEventSubscriptions, DistributedEventSubscriptions>()`，接收入口与重新解码用接口 `GetAll()`；收件箱处理器与目录用 `GetAllWithInternal(接口)`，删除后改回直接用接口 `GetAll()`（即 #319 之前的基线）。
- 周期任务：`RecurringJobSchedule.Every(interval)` 最小 1 秒，按间隔排期启动后 30 秒内先执行一次（`framework/docs/components/background-jobs.md`）。

### 设计

- **代码**：删除标记接口、发布写头、派发本地分支、接收器本地入口与 `DistributedEventAcceptance` 中仅为本地入口存在的部分、三个错误码常量、`DistributedEventSubscriptions` 的内部视图与并集方法及其单独注册；收件箱处理器、目录、启动校验回到基线取法。#319 为本地入口抽出的接收器共用逻辑，若删除后只剩一个调用方，回收为基线写法，不留无用抽象。宽限期相关代码（`DistributedEventRetry.ImmediateGrace` 及两处条件）不动。
- **测试**：删除 `DistributedEventInternalDeliveryTests` 等只为内部事件存在的用例；保留宽限期用例与订阅替换用例；其余 #319 对既有用例补的断言保留。
- **文档**：
  - `framework/docs/components/event-bus.md`：删"本服务内事件"一节与"何时使用"中对应行；"何时使用"补一句"服务内的异步工作不走分布式事件，见后台作业"。
  - `framework/docs/components/background-jobs.md`："何时使用"按 §1 选型第 4、5 行写，去掉指向本服务内事件的链接；补"需要尽快处理时排期到秒级"的说明。
  - 模板 `template/docs/standards/background-jobs.md` §1：放 §1 选型表（精简为生成项目适用的写法，含第 1–5 行的判断顺序），删去条件块里的本服务内事件一行；`template/docs/standards/distributed-events.md` 删去 `IInternalDistributedEvent` 一句，开头选型句保留"能在请求内完成的直接调用"并指向后台任务规范。受读取成本闸门约束，超限在同篇去重抵消，不抬上限。
- **模板前端**：分布式事件页错误码筛选删去三个内部码。
- **规格**：`docs/specs/2026-11-25-event-bus-grace-and-internal-events.md` 填 §4（交付 #319、内部事件部分被本规格撤回），状态改为"已完成"，并在状态行注明"本服务内事件部分已废弃（被 2026-11-25-async-work-selection.md 取代）"。
- **废弃符号闸门**：把 R1 的名字登记进退役符号清单（若该闸门按清单工作），防止日后回流。

### 备选与取舍

- **保留内部事件、只在文档里降级**：写法仍在，下游仍会被"能用就用"吸引，场景继续混乱。不采用。
- **保留 #319 的订阅视图拆分**：没有内部订阅后，三视图只剩一个，拆分是无用抽象。不采用。

### 兼容与回滚

- 破坏性：删除公共类型 `IInternalDistributedEvent` 与三个错误码常量。提交标 `!` 并写 `BREAKING CHANGE:` 脚注（变化与动作：改用业务状态 + 周期任务）。下游尚未采用。
- 已写入的带 `leistd-delivery: internal` 头的发件箱行：只可能存在于试用过 #319 那个 beta 的环境（目前没有已知采用方）。删除后，待发行与被管理端按 ID 或批量重投的死信都会按普通事件交给传输，原本限于服务内的载荷可能被发出。升级前置写进规格与 `BREAKING CHANGE:` 脚注：停止发布内部事件，用仍支持内部路由的版本排空带标记的待发行，并处理或隔离带同一标记的发件箱死信（删除或改为不可重投），确保升级后无法被扫描或重投。以升级前的数据核对完成，不加运行时兼容代码，不为此加自动化用例。
- 回滚即恢复 #319 的内部事件代码。

## 4. 结果

- 撤除本服务内事件的标记、投递分支、内部订阅视图、错误码和专属测试。保留条件宽限及其 G1–G5 用例，接收、处理和目录沿用宿主订阅视图并保留替换用例。
- 模板后台任务规范收录五类场景的选型。框架随包的事件总线、后台作业和模板分布式事件规范同步当前用法。模板页面移除三个预设错误码，整个模板的退役名称及“本服务内事件”复扫为零。
- `Leistd.EventBus.Tests` 在 Release 构建后运行整个项目，199/210 通过、0 失败，11 项真实 RabbitMQ/Kafka 契约交由配备 broker 的 CI 执行。82 个候选包打包成功，三个 event-bus 包的隔离消费、14 道定向静态闸门通过。
- 生成项目的前端 lint 与分布式事件 spec 随 PR 同候选 CI 验收。试用环境的旧发件箱记录由升级前的数据核对验收，升级动作随破坏性变更脚注交付。
