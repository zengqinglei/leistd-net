出站 Webhook 组件 · 详细设计方案

业务在工作单元内发布事件，框架负责可靠投递、签名、重试、停用与投递记录；模板用 IncludeWebhooks 整体裁剪后台管理页、权限、迁移与文档。

风险档：高 Framework：Leistd.Webhooks.Core / .EntityFrameworkCore / .AspNetCore Template：IncludeWebhooks（默认 false） 签名：Standard Webhooks v1 语义：至少一次，不保证顺序 UI：方案 A+

1背景

业务项目要把自己的业务事件推给第三方系统（例如"订单已付款时通知客户的 ERP"）。业界的出站 webhook 做法已经高度一致，适合由框架提前提供，交给业务项目使用后再按反馈改进（2026-11-03 立项）。

签名有事实标准

Standard Webhooks：webhook-id、webhook-timestamp、webhook-signature；HMAC-SHA256；OpenAI、Anthropic、Twilio 兼容。

管线各家一致

发件箱 → 每个"事件 × 端点"一条投递记录 → 工作者发送 → 记录尝试 → 退避重试 → 自动停用。（Svix、Stripe、Boilerplate webhooks）

运维能力是标配

投递日志、手动重发、测试事件、密钥轮换期双签。（Stripe、GitHub、Svix、Gitea）

入站接收不做通用组件

微软 ASP.NET WebHooks 按服务商逐家做接收器，先归档、2023 年又被删除；各服务商都有官方 SDK。

主流做法对照

维度StripeGitHubSvix（开源）Boilerplate webhooks本方案
签名Stripe-Signature 含时间戳X-Hub-Signature-256Standard Webhooks只签请求体，不含时间戳Standard Webhooks v1
重试3 天指数退避不自动重试，可手动重投7 次，约 27 小时后台作业，最多 5 次7 次，约 27 小时（同 Svix）
自动停用有—连续失败 120 小时默认关闭连续失败 5 天，默认开启
内网拦截托管服务自带托管服务自带默认屏蔽私网无连接时检查 IP，可放行白名单
投递日志 / 重发控制台 15 天3 天内可重投有有记录，无界面后台页面，保留 62 天

2现状问题

框架没有出站 webhook 能力，业务项目只能各写一套：签名格式各不相同，重试不持久，失败不可见，也不拦截内网地址。

现状事实对 webhook 的影响
事件总线只做进程内同步分发，不持久（framework/docs/components/event-bus.md）进程重启就丢事件
后台作业队列不持久；文档写明"必须完成、失败要重试的作业不用本组件的队列"不能直接拿来做跨天重试
Outbox工作单元多处让跨系统副作用"走 Outbox"，但框架里没有事件与业务不能原子提交
出站 HTTPservice-client 面向内部服务调用：机器身份、令牌交换、错误还原没有签名、投递记录与内网拦截
后台管理没有订阅登记、密钥管理和投递日志的界面与权限失败只能查日志，不能重发
可以复用的基础已经齐了：集群周期任务（分布式锁保证单副本运行）、带租户上下文的进程内队列、提交后分发的本地事件、Data Protection、按租户库执行的 ITenantDatabaseRunner、持久化组件的纵向切片约定。不需要先造通用 Outbox。

3核心策略

事件表本身就是发件箱；提交后立即投递保证及时，集群扫描兜底保证不丢；接收方按 webhook-id 去重，框架不为极少数重复发送加抢占机制。

3.1 投递链路

① 发布
业务事务内
用例或 BeforeCommit 处理器调 IWebhookPublisher；载荷冻结为 JSON；为匹配的订阅写投递记录（NextAttemptAt = 现在 + 1 分钟宽限）
② 提交
同一事务
业务回滚则事件一起回滚；提交即持久
③ 立即投递
进程内队列
提交后入队，带租户上下文；毫秒级首发；丢了交给 ④
④ 兜底扫描
集群任务 · 10 秒
逐个物理库放开租户过滤取到期记录，按记录切租户处理；负责重试与崩溃恢复
⑤ 发送
签名 + POST
Standard Webhooks 三个头；超时 15 秒；不跟随重定向；连接时检查 IP
⑥ 第三方
接收方
验签 → 按 id 去重 → 15 秒内回 2xx → 异步处理
结果处理（按序）：2xx 成功并清零失败起点 · 410 停用订阅 · 手动尝试失败即终态 · 自动尝试按退避表 5s 5m 30m 2h 5h 10h 10h（带 Retry-After 取较大值），预算用完即失败 · 连续失败 5 天自动停用并发 WebhookSubscriptionDisabledEvent

3.2 包与分层

Leistd.Webhooks.Core

  • Definitions/ 事件类型声明
  • Publishing/ 发布入口与信封
  • Delivery/ 发送器（唯一替换点）、内网拦截、退避与结果分类
  • Signing/ Standard Webhooks v1，轮换期双签
  • Management/ 管理用例与 DTO
  • Events/ 自动停用事件
  • Options/ Errors/ Resources/

Leistd.Webhooks.EntityFrameworkCore

  • 四张表：订阅、事件、投递、尝试
  • 提交后立即投递
  • 集群任务 webhooks.dispatch
  • 保留期任务 webhooks.retention（默认 62 天）

Leistd.Webhooks.AspNetCore

  • MapWebhooks(options)：ReadPolicy / ManagePolicy 必填
  • 订阅增删改、启停、轮换密钥、测试事件
  • 投递日志分页、详情、重发

不另建签名包、入站接收包，也不建防内网访问的 HTTP 包：这几块各只有一个调用点。HTTP 发送用 BCL 与 IHttpClientFactory，Core 仍只依赖抽象；不挂 Polly 重试，因为重试是持久的、按计划执行的。

3.3 可靠性、及时性与幂等

关注点做法刻意不做
不丢事件与投递记录写进业务 DbContext，与业务同一事务提交通用 Outbox、消息中间件
及时提交后立即入进程内队列发送；兜底最迟延迟 = 1 分钟宽限 + 10 秒扫描间隔—
重试持久的退避表，±10% 抖动；尊重 Retry-After；退避表用完标记失败，可手动重发HTTP 层 Polly 重试
并发扫描是集群任务，同时只有一个副本在跑；立即投递与扫描之间靠 1 分钟宽限期错开行级租约、乐观并发抢占
多租户按物理库进入后放开租户过滤取到期记录，每条在所属租户上下文与独立工作单元里处理；某库失败则本轮记失败—
停用停用时把该订阅待投递记录同事务改为失败；两个发送入口发请求前都检查订阅状态；重新启用可一并重发该订阅现存的全部失败投递补发停用期间的事件
手动重发只对终态开放；触发来源 NextTrigger 与排期同事务持久化，扫描恢复也记为手动；只发一次，失败（含带 Retry-After 的 429/503）即终态，不重开自动退避—
发布入口必须在活动工作单元内调用，否则抛异常；在事件处理器里发布须声明 BeforeCommit自开事务
幂等webhook-id = 事件 id，重试与手动重发都不变；接收方按它去重发布侧幂等键
顺序不保证；载荷带 timestamp，接收方按时间或回查 API 处理按订阅串行投递
安全签名带时间戳；密钥用 Data Protection 加密、只显示一次；连接时检查一次目标 IPDNS 重绑定防护、出站代理、ed25519

3.5 模板条件裁剪：IncludeWebhooks

webhook 是可以独立取舍的产品边界，按模板开发规范定为布尔参数，默认 false，适用于全部 ServiceRole；Resource 无前端时只生成后端。

层为 true 时生成为 false 时须无残留
Application本地身份：WebhookDefinitionProvider 声明 user.created，在用户创建用例的同一工作单元内发布；Resource 不声明示例事件。统计用例与抽出的共享区间换算目录、发布调用
ApiAddWebhooks；ComponentEndpoints 映射 webhooks；权限 App.Webhooks / .Manage（开发者组）；写操作记录；开发环境放行回环包引用、权限、端点、配置节
InfrastructureConfigureWebhooks()；EF 存储与保留期；Identity / Resource 增量迁移 AddWebhooks（整文件守卫，并在生成排除中登记）表、迁移、快照块
前端platform/webhooks 页面、开发者组菜单（组条件改为 OpenIddictServer || IncludeWebhooks）、权限常量、DTO、服务、词条、Mock、spec路由、菜单、词条键
文档与 Skill生成项目 docs/standards/webhooks.md（发布方写法 + 接收方接入指南）；读取清单与项目 Skill 加入口文档与链接
代价：有效形态从 320 组翻倍到 640 组，生成检查四个分片的耗时随之增加；矩阵新增 webhooks（core 档）与 resource-api-webhooks（full 档）两个场景。不和其他参数交叉组合（不桥接通知），所以不新增有效能力表达式。

3.6 端到端：从框架到第三方

角色要做的事
框架提供发布入口、投递管线、管理端点与组件文档；默认值可直接上线
业务项目引用引用三个包 → AddWebhooks() + AddWebhooksEfCore<TDbContext>() + AddWebhookRetention<TDbContext>() → modelBuilder.ConfigureWebhooks() → 生成迁移 → MapWebhooks(o => { o.ReadPolicy = …; o.ManagePolicy = …; })。用模板生成时勾选 IncludeWebhooks 即可

方案 A+ · 单页双视图 + 统计卡

已选定

以方案 A 为基础，投递详情改用方案 C 的抽屉：一个菜单入口，分段控件在"订阅"与"投递日志"间切换，视图与筛选记在 URL query。顶部加一行仪表盘同款统计卡（吸收方案 B），订阅表加"近 7 天成功率"列，并提供一步跳转到带筛选的投递日志（吸收方案 C）。

吸收的优点在 A+ 里的做法依据 / 代价
B · 聚合统计四张 app-stat-panel：成功率、投递数、失败（附重试中条数）、已停用订阅；前三张带环比徽章与迷你趋势；区间 今天 / 7 天 / 30 天仪表盘 KPI 卡同一组件与写法；组件只按 UTC 桶计数，日历区间由模板统计端点换算（同平台统计）
B · 单订阅健康度订阅表"近 7 天成功率"列（进度条 + 百分比）；投递日志按订阅筛选时，统计卡只统计该订阅不新增详情路由；列表查询多一次按订阅分组计数
C · 一步跳转点"最近投递"徽章或 … 菜单"查看投递"→ 投递日志带订阅筛选；点"失败"卡 → 投递日志筛选失败只改 URL query，复用同一页面状态
C · 抽屉（投递详情）投递日志不做行展开，右侧抽屉从上到下：概要 → 请求（头 + 体）→ 调用记录；每次尝试保存实际发出的头部快照（不含签名）详情长、需纵向铺排；Stripe、Svix 同样用侧边面板。订阅表详情短，仍用行展开
仪表盘 · 需要关注已停用订阅卡带"需要关注"徽章；区间摘要写"N 个订阅需要关注"与仪表盘摘要行同一写法
