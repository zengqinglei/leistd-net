外壳导航重组与系统切换：一个控件只管一件事

六条反馈全部采纳，系统切换这次一起做。品牌块切换系统，系统列表直接取自 Identity 的开放应用登记，不另建系统目录。侧栏顶部是可搜索的租户选择，底部是平台控制台入口，头像移到右上角。分布式事件页把"选库"改成"选租户"。工作空间面向客户，界面上不出现租户。

你的目的：品牌块上叠了三件事（工作区、平台控制台、工作空间/管理平台），用户要先读懂"区域"和"工作区"的区别才能用。拆开以后，层级从上到下就是 系统 → 租户 → 菜单，每个控件只回答一个问题。业务三仓的外壳已经验证过这套分工，模板跟进后，下游同步时也少一处分叉。

系统切换：复用开放应用登记，不另建目录

业务 Identity 有一套独立的"系统入口"：代码登记系统键，部署时写入地址，按租户开通，再从地址派生第一方客户端的登录回调。它解决了业务仓的两个特有需求：每个租户可以有自己的子域地址，每个系统按租户开通。模板没有这两个需求，而"系统"本来就是在开放应用里登记过的浏览器客户端。所以终局是让开放应用登记直接成为系统目录，一处登记，同时得到登录接入和导航切换。

分布式事件

选租户，不选库；租户范围里不用选

已核对框架实现：页面上的"宿主"指共享业务库，宿主在这里能看到共享库中所有租户的事件；其余选项是独立租户库。用户真正要选的是"谁的事件"，不是"哪个物理库"。

  • 租户范围（工作区或租户账号）：没有筛选，后端按当前租户自动定位到它的库
  • 平台控制台：库选择换成可搜索的"租户"筛选，默认"全部"。选中某个租户时，后端自动找到它的库（共享库或独立库）并过滤；"全部"由后端按时间合并各库的结果，独立库一般很少
  • "发送测试事件""拒收记录"这些仅宿主可用的操作不变

这要改框架组件的管理接口：参数从库键改为租户，属于框架改动，会随 develop 发 beta。

工作空间（业务区）

面向客户，界面上不出现租户

工作空间给最终用户使用。租户由访问域名、邮箱域名或登录页的选择确定，登录后由会话固定。平台人员从管理平台进入时，地址里已经带着 /w/租户，是明确的。所以工作空间里既没有租户切换，也没有租户标识，客户和平台人员看到的顶栏完全一样。平台人员需要知道自己代表哪个租户在操作，这一点放在头像菜单顶部，写成"staff-a · 代表 tenant-a"；换租户回管理平台去做。
