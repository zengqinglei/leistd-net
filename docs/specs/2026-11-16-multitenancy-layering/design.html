多租户分层 · 详细设计方案

宿主只做控制面，租户承载业务。默认形态保留模拟登录并修复其缺陷；可选的工作区形态（--TenantStaffAccess Workspace）让平台人员以本人账号经授予进入多个租户，同一个会话按请求选定工作区，切换不重新登录、不整页刷新，覆盖单服务与 Identity + Resource 跨服务调用。开多租户的产品，私有化就是只有一个默认租户的 SaaS。

风险档：高交付面：模板（不改框架包）生成参数 TenantStaffAccess两个 PR、依次交付规格：docs/specs/2026-11-16-multitenancy-layering.md

1背景及目标

"用户只属于一个租户、宿主人员用模拟登录排障"仍是多数通用项目的合理默认。本需求修两处所有项目都受影响的缺口，并新增一个可选形态，服务"平台运营团队常驻多个租户、SaaS 与私有化同一套代码"的产品。

现状问题

编号问题性质影响面
Q1没写明宿主只做控制面、业务权限侧别规则与私有化形态指引文档缺口全部多租户项目
Q2模拟登录写死用户名 admin，改名或删除后失败设计缺陷全部多租户项目
Q3平台人员只能模拟成租户 admin（全权、非本人），一个会话一个租户，换租户整页跳转场景缺口有平台运营团队的产品
Q4多租户产品私有化只能关闭多租户，与 SaaS 两套路径场景缺口SaaS + 私有化的产品

目标与非目标

目标说明
G1 分层与指引三层划分、侧别规则、私有化形态选择（全部项目）
G2 修模拟登录按内置 Admin 角色选目标，不依赖用户名（默认形态）
G3 工作区形态本人登录、经授予按请求进入多个租户；含 Resource 与跨服务调用，一次做完
G4 默认租户私有化配置一个默认租户，首次启动即可用

非目标：多服务授权编排（模板无服务目录）、客服代入、改框架包、改"关闭多租户"形态。

2核心策略

一条主线：会话只认本人，租户按请求选定，只在工作区认证方案这一个入口校验；入口之后的租户解析、连库、权限判定沿用现有链路。工作区是可选形态，由生成参数决定。

2.0 按场景选择生成参数

应用场景生成参数宿主人员怎么进租户
单客户系统、内部系统--IncludeMultiTenancy false没有租户
多租户 SaaS，平台只管租户、偶尔排障默认（TenantStaffAccess=Impersonation）模拟登录（已修 Q2）
SaaS 与私有化同一套代码，平台团队常驻多个租户--TenantStaffAccess Workspace本人登录，按请求进入多个租户，多标签页互不影响
上述任一的私有化部署不加参数，配置 MultiTenancy:DefaultTenant首次启动建默认租户

参数只在开多租户时有效；同一系统里的 Identity 与各 Resource 取同一个值。纯 API 的 Resource 不需要工作区方案：调用方直接持有对应租户的令牌。矩阵为工作区形态登记 Standalone、Identity、Resource 浏览器会话三个代表场景。

2.1 三层划分

层承载不承载权限侧别前端区（工作区形态）
宿主 · 控制面租户开通与连接、平台人员与授予、开放应用、进程级设置、跨库运维业务数据、业务菜单Host；Both 的宿主部分/platform/**
租户 · 工作区全部业务数据与功能；本租户成员、角色、设置、操作记录其他租户的数据业务 Tenant；成员、角色等 Both/w/:workspace/**（租户用户与平台人员相同）
平台人员 · 桥梁一个本人账号，经授予进入多个租户不代入租户里的现有用户—工作区切换器
侧别规则：开多租户时业务权限默认 Tenant；关闭多租户时只有宿主作用域，业务权限用 Both（框架无租户上下文即判为 Host，DefaultPermissionChecker.cs:33）。两侧都有的页面是同一组件，数据范围由请求作用的工作区决定。

2.2 本人账号与关联账号

本人账号

宿主用户（TenantId 为空）。口令、两步验证、通行密钥、确认身份与会话策略都只在这里。

关联账号

租户内的普通 User 行，多一个 HomeUserId；用户名 platform.<本人用户名>，邮箱空串。领域禁止它持有任何凭据。角色与启停只看它。

访问索引

UserTenantAccess(HomeUserId, TenantId, CreationTime)，放在控制库（与租户注册表同库、固定连接），不映射进租户上下文。

规则做法为什么这样够
关联账号不能直接登录User 聚合拒绝为关联账号设置口令、邮箱、外部登录、通行密钥没有凭据，各登录入口与找回密码天然失败；GetAccessStatus 不改，主体工厂可直接复用
授予、移除、再次授予授予先建或恢复关联账号与角色，后写索引；移除先删索引，后软删除；再次授予恢复同一 Id中间失败只留孤儿行；入口同时要求索引、关联账号存在且启用
审计操作人 = 关联账号（显示名同本人），记录落在租户沿用操作记录组件的 ActorTenantId 语义，框架不改

为什么要替换策略里的方案：默认策略与 App.CurrentUser 显式指定了方案，授权阶段会按它重新认证并覆盖主体（DependencyInjection.cs:63-107）。只改默认方案会让授权后的主体变回本人。Workspace 内部先认证原方案：Identity/Resource 为 Smart，Standalone 为 SessionCookie；机器策略与协议端点不变。
请求结果
不带头；或 /api/v1/auth/**、/api/v1/external-auth/**、/connect/**本人主体
租户用户带自己的租户名本人主体
租户用户带别家租户名403 Workspace:Forbidden
宿主用户带头，索引在、租户启用、关联账号启用换成关联账号
宿主用户带头，任一条件不满足403 Workspace:Unavailable（不回退本人；前端刷新列表并退到下一个工作区）
形态换主体的方式
Standalone、Identity进程内：主体工厂"按本人进入工作区建主体"，在目标租户上下文与新工作单元内建关联主体
Resource 浏览器会话调 Identity"进入工作区"交换；按（服务端票据键, 租户）节点内缓存，期限取 4 分钟与令牌剩余寿命的较小值；票据保存 access_token 与到期时间
Resource 纯 API不读这个头

令牌交换：一处判定，三处复用

用途输入输出与规则
进程内（Standalone/Identity）本人 Cookie 主体 + 目标租户本请求的关联主体
进入工作区（新分支，Resource 用）本人访问令牌 + workspace 参数sub = 关联账号、tenant_id、home_sub；受众同输入；不加 act（本人选择范围，不消耗单跳）；无刷新令牌；寿命 = min(5 分钟, 输入剩余寿命)；拒绝 invalid_target
现有下游交换遇到工作区令牌带 home_sub 的令牌本人账号按 home_sub 在宿主校验、关联账号在租户校验后重建主体；照常加 act、单跳、受众与资源归属检查

会话语义沿用现有边界：进程内由内层 Cookie 校验本人的具体会话；交换路径只校验输入令牌、本人账号、索引、租户与关联账号，不按 home_sub 校验具体会话；会话结束阻止后续刷新，已签发的令牌用到其到期为止。

工作区列表 GET /api/v1/auth/me/workspaces 只按本人返回：Identity/Standalone 读索引；Resource 经应用层端口 + ServiceClient 回源 Identity：沿用账户偏好客户端，用本人令牌做现有交换取得 Identity 受众令牌（不经 Workspace 方案，避免循环）。

刻意不做：同键并发交换去重、授予与移除的一致性补偿、撤销时清缓存事件。撤销时效：Standalone/Identity 下一个请求生效；Resource 最迟 5 分钟。

2.4 前端路由与切换

主题约定
路由工作区形态下 /platform/** 只表示宿主控制面；所有租户内页面（含租户用户自己的）都在 /w/:workspace/**，复用现有子路由（/w/acme/platform/users）。租户用户打开 /platform/** 时转到自己的工作区；链接可在租户管理员与平台人员之间分享
请求范围默认取当前路由的工作区；/platform 与本人账户请求标为本人
状态顺序导航开始时确立目标工作区，守卫判定前加载其权限与设置；切换完成时提交，迟到响应丢弃（复用 SessionContextService 与 SignalR 的代次）
主体AuthService.currentUser 只表示本人；业务订阅、本人行判断、租户资源键取工作区主体
切换只做路由跳转；父组件按工作区键重建子路由出口；不新增离页确认
落点上次的工作区（localStorage 只存"上次"），失效取第一个，没有时 /platform
实时连接平台人员在工作区内两条：本人连接常驻（宿主通知不丢），工作区连接随切换重建；其他情况一条。通知中心按当前范围显示

2.5 默认形态修复与私有化

修模拟登录（默认形态）

  • 目标改为"该租户持有内置 Admin 角色、已启用的用户，按创建时间取第一个"，不再按用户名查找。
  • 工作区形态不生成模拟登录；历史动作码与词条保留，旧记录照常显示。

默认租户（两种形态都可用）

  • 配置 MultiTenancy:DefaultTenant（Name、DisplayName）。
  • 只在 Standalone/Identity 执行；API 启动时 SystemInitializer 在初始化锁内、默认管理员就绪后执行：无任何租户时建默认租户；工作区形态下再给默认宿主管理员建 Admin 关联账号与索引，不另建带口令的本地 admin。
  • 登录页不预选默认租户：认证所在租户与登录后落入的工作区分开。

2.6 备选与取舍

备选不选的原因
工作区形态设为默认多数通用项目不需要，会让每个多租户项目承担工作区与跨服务交换的复杂度
全局用户 + 成员关系模板用户按租户隔离，独立库租户的用户在自己的库里，要重做隔离
会话里记"当前租户"，切换时换 Cookie一个会话只能停在一个租户，多标签页互相影响
只有平台人员走 /w，租户用户沿用原路径同一地址对宿主与租户含义不同、链接不能分享、要两套挂载；工作区形态是新形态，没有存量深链负担
工作区内只保持一条实时连接进入工作区期间收不到宿主通知
访问令牌加 sid；进入工作区令牌固定 5 分钟改变现有令牌契约；派生令牌不应比本人令牌活得久
各登录入口判定"关联账号不可登录"入口多易漏，还与复用主体工厂冲突；领域禁止持有凭据，一处即可
默认租户放在 DbMigratorDbMigrator 没有账号初始化链；SystemInitializer 已持锁且默认管理员已就绪
Resource 分两期用户决定一次做完；跨服务与单服务共用一处主体判定，一起设计更一致

4实施计划

分两个 PR 依次交付，不改框架包。PR1 先交付分层与侧别规则、私有化形态指引和 WP2 模拟登录修复，按本地验证配方验证后合入 develop；PR2 从合入后的 develop 实施工作区参数与 WP3–WP7，再集中验证。每个 PR 内工作包按依赖顺序实施，审查修复后只重跑受影响项。

为什么一轮够

  1. PR1 先交付现有形态的必做层；PR2 的工作区形态一次实施、集中验证。
  2. 开发期只跑目标测试类与目标 spec，每个工作包一个提交。
  3. 越权集中在 Workspace 一个入口的矩阵测试类，不按端点逐个写。
  4. 修复只重跑失败点和直接受影响的检查（quality-assurance.md"证据复用"）。

刻意不做

  • 不为并发交换、授予与移除中间态加锁或补偿；不做撤销即时失效事件。
  • 不在端点或应用服务里再判断租户。
  • 不做"以人为中心"的第二个管理入口、服务目录与授权编排。
  • 本地不跑 core / full 档矩阵。
