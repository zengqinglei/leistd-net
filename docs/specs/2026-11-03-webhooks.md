## 1. 需求

### 问题与背景

业务项目需要把自己的业务事件推给第三方系统（"订单已付款时通知客户的 ERP"），这就是出站 webhook。框架目前没有这项能力：

- 事件总线只做进程内同步分发，不持久（`framework/docs/components/event-bus.md`）。
- 后台作业的队列不持久，文档明确写着"必须完成、失败要重试的作业不用本组件的队列"（`framework/docs/components/background-jobs.md`）。
- 工作单元的注释和文档多处让跨系统副作用"走 Outbox"，但框架里没有 Outbox（`framework/components/unit-of-work/Leistd.UnitOfWork.Core/Events/UnitOfWorkPhase.cs`）。
- `service-client` 面向内部服务调用（机器身份、令牌交换、远程错误还原），没有签名、持久重试和投递记录。

业务项目只能各写一套：签名格式各不相同，重试不持久，失败不可见，也不拦截内网地址。

2026-11-03 用户决定先立项：框架在设计上提前提供这项能力，交给业务项目使用后再按反馈改进。

### 业界做法（调研结论）

出站 webhook 的投递管线各家高度一致，可以抽象；入站接收方没有通用价值。

| 方面 | 业界共识 | 依据 |
| --- | --- | --- |
| 签名 | Standard Webhooks：`webhook-id` / `webhook-timestamp` / `webhook-signature`，HMAC-SHA256 签 `id.timestamp.body`，密钥前缀 `whsec_`，轮换期新旧密钥各签一份 | standardwebhooks.com；OpenAI、Anthropic、Twilio 兼容 |
| 可靠性 | 事件与业务同事务落库（发件箱）→ 为每个"事件 × 端点"写一条投递记录 → 工作者发送 → 记录每次尝试 | Svix、ASP.NET Boilerplate webhook 模块、MassTransit outbox |
| 重试 | 按天级指数退避；3xx 算失败且不跟随跳转；410 表示停用端点；429 遵守 `Retry-After` | Stripe 3 天，Svix 约 27 小时，Standard Webhooks 规范 |
| 至少一次 | 不保证顺序，也不保证恰好一次；接收方按 `webhook-id` 去重；手动重发沿用原 id | Stripe、Shopify、GitHub |
| 运维 | 投递日志、手动重发、端点持续失败自动停用、测试事件 | Stripe、GitHub、Svix、Gitea |
| 入站接收组件 | 微软 ASP.NET WebHooks 按服务商逐家做接收器，先归档、2023 年又被删除；各服务商都有官方 SDK | aspnet/AspLabs PR #591 |

ASP.NET Boilerplate 的后继框架（开源版与商业版）至今没有 webhook 模块，相关需求从 2020 年起一直在 backlog。ASP.NET Boilerplate 自带的 webhook 模块分层可以借鉴，但它的签名不含时间戳，没有任何内网地址拦截，自动停用默认关闭。

### 目标

- 业务在工作单元内发布事件，事件与业务数据一起提交。业务回滚时事件也回滚，提交后不丢失。
- 订阅方按事件类型订阅。请求按 Standard Webhooks 签名，接收方用任何语言的现成库都能验签。
- 正常情况下提交后立即发出。失败按退避表持久重试；进程崩溃后由兜底扫描恢复。
- 管理员在后台管理订阅（地址、事件、请求头、启停、密钥轮换、测试），并查看投递日志、手动重发。
- 模板用条件参数 `IncludeWebhooks` 整体裁剪这项能力。

### 非目标

| 不做 | 原因 |
| --- | --- |
| 入站 webhook 接收组件 | 各服务商的签名与握手方式各不相同，官方 SDK 已覆盖；微软的通用接收器已弃用 |
| 第三方经 API 自助订阅（Stripe / Graph 式） | 首版只做管理员登记。管理服务不排斥以后加机器端点，有反馈时再做 |
| 恰好一次、按顺序投递 | 业界都不保证；接收方去重和回查即可 |
| 投递记录的租约、乐观并发抢占 | 兜底扫描是集群任务，同时只有一个副本在跑；偶发的重复发送由接收方按 `webhook-id` 去重 |
| DNS 重绑定、出站代理、CloudEvents 握手、ed25519 | 不过度防御；连接时检查一次 IP 即可 |
| 设置页可配置项 | 退避、超时、内网白名单属于协议参数与信任边界，归部署配置（`framework/docs/components/settings.md` 的划界） |
| 自动停用后发站内通知 | 组件发本地事件，由业务决定是否通知；模板不跨参数组合 |
| 载荷变换、按内容路由、每端点限流、客户门户 | 强业务相关 |

### 非功能要求

- 克隆即可运行：开发环境放行回环地址，本机接收端不被内网拦截挡住；被拦截时报错写明配置键 `Leistd:Webhooks:AllowedNetworks`。
- 默认值可直接上线：退避表、超时、自动停用和保留期都有默认值，必填项只有授权策略名。
- 首发延迟：正常路径在提交后立即发送；兜底路径最迟一个扫描间隔加宽限期。

### 包与目录

```
framework/components/webhooks/
├─ Leistd.Webhooks.Core
│  ├─ Definitions/      IWebhookDefinitionProvider、WebhookDefinition
│  ├─ Publishing/       IWebhookPublisher、事件信封
│  ├─ Delivery/         IWebhookSender（唯一替换点）、默认 HTTP 发送器、内网拦截、退避与结果分类
│  ├─ Signing/          Standard Webhooks v1 签名、签名密钥的 Data Protection 加密
│  ├─ Management/       IWebhookManagementService 与管理用例实现（internal：校验、启停、密钥轮换、重发判定、变更事件）、停用原因
│  ├─ Dtos/             管理端点的输入与输出 DTO
│  ├─ Stores/           IWebhookDeliveryReader（统计读取）、管理用例的存储契约（internal）
│  ├─ Events/           WebhookSubscriptionChangedEvent
│  ├─ Options/  Errors/  ExceptionMappings/  Resources/
├─ Leistd.Webhooks.EntityFrameworkCore
│  ├─ Entities/  EntityConfigurations/
│  ├─ Stores/           统计读取与管理存储的实现（查询、持久化、删除连带）
│  ├─ Subscriptions/    停用时终结待投递
│  ├─ Dispatching/      提交后立即投递、兜底扫描任务 webhooks.dispatch
│  └─ Retention/        保留期任务 webhooks.retention
└─ Leistd.Webhooks.AspNetCore
   └─ Endpoints/        MapWebhooks
```

- HTTP 发送放在 Core：`HttpClient`、`SocketsHttpHandler` 属于 BCL，`IHttpClientFactory` 属于 `Microsoft.Extensions.Http`，不违反"Core 只依赖抽象"。
- 不复用 `service-client`，语义不同。不挂 Polly 重试：重试是持久的、按计划执行的，HTTP 层只设超时。
- 签名、内网拦截各只有一个调用点，不单独建包（`docs/architecture/design-principles.md#5-变更取舍原则` 第 3 条）。

### 公共 API

| 入口 | 包 | 说明 |
| --- | --- | --- |
| `IWebhookDefinitionProvider` | Core | 业务声明事件类型（名称、分组、说明词条）；发布未声明的类型时抛出 |
| `IWebhookPublisher.PublishAsync(eventType, data, ct)` | Core | 业务唯一入口；在当前工作单元内写事件与投递记录。没有活动工作单元时抛 `InvalidOperationException`，不自开事务冒充业务事务；在事件处理器里调用时，处理器须声明 `[UnitOfWorkEventHandler(UnitOfWorkPhase.BeforeCommit)]` |
| `IWebhookSender` | Core | 替换点：默认 HTTP 发送；可替换为 Svix 等托管服务 |
| `AddWebhooks(configure?, configSectionPath = "Leistd:Webhooks")` | Core | 选项绑定 + `ValidateOnStart`；登记错误码与默认 HTTP 状态 |
| `AddWebhooksEfCore<TDbContext>()`、`modelBuilder.ConfigureWebhooks()` | EF | 存储、提交后立即投递、登记集群任务 `webhooks.dispatch` |
| `AddWebhookRetention<TDbContext>(configure?, configSectionPath)` | EF | 保留期任务，默认开启 |
| `MapWebhooks(options)` | AspNetCore | `ReadPolicy`、`ManagePolicy` 必填，端点名前缀 `Leistd.Webhooks.` |

| `WebhookSubscriptionChangedEvent` | Core | 订阅创建、修改、轮换密钥、启用、停用、删除后经可选 `ILocalEventBus` 发布，提交后分发、回滚不分发；带变更类别 `WebhookSubscriptionChangeKind`（`Created`、`SecretRotated`、`Enabled`、`Disabled`、`Deleted`、`Updated`）与停用原因（手动或投递链路的自动停用）。形态照 `TenantChangedEvent`（一个事件带变更类别），宿主据此留痕或通知管理员 |

| `IWebhookDeliveryReader.GetSnapshotAsync(subscriptionId?, ct)` | Core（EF 实现） | 当前重试中的投递数、已停用的订阅数（存量，不随区间变化） |

### 数据模型

| 表 | 关键字段 |
| --- | --- |
| `WebhookSubscription` | `TenantId`、`Name`、`Description`（可选，对接说明）、`Url`、`EventTypes`（`["*"]` 表示全部事件）、`Headers`、`Secret`（Data Protection 密文）、`PreviousSecret` 与 `PreviousSecretExpiresAt`、`IsEnabled`、`DisabledReason`（手动 / 端点已注销 / 连续失败）、`DisabledAt`、`FirstFailureAt`、审计字段 |
| `WebhookEvent` | `Id`（即 `webhook-id`）、`TenantId`、`Type`、`Payload`（发布时冻结的 JSON）、`OccurredAt` |
| `WebhookDelivery` | `EventId`、`SubscriptionId`、`Status`（待投递 / 成功 / 失败）、`NextTrigger`（自动 / 手动，下一次尝试的来源，与排期同事务保存）、`AttemptCount`（累计）、`AutoAttemptCount`（本轮自动尝试数，决定退避表下标）、`NextAttemptAt`、`LastStatusCode`、`LastError`、`LastAttemptAt`、`CreationTime` |
| `WebhookAttempt` | `DeliveryId`、`AttemptedAt`、`Trigger`（自动 / 手动）、`RequestHeaders`（本次实际发出的头部快照，不含 `webhook-signature`）、`StatusCode`、`DurationMs`、`Response`（截断到 1 KB）、`Error` |

表名沿用 EF Core 默认约定。订阅、事件、投递实现 `IMultiTenant`。删除订阅时一并删除它的投递与尝试，它们随之退出统计。

### 投递链路

1. **发布**：`PublishAsync` 校验类型已声明，序列化载荷，信封为 `{type, timestamp, data}`；按类型匹配本租户的启用订阅，写一条事件和 N 条投递记录。新记录的 `NextAttemptAt = 现在 + 1 分钟`，这是留给立即投递的宽限期。
2. **立即投递**：工作单元提交后，把本次的投递 id 送进进程内队列（`IBackgroundTaskQueue`，带租户上下文）。发送成功就标记成功；失败就按退避表写下一次时刻。队列满或进程退出时不处理，交给兜底。
3. **兜底扫描**：集群周期任务 `webhooks.dispatch`，默认每 10 秒运行一次。按物理库逐个（`ITenantDatabaseRunner`）进入，库内放开租户过滤（`IgnoreQueryFilters`，同通知保留期），取 `Status = 待投递 且 NextAttemptAt ≤ 现在` 的记录及其 `TenantId`；每条记录在所属租户的上下文（`ICurrentTenant.Change`）和独立工作单元里处理，有界并发发送。某个库失败时记日志、继续其余库，本轮结束后抛出汇总异常，让任务记为失败而不是成功。分布式锁保证同时只有一个副本在扫，不另做行级抢占。管理查询照常按租户隔离。
4. **发送**：两个入口（立即投递与兜底扫描）发请求前都重新读取订阅；订阅已停用或已删除时不发请求，按下文"停用的作用"终结这条投递。重新解密密钥并签名，POST，超时 15 秒，不跟随重定向。`SocketsHttpHandler.ConnectCallback` 在连接时检查目标 IP，私网、回环、链路本地地址不在 `AllowedNetworks` 内就拒绝连接。这是内网拦截唯一的检查点；新建订阅时只校验地址是绝对 http(s) URL。每次尝试记录实际发出的头部快照（不含签名）。
5. **结果**：

   按顺序判断，命中即停：

   | 顺序 | 条件 | 处理 |
   | --- | --- | --- |
   | 1 | 2xx | 成功，清零订阅的 `FirstFailureAt` |
   | 2 | 410 | 投递失败，订阅停用（端点已注销） |
   | 3 | 其余失败（含 429、503、3xx、超时、连接失败），且本次是手动尝试 | 直接失败，不排自动重试 |
   | 4 | 其余失败，自动尝试，`AutoAttemptCount` 已用完退避表 | 失败 |
   | 5 | 其余失败，自动尝试，还有重试预算 | 按 `AutoAttemptCount` 取退避间隔；响应带 `Retry-After` 时取两者中较大的值，排下一次 |

   每次失败后检查订阅：`FirstFailureAt` 距今超过 `AutoDisableAfter` 就停用（连续失败）。
6. **手动重发**：只对终态（成功或失败）的投递开放，重试中的投递按钮置灰并提示下次时刻。重发与排期同事务保存：`Status = 待投递`、`NextTrigger = 手动`、`NextAttemptAt = 现在`，提交后立即入队；队列丢失时兜底扫描照样按 `NextTrigger` 记为手动尝试。手动重发只发一次：成功即成功，失败即回到失败，不重开自动退避。`AttemptCount` 累计保留历史，`AutoAttemptCount` 不变。事件 id 不变。

### 停用的作用

| 时机 | 规则 |
| --- | --- |
| 停用时（手动、410、连续失败） | 同一事务里把该订阅所有待投递的记录改为失败，`LastError` 写停用原因，清空 `NextAttemptAt`；记 `DisabledAt` 与 `DisabledReason`。已发出的请求不取消 |
| 自动停用的留痕（410、连续失败） | 改变了订阅状态，按操作记录"改变业务数据的动作都要记"留痕，照 `auth.locked-out` 的写法：动作码 `webhook-subscription.auto-disabled`、失败结果、原因码 `AppWebhook:EndpointGone` / `AppWebhook:ConsecutiveFailures`、授权依据 `WebhookDeliveryPolicy`、操作人为空。处理器在投递链路写回事务提交后、订阅所属租户的上下文里执行，失败记录走独立事务 |
| 停用期间 | 发布时不为它创建投递；发送入口遇到停用订阅时按上一行终结，不发请求。这段时间发生的事件不会补发，文档写明 |
| 重新启用 | 清空 `DisabledReason`、`DisabledAt` 与 `FirstFailureAt`。带 `retryFailed` 时，把该订阅现存（保留期内）的全部失败投递按手动重发处理，不另维护失败区间 |

### 统计口径

| 指标 | 口径 |
| --- | --- |
| 投递数 | 按投递的 `CreationTime`（即发布时刻）分桶的投递记录数；一个事件发给 N 个订阅计 N |
| 成功 / 失败 / 重试中 | 按投递**当前**状态计入其创建时的桶；手动重发改变终态后，统计随之改变 |
| 成功率 | 成功 ÷（成功 + 失败），不含重试中；分母为 0 时为空 |
| 近 7 天成功率（订阅列表） | 最近 7×24 小时内创建的投递，口径同上 |
| 已停用订阅、重试中 | 存量，不随区间变化 |
| 环比 | 上一区间按日历前移同样天数；上一区间起点早于保留期下限时，上一区间返回空，界面显示"无可比数据"，不按 0 计算 |

按日历区间的统计不放进组件端点：时区、日历桶与上一区间是模板统计接口的约定（`template/docs/standards/api-batch-statistics.md#2-按日历区间统计`），组件只提供按桶计数，与操作记录一致。

### 模板集成与条件裁剪

`IncludeWebhooks` 是一个可以独立取舍的产品边界，按 `docs/template/development-guide.md#31-加开关的两条规则` 定为布尔参数，默认 `false`，适用于全部 `ServiceRole`。为 `true` 时生成：

| 层 | 内容 |
| --- | --- |
| Application | 本地身份形态：`Webhooks/Provider/WebhookDefinitionProvider` 声明示例事件 `user.created`（载荷只带用户 id），在 `UserAppService` 的创建用例里、同一工作单元内直接调用发布器（不新建领域事件）。Resource 形态不声明示例事件：本地用户是投影，"创建"不是业务事件；生成项目只有内置的 `webhook.test`。webhook 统计用例（按日历区间，调用组件的按桶计数）；平台统计里私有的区间换算 `ResolvePeriod` 有了第二个使用方，抽成 `Statistics/` 下的共享类型，两处共用 |
| Api | `AddWebhooks` 组合；`ComponentEndpoints` 映射 `webhooks` 组；统计端点 `GET /api/v1/webhooks/statistics`（`startDate`、`endDate`、`timeZone`、可选 `subscriptionId`，与平台统计同一约定）；权限 `App.Webhooks`、`App.Webhooks.Manage`（开发者组，宿主与租户两侧）；新建、修改、删除、轮换、启停写操作记录（`webhook-subscription.created` / `updated` / `deleted` / `secret-rotated` / `enabled` / `disabled`；成功记录由订阅变更事件的处理器在提交后写，被拒由端点上的动作码补记）；投递链路的自动停用（410、连续失败）由同一处理器记 `webhook-subscription.auto-disabled`，失败结果带原因码、无人工操作者；`appsettings.Development.json` 放行回环地址 |
| Infrastructure | DbContext 调 `ConfigureWebhooks()`；`AddWebhooksEfCore`、`AddWebhookRetention`；Identity 与 Resource 两套增量迁移 `AddWebhooks`（整文件守卫，并在生成排除中登记），快照加条件块 |
| 前端 | `platform/webhooks` 路由与页面、侧栏开发者组入口（组条件改为 `OpenIddictServer \|\| IncludeWebhooks`）、权限常量、DTO 与服务、词条（en / zh-CN，`webhooks` scope）、Mock 数据、spec；生成项目列表规范 `docs/standards/frontend-lists.md` 补一条：详情内容长、需要纵向铺排时用右侧抽屉，抽屉顶部列全表格各列，代替行展开补偿被裁的列 |
| 文档 | 生成项目 `docs/standards/webhooks.md`：怎样声明与发布事件、接收方如何接入（验签、去重、快速 2xx、不依赖顺序、410 退订）；`docs/README.md` 按任务读取清单加一行 |
| 项目 Skill | 业务开发任务读取清单里加 webhook 规范入口 |

代价：

- 有效形态从 320 组翻倍到 640 组，生成检查四个分片的耗时随之增加。
- 场景矩阵新增 `webhooks`（Identity、多租户、本地化、带前端；`core` 档）和 `resource-api-webhooks`（Resource、无前端；`full` 档）两个场景。其余组合由两两覆盖负责。
- 唯一的交叉是纯 API 形态（无 SPA）开启 Webhook 时注册持久 Data Protection 密钥环，否则签名密钥在重启后无法解密。此外自动停用不桥接通知；操作记录用已有的无条件写法。所以不新增有效能力表达式。

### 备选与取舍

| 备选 | 结论 |
| --- | --- |
| 先建通用 Outbox / 持久作业队列，webhook 架在它上面 | 不采用。事件表本身就是发件箱，兜底扫描复用已有的集群周期任务即可；通用队列另有其他消费者时再单独立项 |
| 只做兜底扫描，不做立即投递 | 不采用。首发延迟会退化为一个扫描间隔，及时性不足 |
| 投递记录加租约字段，按行抢占 | 不采用。扫描本来就单副本运行；立即投递与扫描之间留 1 分钟宽限期，超过 15 秒超时的重叠极少，重复由接收方去重 |
| 在设置页暴露退避和超时 | 不采用。这些是协议参数，超时和内网白名单也是信任边界 |
| 包装官方 StandardWebhooks 库 | 不采用。签名只有几十行，自己实现可以支持新旧双签；验收用官方库验签，证明格式兼容 |
| 模板不加参数、始终包含 | 不采用。这是可以独立取舍的产品边界，不用的项目会带上四张表和一个管理页 |

### 兼容与回滚

新增家族与新增模板参数，默认关闭，不影响现有 API 与已生成项目。回滚就是撤掉对应 PR；在 `IncludeWebhooks=true` 的形态发布之前，迁移不会进入任何生成项目。

## 3. 计划

### 节奏：一个 PR、契约先行、验证分层只跑一次

框架与模板放在**同一个 PR**：本地模板工作区经 `pack-local-feed` 消费同树候选包，PR CI 也从同一候选包源验证模板场景（`docs/framework/ci-release-gates.md#同候选输入计划`）。因此不必等框架 beta 发布，代码审查、PR CI 与端到端验收各只走一轮。

| 波次 | 任务 | 并行关系 |
| --- | --- | --- |
| W1 契约冻结 | 任务 1 的公共契约（接口、DTO、Options、错误码）与 `MapWebhooks` 路由和 DTO；模板统计 DTO；前端 TS DTO | 单独执行，后续各路都依赖它 |

## 4. 结果

### 实际交付

一个 PR 交付框架与模板：[#222](https://github.com/zengqinglei/leistd-net/pull/222)。

- 框架：`Leistd.Webhooks.Core`（契约、管理用例、签名与密钥保护、内网拦截发送器、按序结果分类）、`.EntityFrameworkCore`（四张表、发布、立即投递与兜底扫描、停用终结、统计读取、保留期、管理存储）、`.AspNetCore`（`MapWebhooks` 与端点名常量）；随包文档 `framework/docs/components/webhooks.md`。
- 模板：`IncludeWebhooks` 参数与裁剪、权限与操作记录（含自动停用）、示例事件 `user.created`、统计端点与共享 `StatisticsPeriod`、两套增量迁移、方案 A+ 管理页、生成项目 `docs/standards/webhooks.md`、场景 `webhooks` 与 `resource-api-webhooks`。

### 与计划的偏差

| 偏差 | 原因 |
| --- | --- |
| 订阅变更合并为单个 `WebhookSubscriptionChangedEvent`（含 `Updated`），模板用事件处理器写操作记录 | 照 `TenantChangedEvent` 先例；"修改订阅"改变推送目标，须留痕 |
| 自动停用（410、连续失败）写 `webhook-subscription.auto-disabled` 操作记录，无人工操作者；投递在系统身份下执行，不继承入队请求的用户 | 端到端验收发现；依据操作记录原则 §1、§7 与 `auth.locked-out` 先例 |
| 纯 API（无 SPA）开启 Webhook 时注册持久 Data Protection 密钥环（唯一跨参数条件） | 否则重启后签名密钥无法解密，投递全部失败 |
| 密钥解不开时记一次失败尝试并按普通失败退避 | 否则投递永久停在待投递、每轮扫描重复报错 |
| 场景断言新增 `ForbiddenFileTokens`；三个已有场景开启 Webhook | 词条 JSON 的裁剪需要按文件断言；满足 full 档条件行覆盖 |
| 平台统计的区间换算抽成共享 `StatisticsPeriod`，仪表盘环比与迷你趋势抽成 `shared/utils/stat-trend.ts` | 各有第二个使用方 |
