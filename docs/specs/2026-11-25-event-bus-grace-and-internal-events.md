# 分布式事件：宽限期只给立即路径，支持本服务内事件

状态：进行中 · 风险档：高 · 关联：下游反馈（总协调 2026-11-25，发件箱延迟与自定义传输下的内部事件）

## 1. 需求

### 问题与背景

下游项目两条反馈，都已在协调材料里给出结论，本规格落实框架侧改动：

1. **只写发件箱的进程发布的事件晚约 60 秒。** 发布时 `NextAttemptAt = now + 1 分钟`（`EfCoreDistributedEventBus.cs:55`），收件箱同样（`EfCoreDistributedEventReceiver.cs:137`）。这 1 分钟是留给"本进程提交后立即发送/处理"的宽限期（`docs/specs/2026-11-06-distributed-events.md` 发送第 1 步），让兜底扫描不和立即路径抢同一行。但宽限无条件写入：写入进程关掉 `Outbox.DispatchEnabled`（规格 D15 的分工）时没有立即路径，扫描就是正常路径，宽限只剩延迟。下游 API 只写发件箱、Worker 每 5 秒扫描，生产上 API 发出的事件全部晚约 60 秒，System e2e 一个用例多等 65 秒。收件箱在"接收进程不处理"的分工下同理。
2. **内部事件在生产传输下进死信。** 下游要把"API 提交后由 Worker 立即处理"的两类作业（现为每分钟一轮的周期任务）改成分布式事件。但下游生产 Worker 唯一的传输是一个自定义对外集成传输，发送前查能力目录，未登记事件直接永久失败；而"每个服务只能选择一个传输"（`framework/docs/components/event-bus.md`）。结果开发、演示、e2e（Loopback）都通过，生产一开该传输，只有本服务消费者、本不该出服务的事件全部进死信。

### 目标与非目标

- 目标：
  - 宽限期只在本进程会走立即路径时才加，否则新行立即可被扫描。
  - 事件契约可以显式声明为"本服务内事件"：发件箱取到后不经传输，由框架在同库直接写本服务收件箱，其余语义（重试、死信、重投、收件箱去重与处理、管理端）与普通分布式事件一致。
- 非目标：
  - 不做跨进程唤醒（LISTEN/NOTIFY、额外消息通道）；正常情况下由下一轮扫描取走（`DispatchInterval`，默认 5 秒），集群锁、积压与重试都可能延长。
  - 不加"首次可取时间"配置项；正确取值由分工开关决定。
  - 不放开"每个服务一个传输"，不做按事件路由到多个真实传输。
  - 不改"开启发送须注册传输"的现有校验；只有内部事件的服务仍需注册一个传输（可用 Loopback）。
  - 不新增持久化作业队列组件。

### 部署前提

- 本地投递按派发实例**本机登记**的内部消费者写收件箱，框架依赖同库实例的部署一致性，不做集群订阅发现：共库中所有能派发发件箱（`Outbox.DispatchEnabled=true`）或处理收件箱（`Inbox.ProcessingEnabled=true`）的实例，都必须登记相同、完整的本服务内事件处理器。处理实例也在内，因为它们可能先扫描到内部收件箱行。典型分工（API 只写、Worker 全开且同一镜像）天然满足。
- `Inbox.ReceiveEnabled` 只管传输入口，不参与本地投递的判断；关闭它的派发实例照样按本机登记本地投递。
- 违反前提的实际后果：派发端**找不到任何**匹配的内部消费者时，运行期进 `internal-no-consumer` 死信，修正后重投；只漏登部分消费者时，已登记的消费者照常收到、发件箱标 Sent，遗漏的消费者收不到，框架无法据此发现，只能靠部署一致性保证。框架不为异构实例另做逐行跳过或领取机制。
- 启动时无法发现"只写进程日后会发布哪些内部事件"，所以"无本地消费者"只在运行期由派发进程判定。
- 已有事件名从对外改为内部（或反过来）前，先排空该事件的待发行，或给内部事件用新的事件名：旧行按发布时冻结的路由投递，而订阅视图跟随当前契约。
- 升级顺序：先把能派发该发件箱的全部实例升级到新版本，再开始发布本服务内事件（旧 Worker 会把带标记的行交给实际传输）。

### 已确认的决策

- 选择"本服务内事件 + 本地投递"，不做多传输路由、不另建作业队列（用户经总协调询问，2026-11-25 由 Claude 定，结论已记入下游协调材料）。
- 宽限修复与本服务内事件同批，随下一个框架 beta 发布；若后者评审拖长，宽限修复先单独发。

## 2. 方案

### 现状事实

- 发布：`Leistd.EventBus.EntityFrameworkCore/Publishing/EfCoreDistributedEventBus.cs` 写发件箱行，`NextAttemptAt = now.AddMinutes(1)`；提交后 `DistributedEventQueue.OutboxAfterCommit` 仅在 `Outbox.DispatchEnabled` 时入队立即发送。
- 扫描：`Dispatching/DistributedEventScanner.cs` 取 `Status == Pending && NextAttemptAt <= now`；两条路径都不认领行，重复发送靠收件箱按（租户、EventId、消费者）唯一约束去重。
- 发送：`Dispatching/DistributedEventOutboxProcessor.cs` 调 `IDistributedEventTransport.SendAsync`，按结果标 Sent / 退避 / 死信。
- 接收：`Receiving/EfCoreDistributedEventReceiver.cs` 的 `AcceptAsync(raw, message, ct, persistRejection, enqueue)` 按本进程登记的订阅（`IDistributedEventSubscriptions`）为每个消费者写收件箱行，无消费者时直接返回 true；`NextAttemptAt = now.AddMinutes(1)`，`InboxAfterCommit` 仅在 `Inbox.ProcessingEnabled` 时入队。
- 回环：`Leistd.EventBus.Distributed/Loopback/LoopbackEventTransport.cs` 就是"发送 = 调本进程接收入口"，坐标 `transport=Loopback`；受"每个服务一个传输"约束，不能与其他传输并存。
- 消息头：`DistributedEventHeaders`（`traceparent`、`tracestate`、`leistd-correlation-id`），发件箱 `Headers` 以 JSON 持久化，收件箱复制一份。

### 设计

**宽限期**：发布时 `NextAttemptAt = DispatchEnabled ? now + 宽限 : now`；收件箱新行的公式见下文"收件箱宽限"。宽限仍是内部常量（1 分钟），两处共用一个常量。

**本服务内事件**：

- **声明**：Core 新增标记接口 `IInternalDistributedEvent : IDistributedEvent`（命名在评审中可调整）。事件契约实现它即为本服务内事件；契约通常不进共享契约包。
- **记录**：发布时若事件实现该接口，在发件箱行的 `Headers` 写入 `leistd-delivery: internal`。这是发件箱内部的持久化路由元数据，常量放在 EF 实现内部，不进公开的 `DistributedEventHeaders`（那里是跨传输消息头约定，公开会让自定义传输误以为要处理它）。路由在发布时冻结进行里，派发进程不需要认识事件类型；契约日后改动不影响已写入的行。不新增列、不需要迁移。
- **派发**：`DistributedEventOutboxProcessor` 读到该头时不调传输，改为本地投递：由行构造信封（坐标 `transport=internal`，接收时刻单独传入），调用接收器的本地入口写本服务收件箱，成功即按现有逻辑标 Sent。立即派发、扫描与单条重投都走同一处理器，行为一致。
  - 本进程没有该事件的消费者 → 永久失败，错误码 `internal-no-consumer`（不能沿用接收侧"无消费者即视为成功"的语义，否则静默丢失）。
  - 载荷无法还原、租户不存在 → 永久失败，错误码 `internal-invalid-payload` / `internal-unknown-tenant`；不写拒收表（拒收表属于传输入口）。
  - 写收件箱时数据库异常 → 瞬态失败，按现有退避重试。
  - 立即路径（单进程部署）同样走本地投递。
- **订阅视图**：公开的 `IDistributedEventSubscriptions.GetAll()` 是传输视图，默认实现只含对外订阅（事件类型未实现标记接口），供传输建订阅、传输入口与重新解码匹配；自定义传输（如下游的对外集成传输）照旧调用它，自动不含内部事件，无需改动。宿主仍可替换该接口，框架各处继续尊重替换结果。内部订阅由框架内部服务从同一批 `DistributedEventSubscription` 登记派生，不随接口替换变化；本地入口只匹配内部订阅，收件箱处理器、重放与事件目录用"`GetAll()` ∪ 内部订阅"查找处理器。
- **接收器**：抽出共用的载荷还原、租户校验、扇出与入库；传输入口（`ReceiveAsync`、重新解码）只匹配对外订阅，行为不变（无消费者即成功、写拒收表）；EF 内部新增本地入口，返回可区分的结果（已写入 / 无消费者 / 载荷无法还原 / 租户不存在），由处理器映射为 Sent 或三种永久失败；写库故障沿用瞬态退避，日志写明失败发生在本地投递。
- **收件箱宽限**：新行 `NextAttemptAt = (enqueue && ProcessingEnabled) ? now + 宽限 : now`，覆盖普通接收、本地投递与重新解码（批量同步重新解码 `enqueue: false`）。
- **管理端**：收件箱坐标显示 `internal`；发件箱详情展示消息头即可看到标记；三个错误码沿用现有发件箱失败码的做法，只加常量、不加本地化词条，界面原样显示码值。

### 备选与取舍

- **跨进程唤醒**：要么依赖数据库专有能力（PostgreSQL LISTEN/NOTIFY 需会话级长连接、分库逐库监听），要么再开一条消息通道，多一个故障面；5 秒轮询已满足"秒级"。不采用。
- **"首次可取时间"配置项**：取值完全由分工开关决定，做成配置只会多一个能配错的值。不采用。
- **按事件路由到多个传输**：放开"每个服务一个传输"，连带多传输的健康上报、状态、管理端区分与重新解码路由；需求只是"内部的不出去"。不采用。
- **持久化作业队列**：与发件箱/收件箱/死信/管理端重复建设一套。不采用。业界同类做法（NServiceBus `SendLocal`、Wolverine 本地持久队列）也是在消息框架内按类型本地路由。
- **在发件箱加列记录投递方式**：可查询，但要模板两套基线与下游各自迁移；目前没有按投递方式查询的需求，消息头已持久化且随行冻结。选消息头。
- **由派发进程按订阅类型判定是否内部**：派发进程若漏登记消费者，事件会被当作外部事件交给传输，错误表现为传输侧拒绝，难以定位。发布时冻结更可靠。

### 兼容与回滚

- 宽限修复：`DispatchEnabled=false` 的进程发布的行提前可取。立即路径不存在，没有"抢同一行"的问题；多副本 Worker 的扫描本来就由集群锁串行。行为变化只是延迟变短。
- 本服务内事件：新增能力，不实现标记接口的事件行为不变；无迁移。升级顺序见 §1 部署前提。回滚前先停止发布本服务内事件，排空或隔离带标记的待发行，并暂停这类死信的重投，直到能识别标记的 Worker 恢复；否则旧版本会把它们交给实际传输。
- 版本：`feat(event-bus)`，非破坏性。

## 3. 计划

1. **框架实现**：宽限条件化（发布、接收两处，收件箱按 `enqueue && ProcessingEnabled`）；`IInternalDistributedEvent`（Core `Events/`，带中文 XML 注释）、EF 内部路由头、发布时写头；订阅视图分对外与内部；接收器抽出共用逻辑与本地入口；处理器本地投递分支与三个错误码（沿用现有发件箱失败码的做法：只加常量，不加本地化词条，界面原样显示码值）。验证：event-bus 相关单测与关系型数据库测试覆盖 G1–G5、L1–L8（G2、G4 用现有用例补断言，L6 新增收件箱保序用例），修复前 G1、G3、G5、L1、L2、L8 失败。公共 API 变化按 L1 配方打包到 `.tmp/local-feed` 并做定向隔离消费，确认契约可从发布包引用。
2. **随包文档**：`framework/docs/components/event-bus.md` 的"分工与配置"改写宽限一句（扫描间隔写成正常情况下的下一轮时机，不写延迟上限）；新增"本服务内事件"一节：何时使用、可编译的最小声明与处理器登记示例、部署前提与升级/回滚顺序、错误码、传输不为它建订阅、与周期任务对账的关系。验证：文档引用与骨架检查。
3. **模板**：核对模板有无依赖 1 分钟宽限的测试或说明，以及前端失败码映射是否要登记三个新错误码（需要则写明产物并做定向验证）；不新增示例。验证：受影响场景（含分布式事件）定向生成与测试，PR CI 跑增量，全集由合入后与发布前承担。
4. **审查与发布**：方案送 Codex 审查通过后实施；代码送 Codex 审查通过、CI 全绿后合并，发框架 beta；在协调材料追加回执（确切 beta 版本、下游动作）。

不做的事：见 §1 非目标。
