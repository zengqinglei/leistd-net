# 前端会话级数据首读不重复

状态：已完成 · 风险档：中（只改模板前端的会话数据持有与页面首读，不改接口） · 关联：[#330](https://github.com/zengqinglei/leistd-net/pull/330) · 来源：下游业务项目反馈（会话数据重复读取） · 基线 develop `15b0182e`（反馈核对于 `9a22afd5`）。

## 1. 需求与验收

**目标**：同一主体、同一范围、同一界面语言下，会话级数据在一次进入里只读一次；页面和组件消费会话持有的结果，只在规定时机重读。

已核对的模板现状：

| 数据 | 重复来源 | 判定 |
| --- | --- | --- |
| 设置 `GET /api/v1/settings` | 启动 `loadContext()` 以 `load('entry')` 读过；冷启动直达系统设置页，`SettingsPageState` 构造时 `refresh()` → `sessionContext.refreshSettings()` 再读一次。代次只管结果落定，请求照发 | 修 |
| 通知历史 `GET /api/v1/notifications?limit=50` | 铃铛 `ngOnInit` 每次 `init()` → `loadNotifications()`；外壳重建再取，无在途合并、无同代复用 | 修 |
| 权限：首次实时订阅确认后重查 | 模板前端没有 `AccessChanged` 链路 | 归下游，不改 |
| 平台入口权限 + 工作区权限 | 两者用途不同 | 保留 |
| 回到前台 / 实时被拒后重查 `/me` | 会话恢复机制，已合并在途 | 保留，补断言 |

验收（Given/When/Then）：

1. Given 已登录、冷启动深链到系统设置，且启动设置读取成功、与页面首读使用同一请求语言，When 页面渲染完成，Then 同范围 `GET /api/v1/settings` 只出现一次。
2. Given 启动时设置读取失败，When 进入设置页，Then 页面自己读一次（不复用失败结果）。
3. Given 设置页已打开，When 切换界面语言 / 切换范围（租户、工作区、本人设置）/ 写入成功后确认 / 手动刷新，Then 各按原策略读取一次。
4. Given 账号本人设置（homeScope），Then 仍走本人范围读取，不复用系统范围快照。
5. Given 已登录，When 外壳初次渲染或同范围重建，Then 同一 SignalR 代次内首读与在途请求共用，默认 50 条历史成功读取后重建不再发请求。切换有效工作区或更换登录主体后，目标代次首次消费读取一次。显式重试仍发请求。
6. Given 正常站内导航 / 回到前台 / 实时重连，Then 三种场景各自的请求次数与规定时机表一致（见 §2）。
7. 模板全部路由的冷启动与站内导航网络审计：除 §2 表允许的时机外，无同范围的会话级重复读取；审计清单随 PR 附上。

## 2. 方案

**规则（写入前端规范，一处维护）**：会话级数据由会话层服务持有快照与在途请求，消费方读快照。下表覆盖会话级读取。业务列表、词条、Hub 协商和业务实时订阅各自计数。

| 数据 | 启动或登录 | 有效工作区切换 | 界面语言切换 | 回到前台 | 实时重连 | 写后确认 | 显式重试 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `GET /auth/me` 与账户偏好 | 建立登录主体时读；偏好随响应返回 | 使用已读到的本人数据，无新 GET | 无新 GET | 已登录时重验，合并在途 | 正常重连零次；疑似 401 被拒时重验，合并在途 | 资料与偏好使用写响应；安全设置、重新认证等保留既有 `loadUser()` 调用 | 启动失败重试会重跑启动 |
| 当前权限 | 按入口范围读取；宿主工作区深链可另读本人平台入口权限 | 建立目标范围时读取；同范围导航复用 | 无 | 无 | 无会话权限 GET | 保存角色权限、变更用户角色等现有入口重读 | 启动失败重试会重跑启动 |
| 生效设置 | 建立会话范围时预读；页面首读仅复用同主体、同范围、同请求语言的成功结果，无可用快照时由页面补读 | 建立目标范围时读取；本人设置在工作区形态继续独立按本人范围读 | 打开中的设置页在语言实际切换后重读；其他页面无会话设置 GET | 无直接读取；重验若应用了新语言，打开中的设置页按语言规则读 | 无直接读取；被拒后的重验也可能应用新语言 | 普通设置写成后重读；账户偏好 PATCH 使用写响应，若语言变化则按语言规则重读 | 设置页重试强制读；启动失败重试会重跑启动 |
| 通知历史 | 铃铛首次消费时读 | 切换范围后目标代次首次消费时读，同范围重建复用 | 无 | 无历史 GET | 正常重连和连接被拒均不直接重读历史 | 已读与删除成功后更新本地列表 | 铃铛或工作台显式重试 |

**设置**：`SettingContextService` 记住最近一次成功快照所属的键（主体代次 + 范围 + 语言），并保留在途的 entry 读取。新增「取当前快照」入口：键一致且成功时直接返回（在途则等它），否则读取。成功的空列表可复用，静默失败产生的空列表须补读。语言以请求发出时为准。`SettingsPageState` 只在构造首读时使用它，本人设置保持独立；写后确认、切语言、手动刷新仍走 `refresh`。不新增缓存层，不加 TTL。

**通知**：`NotificationService.init()` 按 SignalR 现有 `authGeneration` 复用默认 50 条历史的在途与成功结果。成功以历史请求结果为准。显式重试走 `loadNotifications()`，默认 50 条重试成功即满足同代首读，失败可再读。

**审计**：生成 identity-workspace（真实后端），有头浏览器逐路由冷启动 + 站内导航，记录请求，列「数据 × 次数 × 触发方」；不属于 §2 时机的同范围会话级重复一并修。

**回归**：前端单测挂真实守卫与页面组件（`RouterTestingHarness` + `HttpTestingController`）按场景断言请求次数，覆盖验收 1–6；不新增 E2E（准入闸门）。审计本身作为一次性证据，不进 CI。

**不做**：通用请求去重/缓存拦截器；按 URL 的全局去重；下游 `AccessChanged` 链路。

## 3. 约束与计划

- 规范读取成本：全栈 CRUD 路径 70694 / 70700，只剩 6 字符。新增规则须在同篇去重抵消，不抬上限。
- 条件裁剪：设置、通知、工作区按参数存在与否，改动与测试须在相关形态都 build（真假两侧）。
- 前端设计不变，无 UI 改动。

### 计划

1. 网络审计（先做，结果可能补充 §1 表格与 §2 时机表）。
2. 设置首读复用、通知初始化同代幂等，各自先写修复前失败的计数用例。
3. 审计发现的其他同范围会话级重复，按同一规则修。
4. 前端规范写入时机表（同篇去重抵消篇幅）。
5. 受影响形态的 verify、读取成本闸门，审计复跑，§4 记录证据。

## 4. 验证记录

- 在生成的 identity-workspace 上，系统设置冷启动重复读与通知并发重复读两条回归均在修复前按预期失败。修复后定向浏览器单测通过 277 项，覆盖请求语言不同、启动失败后补读、本人范围及通知重试。
- 有头审计使用真实后端。基线与修复版各采集 52 个冷启动入口、41 条站内导航，并验证同范围外壳重建及工作区切换。同语言下宿主和工作区系统设置冷启动由 2 次降到 1 次，站内首读由 1 次降到 0 次。同范围外壳重建后的通知历史由 1 次降到 0 次，切换工作区后目标范围仍读 1 次。
- 已同步[前端规范的会话级读取](../../template/docs/standards/coding-frontend.md#会话级读取)，全栈 CRUD 阅读成本为 70,528／70,700，通过。
- `identity-workspace` 和 `identity-capabilities-01` 的完整 `verify` 均通过，覆盖启用与裁剪形态的构建、前端单测及既有端到端用例。
