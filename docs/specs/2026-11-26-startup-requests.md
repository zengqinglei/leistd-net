# 前端启动请求去串行与去重复

状态：已完成 · 风险档：中（只改模板前端的启动编排与守卫，不改接口） · 关联：[PR #324](https://github.com/zengqinglei/leistd-net/pull/324)

## 1. 需求

### 问题与背景

一个下游业务项目（由模板生成）分析了冷启动的请求链，模板里也有同样的问题。用 `TenantWorkspace` 形态、直接打开 `/w/{key}/…` 冷启动时，路由页面加载前最多要经过 7 个串行请求：

```
/me → 权限 → 设置 → 工作区列表 → [宿主] 平台权限 → 权限（带工作区头）→ 设置（带工作区头）
```

已对照源码核实：

- **权限和设置串行。** 在 `session-context-service.ts` 的 `loadContext` 里，`await authorization.initialize()` 之后才 `await refreshSettings()`，但这两个请求互不依赖。
- **同一份数据取两遍。** 首轮请求通过拦截器的 `requestScope()`，已经按地址里的工作区带上了头。但启动时没有设置 `target`。守卫调用 `workspace.establish(name)` 时，判断 `target() === name` 不成立，于是执行 `authorization.clear()` 和 `session.establish()`，把权限和设置用同一个头完整重取一遍。
- **工作区列表每次进入都重取。** `/platform` 也挂了 `workspaceGuard`，它会调用 `workspace.refresh()`，每次进入都重新取工作区列表；宿主账号还会再串行取一次平台权限。

三个接口（`/me`、`/permissions/current`、`/settings`）**不合并**：
- 失效时机不同：`/me` 每次回到前台就重取，权限随实时推送重取，设置只在保存后重取；
- 失败语义不同：`/me` 失败就去登录页或失败页；权限失败就阻止进入；设置失败按默认值继续；
- 后两个接口是框架组件提供的，被多处复用；
- HTTP/2 下，并行的小请求代价约等于一个往返，真正的成本在于串行。

### 取舍依据

- `docs/architecture/design-principles.md` §5：
  - **终局：** 同一份数据不在一次启动里取两遍；
  - **优先官方机制：** Angular 守卫保持轻量、复用已有状态，互不依赖的请求并行；
  - **不过度设计：** 不新增状态管理库、通用缓存层或请求编排框架，在现有服务里改，在途请求用共享的 Promise 去重。
- 模板测试规范：新增的测试断言要能证伪，按行为断言请求，不断言实现细节。

### 目标与非目标

- **目标：** 深链冷启动只剩「`/me` 之后一批并行请求」；守卫复用启动结果；工作区列表一次会话只取一次，在途请求共用。
- **非目标：**
  - 不合并接口；
  - 不改后端；
  - 不做 `permissions/current` 的 ETag/304。原因：响应体小，HTTP/2 下 304 只省字节、省不掉往返，权限变化已有实时推送触发重取。出现大响应体或高频轮询时再评估。
  - 不改工作区切换、权限失败、设置失败、租户跳转和拒绝页这些现有的行为语义。

### 功能要求与验收

#### R1 权限与设置并行，失败归属由启动流程决定

`loadContext` 里，`authorization.initialize()` 和 `refreshSettings()` 同时发出，两者都结束后，才按下面的规则决定结果。不能按哪个先返回来决定。

- **401 的归属。** 启动和进入工作区阶段，设置请求和权限探测一样，不走全局的 401 处置，由启动流程统一决定。这样可以避免先返回的设置 401 抢先清掉会话并跳转，而权限稍后返回的其实是一个需要显示失败卡片的 503。
- **权限失败：** 照旧向上抛，由启动或守卫按现有方式呈现，包括失败卡片和拒绝页。
- **设置失败：** 照旧清空设置快照，不抛。
- **旧范围的失败不能覆盖新范围。** 设置上下文现在只对成功响应判断代次。改为失败也判断代次：快速切换工作区时，旧工作区的设置晚到失败，不能清掉新工作区已经写入的快照。
- **偏好的读取号**仍取 `/me` 发起时的那一个。

验收：用真实的 `HttpClient`、拦截器和 `HttpTestingController` 测以下情况：
1. 两个请求同时挂起；
2. 权限失败时设置仍在途，最终结果按权限失败呈现；
3. 设置先返回 401、权限后返回 503，最终显示失败卡片，不跳登录页；
4. 设置失败照常进入；
5. 快速切换时，旧范围设置晚到失败，不影响新范围的快照。

#### R2 启动时确定目标工作区，守卫复用首轮结果（`TenantWorkspace`）

- 启动流程在发出首轮请求之前，就按入口地址确定目标工作区：入口是 `/w/{key}` 就取 key，否则取 `null`。确定后写入 `workspace` 的 `target`，首轮的权限与设置就是带这个头的结果。
- 守卫 `establish(name)` 时，name 与启动时确定的目标是同一个工作区（大小写不敏感）、权限也已就位，就复用首轮结果，不清空、不重取。
- 复用时仍要做这几件事：
  - 用目录里的规范名称识别操作账号和已提交的工作区（`actor`、故障恢复按精确名称匹配）；
  - 照常设置实时连接的工作区（`signalR.setWorkspace`），不能因为提前返回而跳过。
- **冷启动时的工作区拒绝。** 首轮带头请求返回 `Workspace:Forbidden` 或 `Workspace:Unavailable` 时，不当作全局启动故障，交给守卫按现有方式呈现拒绝页或恢复路径。

验收（按工作区头分别计数）：
- **租户账号深链 `/w/{key}/platform`：** `/me` 之后同一批里，目录、带头的设置、带头的权限各一次，没有不带头的权限请求。
- **宿主账号深链 `/w/{key}/platform`：** `/me` 之后同一批里，目录、带头的设置、带头的工作区权限、不带头的宿主权限各一次。
- **宿主账号冷启动 `/platform`：** 首轮的权限已经是不带头的，平台入口判定直接复用它，不再另发宿主权限请求。
- **入口 `/w/ACME/…`、目录里是 `acme`：** 复用首轮结果，识别出的工作区主体和实时连接都用目录里的名称。

#### R3 工作区目录并入首批，会话内复用，授权变化后更新（`TenantWorkspace`）

- `/me` 返回后，工作区目录（以及宿主账号需要时的不带头权限）与 R1 那一批一起发出。这一批全部结束后，启动才结束。
- **错误仍由守卫负责。** 目录原来由守卫读取，移到启动批次后，错误归属不能变：目录或宿主权限失败时，启动不判定为全局故障；守卫等待这份结果时，按原来的方式呈现。失败的结果不缓存，下次守卫或显式刷新时重试。
- **会话内复用。** `workspace.refresh()` 改为一次会话只取一次，并发调用共用同一个在途请求，按请求范围各一份：目录一份；确实需要宿主权限时，宿主权限一份。
- **以下情况重新取：**
  - 本页成功授予或移除当前登录账号的工作区访问后，比如平台管理员在租户人员表单里给自己授权。复用现有写入成功的路径，调用显式刷新；
  - 现有的显式入口：`recoverUnavailable`、`workspace-denied` 的重试、登录收尾（`login-completion`）；
  - 主体变化。模拟进出和真实退出都会整页跳转，内存里的目录自然清空，不需要额外监听。

  显式刷新的语义保持「重新取」，可以用参数表达，也可以拆成两个方法，命名按规范定。
- **其他会话里的授权变化**（另一个浏览器或另一位管理员改的）：下次显式刷新、重新登录或整页刷新后可见。这一点写进规范，不新增推送或轮询。
- `/platform` 的 `workspaceGuard` 保留（负责把租户用户导到自己的工作区），不再触发重复取数。

验收：
- 宿主账号第二次进入 `/platform`，不再请求目录；
- 并发两次 `refresh()`，每个范围只发一个请求；
- 目录失败后再进入，会重试；
- 目录已加载，给本人授予一个工作区，不整页刷新，就能从目录（侧栏或选择器）进入新工作区。

#### R4 租户用户的入口跳转（保持现状）

租户用户从没有工作区的入口（比如 `/platform`）进入时，守卫照旧跳到自己的工作区，并带工作区头重读一轮。

静态核对显示带头和不带头时主体一致，但带头还会校验工作区名称、归属和启用状态。保留这一轮重读是低复杂度的选择，这次不消除它，也不需要做后端核实。

#### R5 不变的行为（回归）

现有用例全部保持通过，至少覆盖：
- 快速连续切换工作区时，以最后一次为准（`revision` 机制）；
- 权限失败时阻止进入；
- 工作区不可用或被拒时，走拒绝页和恢复路径；
- 登录收尾 `enter()` 的偏好提交时机；
- 实时连接按工作区重连（`signalR.setWorkspace`）。

#### R6 请求链证据

- 在生成的 `identity-workspace` 里，用真实浏览器冷启动 `/w/{key}/platform`，按时间顺序记录启动阶段的 API 请求。改动前后各记一次，写进 §4。证据要能看出：改动后，`/me` 之后只有一批并行请求，没有第二轮。
- 这是一次性的取证，不新增常驻 E2E 用例，也不调整 E2E 上限。

#### R7 规范

在模板前端规范的现有路由章节加一条守卫复用规则：
- 启动阶段互不依赖的请求并行；
- 守卫复用启动和会话内已取得的状态，不重复取数；
- 以下情况照常刷新：授权变更成功后、设置保存后、显式恢复时，以及范围（主体或工作区）变化时；
- 其他会话里的授权变化，在下次刷新或重新登录后可见。

受读取成本闸门约束，只降不升，在同一篇里去重抵消。

## 2. 方案

- 改动集中在 `startup-service`、`session-context-service`、`workspace-context-service` 和 `workspace-guard`。不新增服务或依赖，在途请求用共享的 Promise 去重。
- 非 `TenantWorkspace` 形态只涉及 R1，条件的真假两侧都要构建、跑测试。
- `resource-workspace` 也会生成这套启动代码。它的工作区票据提供器在缓存为空时，先查缓存再交换；并行请求可能各触发一次交换。这次要生成、构建并跑这个形态的前端测试，在 §4 记下冷启动时的实际交换次数和代价。不新增后端锁或接口。
- **回滚：** 按提交撤回即可，不涉及接口和数据。

### 修复前反证

- R1 使用生成的 `identity-workspace` 和真实 Chromium 运行 `startup-service.spec.ts`、`session-context-service.spec.ts`。41 条通过，3 条按预期失败。两个启动用例在权限仍在途时找不到 `/settings` 请求，旧设置失败的用例读到空快照，未满足保留新范围设置的断言。
- R2、R3 使用同一形态运行 `startup-service.spec.ts`、`workspace-context-service.spec.ts`。23 条通过，5 条按预期证伪。三种入口的首批都缺少目录，目录错误用例也找不到首批目录请求，两次并发刷新发出了两个目录请求。另一个拒绝页用例受测试初始化影响，未计入行为反证。
- 在隔离的生成目录中分别反转设置 401 的静默标记、取消设置失败的代次检查、复用时保留入口的原大小写、取消目录共享。每次运行相关前端 spec，四次各命中一条预期失败。
- 禁用冷启动拒绝结果的交接后，拒绝页用例超时，HTTP 检查报告守卫重发了权限和设置。禁用本人授权后的目录刷新后，浏览器用例在等待该目录响应时失败。两项变异均在隔离生成目录内完成。

### 租户入口（R4）

复用现有 `WorkspaceAuthenticationHandler`。裸入口先加载本人范围，守卫跳到本人工作区时仍以 `X-Workspace` 读取权限和设置。后端校验工作区名称、归属和启用状态后返回本人主体。客户端保留原请求路径，无需通过响应内容推断范围等价。

### Resource 冷启动

通过 `pwsh scripts/test-template-oidc-e2e.ps1 -SkipPack -Workspace -CandidateSha 8d5fc4e5` 的临时副本运行真实 Identity、Resource 和 PostgreSQL。在生成的 Resource 应用上构建生产前端，通过有头 Chromium 打开 `/w/shared-e2e/platform`。临时计时点放在生成目录的工作区令牌提供器，仅记录交换耗时。

`/me` 在 231 ms 完成，随后四个请求在 239–245 ms 发出，最后一个在 488 ms 完成。带头的权限与设置都在工作区缓存仍为空时触发交换，共两次，分别耗时 64.7 ms 和 78.6 ms。该轮未添加网络延迟。脚本的 `workspace` 场景通过。
