# 测试分层预算、E2E 准入、逐条耗时与缓存时钟

状态：进行中 · 风险档：中 · 关联：待定

## 1. 需求

### 问题与背景

一个下游业务项目（三个仓库，都由模板生成）报告了 11-24～25 两天的实测教训：

- **E2E 失控。** 单个需求跑一次完整档 E2E 约 90 分钟。PR 档用例一个多月内从 31 条涨到 69 条，没有上限。
- **CI 耗时与写盘。**
  - 拆分并行后，每个作业各自还原和构建；每个测试类又克隆一个库，节点写盘打满。
  - 耗时预算只算测试步骤，没算还原和构建。
- **不稳定用例。** 有四条，都依赖墙钟或时序。其中一条的原因是 HybridCache 本地层不跟随测试宿主的 `FakeTimeProvider`。

核对本仓库现状：

- **框架：**
  - 内存缓存和 HybridCache 本地层的过期都不跟随容器里的 `TimeProvider`。
  - .NET 10 的 `MemoryCache` 只认 `MemoryCacheOptions.Clock`（`ISystemClock`）。
  - 框架和模板的测试里共有 5 份手写的时钟适配器。
- **模板测试规范：** `template/docs/standards/testing.md` 已有按风险选测试、E2E 三档和 E2E 范围原则。缺的是：
  - 分层预算；
  - 适用于所有层的精简口径；
  - 「一个实体只读一次时钟」「不断言墙钟内完成量」两条。
- **模板 `verify.ps1`：**
  - 不输出逐步耗时；
  - MR/PR 上不按改动选步骤；
  - 不产出逐条用例耗时的报告：后端只有总数。
- **模板测试夹具：**
  - PostgreSQL 已用非持久化参数（`fsync=off` 等），但数据目录在容器磁盘上；
  - 克隆用默认的 `WAL_LOG`。
- **模板 E2E：**
  - 已有 `@auth`、`@crud` 分组标签和 30 秒单例超时；
  - 没有「每条只证明一类跨进程接线」的准入核对，也没有数量上限。

### 取舍依据

- `docs/architecture/design-principles.md` §5。
- 模板按派生项目长大后的终局给规范，不按模板自带示例的体量取舍。
- **优先官方机制**：Playwright 标签和 reporter、Vitest reporter、Testcontainers tmpfs、PostgreSQL `CREATE DATABASE … STRATEGY`、GitLab `artifacts:reports:junit`、GitLab 推荐的 JunitXml.TestLogger。
- **不过度设计**：闸门只核对能证伪的判据，核对不了的信息写进 PR 描述。
- **只修默认就会出错的**：不为极少见的边缘或竞态场景加防护。
- **显式选择给文档**：模板不知道项目的合并方式，这类内容只写文档。

### 目标与非目标

- **目标：**
  - 框架：缓存过期默认跟随宿主 `TimeProvider`。
  - 模板：规范有分层预算和精简口径；E2E 有准入和上限；验证脚本按改动选步骤，并输出逐步与逐条耗时；测试库写盘更少。
- **非目标：**
  - 不拆 CI 作业，仍然是一个 `verify` 入口。
  - 不让完整档 E2E 脱离合并关卡。
  - 不做 E2E 的 `lowerCoverage` 字段。
  - 不做 p95 统计：需要跨次运行的历史数据。
  - 模板默认不去掉合入后的验证。

### 功能要求与验收

- **R1 缓存时钟（框架）：** Given 宿主用 `RemoveAll<TimeProvider>()` 换成 `FakeTimeProvider`，并且通过 Leistd 组件或宿主自己的 `AddMemoryCache` / `AddHybridCache` 使用缓存，When 假时钟推进越过 TTL，Then `IMemoryCache` 条目和 HybridCache 本地层条目都已过期。
  - 宿主自己设置了 `MemoryCacheOptions.Clock` 时，无论设置在框架登记之前还是之后，宿主的设置都生效。
  - 生产环境用 `TimeProvider.System`，行为不变。
  - 模板和框架测试里手写的缓存时钟适配器全部删除，改走默认接线。
  - 模板 `testing.md` §2.2 的缓存说明相应简化。
- **R2 分层预算（模板规范）：** `testing.md` §1 的耗时表改成分层表，写明每层证明什么、何时跑、默认预算：

  | 层 | 默认预算 |
  | --- | --- |
  | 编辑中 | ≤1 分钟 |
  | 推送前 | ≤3 分钟 |
  | 合并关卡 | 作业墙钟 ≤10 分钟，含还原与构建 |
  | E2E 受影响分组 | ≤10 分钟 |
  | E2E 完整档 | ≤25 分钟 |

  - 项目可以在 `docs/project/testing.md` 改数值。
  - 单元和集成测试只设耗时预算，不设数量上限。
  - 超预算时先收窄范围，不靠反复重跑。
- **R3 精简口径（模板规范）：** `testing.md` §4 的「下沉或删除」适用于所有层：
  - 只按五类处理：重复覆盖；已被下层覆盖；测实现细节（例如 `as unknown as` 调内部成员）；已删功能的遗留；只测框架或第三方本身。
  - 关键路径、认证授权、租户隔离、合规判定只下沉、不删除。
  - 先补下层，再删上层。
  - 每条处理写进 PR/MR 描述，指出替代覆盖。
- **R4 时间规则（模板规范）：** 后端 §2.2 和前端 §3 各补两条：
  - 同一实体的多个时间字段取同一次时钟读数；
  - 推进类用例按条数或可控时钟断言，不断言墙钟时间内的完成量。
- **R5 E2E 准入（模板 E2E + 静态闸门）：**
  - Given 一条 E2E 用例，When 运行静态检查，Then 它必须恰好带一个 `@proves:<类别>` 标签，类别属于固定集合：auth-session、service-call、gateway-route、deploy-orchestration、realtime、main-flow。缺标签、多标签或类别不在集合里，都失败。
  - 完整档用例数超过登记的上限也失败。上限只在一处登记，默认值为模板现有用例数加少量余量。
  - 闸门带 `--self-test`，进入 `verify`（含 `-Fast`），并写进 `testing.md` §5。
  - 现有用例全部按实际证明的接线打上标签。
- **R6 并发约定（模板规范）：** E2E 默认并发。串行或独占的，必须在旁边注释写明改了哪项全局状态、为什么不能用自建租户隔离。
- **R7 逐步耗时（模板 `verify.ps1`）：** 每一步结束时输出该步耗时，最后汇总各步耗时和总墙钟。还原、构建、浏览器安装都包括在内，只输出、不阻断。
- **R8 按改动选步骤（模板 `verify.ps1` + CI）：**
  - Given MR/PR 流水线，When 改动只涉及后端，Then 只跑静态闸门、后端步骤和 E2E（如有）。
  - 只涉及前端时，只跑静态闸门、前端步骤和 E2E。浏览器只在前端步骤或 E2E 要跑时安装。
  - 只涉及文档时，只跑静态闸门。
  - 无法判定的路径（例如根目录脚本或 CI 文件）按全量处理。
  - 默认分支、定时、手动运行和本地不带参数时，照常跑全量。
  - `-List` 能输出某组改动对应的选择结果。
  - GitLab 和 GitHub 两种形态都接上：改动基准取平台提供的 MR/PR 目标基准。
- **R9 测试库写盘（模板夹具）：**
  - 集成测试和 E2E 的 PostgreSQL 数据目录挂 tmpfs，路径按 `postgres:18-alpine` 镜像的实际数据目录。
  - 克隆改为 `STRATEGY FILE_COPY`。
  - 在模板集成测试全集上做前后对比，记录步骤耗时。哪一项变慢就不保留哪一项。
  - `testing.md` 补一句：分片前先确认依赖缓存在节点上。
- **R10 逐条耗时（模板 `verify.ps1` + CI）：**
  - 后端测试用 JunitXml.TestLogger 产出 JUnit，前端单测和 E2E 用 Vitest、Playwright 的 junit reporter 产出 JUnit，统一放进一个报告目录。
  - GitLab 形态通过 `artifacts:reports:junit` 上报，无论成败；GitHub 形态作为产物上传。
  - `verify.ps1` 结束时按层列出最慢的若干条，超阈值输出警告，不阻断。阈值写在 `testing.md`，项目可以覆盖：
    - 单元（前后端）：目标 ≤100 ms，超过 300 ms 警告；
    - 集成：单条超过 5 秒警告；
    - E2E：超过 15 秒警告。
- **R11 合入后不重跑（模板规范，只写文档）：** `testing.md` §1.1 两种 CI 形态各补一句：
  - GitLab：强制快进合并并开启 Pipelines must succeed 后，默认分支推送可以只构建和发布镜像；
  - GitHub：merge queue 设为必需后同理。

## 2. 方案

- **R1：** 在框架登记内存缓存的公共位置，用 options 配置把 `MemoryCacheOptions.Clock` 接到容器里的 `TimeProvider`。宿主已设置的时钟优先。
  - 具体落点由实施方按框架规范选：不新建包，公共面尽量小；保证模板各形态、只用宿主自己 `AddMemoryCache` 的场景也生效。
  - 宿主不经任何 Leistd 组件时是否需要一个公开入口，按是否有两个以上调用点决定。
  - HybridCache 本地层用的就是容器里的 `IMemoryCache`，无需单独处理。
- **R5：** 闸门脚本放进 `template/scripts/`，与现有 `check-*.py` 同形态。只在有 E2E 的模板形态生成。
- **R8：** 改动判定在 `verify.ps1` 里完成，CI 只负责传入基准。路径到步骤的映射写在一处。
- **R10：** 耗时汇总复用 R7 的输出位置。阈值的唯一来源是 `testing.md` 里的表，脚本内常量与之一致，由脚本自检核对。

## 3. 计划

| 步骤 | 内容 | 验证 |
| --- | --- | --- |
| 1 | R1 框架缓存时钟与测试；删框架侧手写适配器 | 受影响框架测试项目全量；打包到 `.tmp/local-feed` |
| 2 | R1 模板侧：删手写适配器，简化 §2.2 | 受影响生成场景的集成测试 |
| 3 | R9 tmpfs + `FILE_COPY`，前后对比实测 | 同一场景的集成测试全集，各跑前后两次 |
| 4 | R7、R8、R10：`verify.ps1`、两种 CI 文件、JUnit 报告 | `verify.ps1 -List` 覆盖各类改动；真实运行一次完整验证和一次 `-Fast` |
| 5 | R5、R6：E2E 标签、闸门、上限 | 闸门 `--self-test`；故意缺标签或超上限时闸门失败 |
| 6 | R2～R4、R11：规范条文 | 模板规范读取成本闸门；`scripts/check-all.ps1` |
| 7 | 端到端闭环 | 见下 |

端到端闭环：
- 在全功能与最小两类生成场景里各真实运行一次 `pwsh scripts/verify.ps1`，确认四项：
  - 逐步耗时、慢用例汇总和 JUnit 报告都产出；
  - E2E 闸门生效；
  - 缓存时钟用例通过；
  - tmpfs 和 `FILE_COPY` 下的集成测试全绿。
- 再用模板包隔离安装生成一次（`pwsh template-package/test-template-package.ps1`），确认重建零差异。
