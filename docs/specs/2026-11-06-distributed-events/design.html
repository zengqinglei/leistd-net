分布式事件组件 · 详细设计方案

为框架补齐跨服务事件的可靠投递：事件随业务事务写入发件箱，提交后立即发送，失败时持久重试，集群任务逐库兜底；消费侧用收件箱去重，处理器的写入与"已处理"标记同事务提交；传输可替换，首批附带回环、RabbitMQ 与 Kafka，私有事件中枢由业务按同一契约接入；模板以条件参数接入后台页面。

风险档：高 基线 develop 67bf27e3 一个 PR：框架 + 模板，验证各跑一次 2026-11-07：七项缺口按终局补齐；传输、模板、节奏按终局决策；UI 选 A 规格：docs/specs/2026-11-06-distributed-events.md

1背景

框架现在只有进程内事件总线。跨服务的可靠投递是通用能力，换一个业务项目也会遇到，所以先立项设计，交给业务项目使用后再按反馈改进。

现有能力

Leistd.EventBus.Local 在进程内同步分发，按工作单元阶段推迟到提交前或提交后。文档写着跨服务"当前分组未提供，需另选分布式总线"。

业务诉求

一个下游项目自建了发件箱、收件箱、按 key 保序和事件页，不含测试约 1,700 行。它的反馈希望框架提供一套与传输无关的组件，业务只实现私有传输。

可复用的底座

Webhook 组件刚走通同一套组合：工作单元内入库、提交后立即处理、集群任务逐库兜底、两级管理策略、统计卡加详情抽屉的后台页。本组件照这套组合做。

2现状问题

业务项目自建时反复踩到的问题，以及现有开源方案没有解决、框架必须补上的部分。

业务项目自建的代价

  • 每个项目各写一套发件箱、收件箱、扫描与运维查询，模式和 Webhook 组件高度重复。
  • 保序做在单轮扫描里：队首失败退避后，同 key 后一条在下一轮先发出。
  • 入站在收到时同步执行处理器，失败只能人工重放，处理时长还会拖慢传输确认。
  • 收件箱不存载荷，重放只能依赖发布方的发件箱，跨服务时取不到。
  • 没有拒收存储：解不开的消息要么被丢弃，要么让传输无限重投。

现有方案缺的部分

  • 每租户一个物理库的逐库扫描：三家主流开源方案都不支持。
  • 永久失败与瞬态失败分开处理：多数实现一律重试。
  • 按 key 跨轮保序：都只做到尽力而为。
  • 消息确认语义：调研到的 Kafka 实现处理失败也提交位点，消息会丢；RabbitMQ 实现无限重新入队，毒消息会死循环。
  • 两级权限的管理端点：开源方案几乎都没有。
.NET 官方没有分布式事件总线。MassTransit 9 起商业许可；CAP 自带事务入口与存储，和框架的工作单元平行；Wolverine 要替换整套消息运行时。所以自建，只在主链路上对齐业界共识。

3核心策略

主链路对齐业界共识：同事务写发件箱 → 提交后发送 → 失败重试 → 收件箱去重 → 处理与标记同事务。在此之上补齐保序、永久失败、拒收、逐库与管理面。

3.0 六个问题的结论

新组件的目录结构
放进现有 event-bus 家族。Core 增加五个分布式契约类型，BaseEvent 元数据增加 init 以还原传输标识；新增 Distributed（纵向切片的 Core 角色）、EntityFrameworkCore、AspNetCore、RabbitMQ、Kafka 五个包。见 3.2。
模板要不要可观测性，要不要裁剪
要。模板加后台页，提供操作层的可观测性，并在 readiness 健康检查里挂上传输；框架提供链路续接和稳定日志事件。页面带表、迁移和 compose 服务，属于可独立取舍的产品边界，所以新增布尔参数 IncludeDistributedEvents，默认关闭。代价是有效形态翻倍。见 3.6。
首批是否支持 Kafka、RabbitMQ
首批同时交付 RabbitMQ 与 Kafka。RabbitMQ 代表"逐条确认"模型，Kafka 代表"提交位点"模型，两种主流确认模型都由真实实现检验契约，避免被单一模型塑形；Kafka 语义也正是私有中枢的语义。模板默认用 RabbitMQ，改用 Kafka 只需换一行注册加一个 compose 服务。见 3.4。
配置项与后台可配
有配置项，默认值即可直接上线。退避、死信窗口、扫描间隔、保留期属于协议参数与部署配置，不进设置页，与 Webhook、通知、后台作业的划界一致。保留期以后如需在后台调整，照操作记录的先例加一行 HostSettingBindings 映射。见 3.5。
可靠性、及时性、下游接入与幂等
提交后立即发送，集群任务兜底；至少一次送达；收件箱去重，处理与标记同事务，处理器对数据库的写入只生效一次。外部副作用由处理器按 EventId 自己幂等。下游接入只需实现 IEventHandler<T> 并登记。见 3.3 与 3.7。
业务集成与后台管理
业务经 IDistributedEventBus 发布、经 IEventHandler<T> 消费。后台需要管理：状态快照、事件目录（静默检测）、积压、死信、处理失败和拒收；宿主可选物理库查看全部租户；单条或按条件批量重投、重放、重新解码、丢弃；发测试事件。只读与操作两级权限，操作写操作记录。见 3.8 与第 4 章。
私有事件中枢接入
能很好支撑。契约按私有中枢的特点补齐七项，并都做成终局形态：异步解码与外部格式映射、传输层拒收入口、进程分工开关、按条件批量恢复与错误分类指南、事件目录、宿主按库查看、测试事件开关。每项在主流框架里都有对应做法，不是为某一个中枢定制。见 3.9。

3.3 可靠性、及时性与幂等

及时性

  • 发件箱和收件箱都在提交后立即进入进程内队列。
  • 兜底任务每 5 秒扫描一次，新记录留 1 分钟宽限期，避免和立即发送重叠。
  • 最坏延迟：一个扫描间隔加宽限期。

可靠性

  • 发件箱与业务同事务。
  • 永久失败直接进死信；瞬态失败指数退避（2 秒起，封顶 5 分钟），一天后进死信。
  • 传输在写库成功后才确认；解不开的消息进拒收表，不让传输无限重投。

幂等

  • 收件箱 (TenantId, EventId, Consumer) 唯一，重复只计数；信封 EventId 与 OccurredAt 在反序列化时恢复到事件实例。
  • 处理器写入与"已处理"标记同事务，并以 AttemptCount 作并发令牌，每次成功或失败都递增；并发冲突整笔回滚且不覆盖胜方。重放清零本轮次数，重新获得五次预算。
  • 结果：对数据库的副作用只生效一次。外部副作用为至少一次，处理器按 EventId 幂等。

发送结果按序判断

顺序条件处理
1成功已发送 记 SentAt
2永久失败（带稳定错误码）死信 Error 日志 DistributedEventDeadLettered
3瞬态失败，距首次失败已超过 DeadLetterAfter死信 错误码 retry-window-exceeded
4瞬态失败，未超窗口重试中 2s × 2^(n-1)，封顶 5 分钟，±10% 抖动

保序的语义

同租户、同一事件名、同排序键下存在更早的 Pending 记录时，后一条不发送（处理侧按"同消费者"同样执行）。进死信或标 Failed 都算终态，不再阻塞后续，所以消费方要能容忍版本跳号。发送按提交后可见的发件箱 Id 排队，处理按接收入库的 Id 排队；RabbitMQ 单活串行入库，Kafka 同键同分区。故障重投不承诺重新排序；同一键上的并发事务按提交后可见的顺序排队，不另加锁：业务对同一聚合的并发写本来就由并发令牌串行化。这条规则修正了下游实现的跨轮乱序。

3.4 传输：RabbitMQ 与 Kafka

传输契约（替换点）

public interface IDistributedEventTransport { string Name { get; } // 成功 / 瞬态失败 / 永久失败(code)；抛出异常按瞬态处理，取消除外 Task<DistributedEventSendResult> SendAsync( OutgoingDistributedEvent message, CancellationToken ct); // 原始消息 → 框架信封；外部格式在这里映射（可异步查注册中心） // 无法解码时抛 DistributedEventDecodeException(reasonCode, message) ValueTask<IncomingDistributedEvent> DecodeAsync( RawDistributedEvent raw, CancellationToken ct); } public interface IDistributedEventReceiver { // 解码 → 写收件箱或拒收表 → 返回；暂时性依赖故障、存储故障与取消向上传播 Task ReceiveAsync(RawDistributedEvent raw, CancellationToken ct); // 传输自己已判定无法处理（位点可能已提交）：直接写拒收表 Task RejectAsync(RawDistributedEvent raw, string reasonCode, string error, CancellationToken ct); }

不可恢复的单条格式错误才入拒收；注册中心不可用等暂时性依赖故障向上传播，取消不记失败。三表保存最后变更时刻，保留期只删除到期终态。重新解码会用保存下来的原始消息再走一遍 DecodeAsync 与校验，所以修好传输、补登事件类型之后都能恢复。RawDistributedEvent 带不透明的 Coordinates（topic/partition/offset、中枢事件 ID 等），框架只存不解释。

3.7 业务项目如何引用与使用

① 定义契约（共享契约包）

[EventName("customer.activated")] public sealed class CustomerActivatedEvent : DistributedEvent, IOrderedDistributedEvent { public Guid CustomerId { get; init; } public int Version { get; init; } public string OrderingKey => CustomerId.ToString(); }

只引用 Leistd.EventBus.Core。

② 发布（发布服务）

[UnitOfWorkEventHandler(UnitOfWorkPhase.BeforeCommit)] public class CustomerActivatedForwarder( IDistributedEventBus bus) : IEventHandler<CustomerActivatedDomainEvent> { public Task HandleAsync( CustomerActivatedDomainEvent e, CancellationToken ct = default) => bus.PublishAsync(new CustomerActivatedEvent { CustomerId = e.Id, Version = e.Version }, ct); }

也可以在 [UnitOfWork] 方法里直接发布。

③ 消费（消费服务）

public class CustomerProjectionHandler(AppDbContext db) : IEventHandler<CustomerActivatedEvent> { public async Task HandleAsync( CustomerActivatedEvent e, CancellationToken ct = default) { var row = await db.Customers.FindAsync([e.CustomerId], ct); if (row is null || row.Version >= e.Version) return; row.Activate(e.Version); // 与收件箱标记同事务 } } // Program.cs services.AddDistributedEventHandler<CustomerProjectionHandler>();
场景用法
领域事件要通知其他服务BeforeCommit 本地处理器转成分布式事件
消费方维护本地投影处理器直接写库，框架保证只生效一次；按版本号覆盖，容忍跳号
消费方调用外部系统处理器按 EventId 幂等，外部支持幂等键时直接传入
对接私有事件中枢实现传输契约与消费循环，在信封与对方格式之间映射，登记健康检查
同步查询与命令继续用 ServiceClient
进程内解耦继续用本地事件总线

3.9 接入私有事件中枢

私有中枢常见的特点：Kafka 内核、Avro 外壳、信封里没有租户与事件类型、事件 ID 由 SDK 生成、外壳解码失败时 SDK 照常提交位点、鉴权失败后降级且不再重连。下表是这些特点在契约里各自的着落，每一项都是通用写法，不为某一个中枢定制。

#中枢特点契约里的着落主流框架的对应
1外壳要查注册中心；外部系统的载荷不是本框架格式DecodeAsync 异步，外部格式由传输映射：业务 ID、租户从载荷公共头取，取不到时退回中枢事件 IDMassTransit raw JSON 反序列化器
2外壳解码失败时位点已被 SDK 提交RejectAsync(raw, reasonCode, error) 直接入拒收表；写库失败记 DistributedEventRejectPersistFailed 告警MassTransit _skipped / _error
3写入进程不连中枢，发送与消费在 Worker三个显式分工开关；发送或接收开启却没有传输时启动期报错；兜底任务的开关登记给调度器，关闭的进程不抢锁ASP.NET Boilerplate 后继框架的 IsSendingEnabled / IsProcessingEnabled
4鉴权失败后降级，期间事件大量失败错误分类指南：整条通道故障判瞬态（只积压），单条消息问题判永久；按条件批量重投、重放、重新解码CAP 批量重新入队；MassTransit 整体移回 _error
5需要按通道判断静默与"未发布 / 不属于本应用"事件目录：每个事件名的最近活动、异常数与最近错误码CAP Dashboard 的按消息视图
6宿主要逐库运维GET /databases + 各端点 database 参数，宿主看所选库的全部租户（多租户分库是本框架的一等能力）
7不一定允许同一应用自发自收TestEvent:Enabled：关闭时不订阅测试事件，界面隐藏按钮带 ACL 的 broker 普遍如此
错误类别判定结果
瞬态整条通道暂时不可用：断连、超时、限流、鉴权失败、SDK 降级退避重试，最长 1 天；积压告警
永久这一条消息原样重发永远失败：过大、schema 不符、通道不属于本应用直接死信；修复后按条件批量重投
结果未知已发出但没有确认按瞬态重发；消费端按 EventId 去重

业务侧仍然负责

  • 传输实现：SDK 发布与订阅、错误码映射、外壳与载荷公共头、健康检查加 event-bus 标签。
  • 中枢专有能力：resync、tombstone、Sandbox / Production 环境、通道登记，直接调用 SDK。
  • 契约类与版本水位；页面上的数据范围过滤。

一个 PR 交付框架与模板：模板经本地候选包消费同树框架，审查、CI 与端到端各只走一轮。取舍口径：终局但不过度设计；不过度考虑安全；不为极少数竞态加复杂度；端到端只做一次入口验证，其余分层覆盖。

省时的关键

  • 契约先冻结先审，三路互不等待，后期不因契约返工而重跑。
  • UI 在接后端之前按原型核对，界面偏差不拖到端到端阶段。
  • 实施期只跑目标测试类；整套测试、打包、模板生成、浏览器各只在 W4、W6 跑一次。
  • 两种 broker 共用一套契约测试，本机只起一次容器。
  • 审查与 CI 并行；返工只重跑受影响部分。

不做的事

  • 观察点回调；Meter 指标与模板 OTel；模板按参数切换传输。
  • 恰好一次投递、跨服务全局有序。
  • 后台配置页；跨物理库合并成一张列表；保留期后只清载荷。
  • 中枢专有能力（resync、tombstone、环境、通道登记）。
  • 把 Webhook 组件改成基于本组件。
