# 项目通用开发规范

> 本文是语言和技术栈无关的最低开发规范。具体 .NET、Angular 或其他技术栈规则应放在对应项目规范中；当项目没有技术栈定义时，AI 只应用本文原则和现有代码风格。

## 1. 开发原则

- **范围受控**：只实现已确认 Plan 范围；范围变化先记录并确认。
- **可读优先**：命名清晰、结构直接，避免过度抽象。
- **依赖最小化**：仅在没有合理替代方案时引入新依赖，并说明收益、成本和风险。
- **错误可诊断**：失败路径应有明确错误信息、日志或返回结果。
- **安全默认**：不硬编码密钥、Token、密码或真实客户数据；敏感信息必须脱敏。
- **文档同步**：新增 API、架构变化、部署变化或重要约定必须同步相关文档。

## 2. 变更规则

- 修改已有代码前先理解邻近实现和项目配置。
- 保持与现有目录、命名、格式、错误处理和测试风格一致。
- 删除、迁移或重命名代码必须有明确依据，并说明影响范围。
- 影响外部接口、数据结构、权限、安全、部署或费用的变更必须先确认。
- 不回滚用户未授权的变更。

## 3. 验证规则

- 优先运行项目声明的 build、lint、typecheck、test 命令。
- 只运行与当前阶段匹配的最小必要验证；完整测试由测试阶段执行。
- 测试失败时记录命令、错误摘要、影响和建议，不删除有效断言来制造通过。
- 未执行的验证必须说明原因，不能写成已通过。

## 4. Git 与提交

项目有 Git/分支/提交规范时以项目规范为准。无项目规范时建议使用 Conventional Commits：

```text
<type>(<scope>): <subject>
```

常用 type：`feat`、`fix`、`docs`、`style`、`refactor`、`test`、`chore`。

## 5. 工程铁律（⚠️ 踩坑写死，优先级高）

> 本节是技术栈无关的**通用工程原则**，多为"踩过坑才写死"的强约定，优先级高于一般风格建议。每条**正文是通用原则**（可迁移到任意项目），`例` 是本模板技术栈（.NET/EF Core/DDD + Angular/Spartan UI）的落地示范——**换技术栈时替换例子、原则不变**。带 ⚠️ 的条目隐蔽、易在联调期才暴露，务必遵守。

### 5.0 开发前：先找参考链路 ⚠️

动手写新需求前，**先在现有代码里找 1~2 个同类的、从前端到后端的完整链路作为参考样板**，照它的分层、命名、目录、错误处理、mock 风格来写——不要凭空发挥或套用外部习惯。

- **为什么**：与既有代码一致是可读性/可维护性的第一保障；新代码偏离项目风格，比"写得不够好"危害更大。这是 AI 最易犯的错（凭记忆自创风格）。
- **怎么做**：挑形态最接近的已完成功能，端到端读一遍（前端组件 → service → DTO/model → mock ↕ 后端 Controller → AppService → DomainService/Entity → 持久化/迁移），新功能骨架应与它逐层对应。拿不准某层怎么写就回看参考实现，不自创第二种风格。

> 这是所有实现任务的前置动作，不是可选建议。

### 5.1 守卫/校验的分层放置是刻意判断

一条校验放哪层，取决于它约束**单聚合内不变量**还是**跨聚合关系**：

- 只需**单个聚合自身状态**即可判定 → 放**领域层**（领域服务/实体方法）。
- 需**跨聚合**校验（依赖其它聚合的存在/状态）→ 放**应用层**：领域服务不引外聚合，此类校验必须上提。

落守卫前先问："这条规则只看当前聚合，还是要看别的聚合？"——刻意判断，不是随手写。

### 5.2 验证只在入口 DTO 层做，内层信任 ⚠️

- 字段验证优先在**入口 DTO** 用注解完成（必填/长度/范围）；应用层、领域层**信任 DTO 已保证的前置条件，不重复校验**。
- **例外**：实体构造函数若存在**不经该 DTO 的第二条调用路径**，其守卫是多入口共享的不变量保护，**合法保留**——先判断"是否真由该 DTO 唯一喂入"再决定删不删，别一刀切删掉多入口守卫。

### 5.3 新增能力优先扩现有抽象，不旁开第二套 ⚠️

- 需要新能力时先问"**现有抽象能不能扩**"，扩不动才新增接口；需要外部能力时在既有抽象上加方法，**不在应用服务里直连外部 SDK/客户端**。
- **杜绝并行的第二套实现路径**：同一件事不该有两处判断分支（会各改一处、漂移、漏改）。AI 尤其爱新建接口造第二套，务必先扩后建。

### 5.4 抽象在内层、依赖只向内（洋葱）

- 依赖只能向内：领域层不依赖任何上层；应用/基础设施/表现层向内依赖。
- **接口定义放领域层，技术实现下沉外层**；应用/领域层需向外"下发"动作时，**在内层定中性抽象接口、由外层适配器实现**（依赖倒置），禁止内层直接引用外层类型。
- 反复出现的信封/载荷用**不可变值对象统一定义一次**，不散落多套。

> `例`：`IRepository`/第三方服务接口定义在 `Leistd.Ddd.Domain`，EF/Redis 等实现在 Infrastructure；应用层若需下发指令，定 `ICommandSender` 抽象、由 Api 层适配器实现。

### 5.5 外部资源删除：幂等 + 真失败上抛 ⚠️

删除类接口通用约定：**只吞「资源不存在(NotFound)」**（保证幂等重试安全），**其余真错误一律上抛**，让调用方据此中止后续删库/落库——杜绝"本地记录已删、外部资源仍存在（仍计费/占用）"的孤儿资源。

### 5.6 是否触达真实外部端由统一开关决定

是否真正调用外部/云端，由**统一开关**（如 dry-run 配置）决定，**不靠调用方（尤其前端）传 opt-in 参数**。行为一致性优先：同一操作在不同调用方下行为必须一致，开关集中在一处。

### 5.7 枚举的边界转换：内部强类型、只在边界转串 ⚠️

- 领域内部状态用**强类型枚举**，不散裸字符串；**枚举 ↔ 对外契约串的转换只发生在边界**（序列化/handler 层），不下沉进领域、不上浮进无关层。
- **对外契约的分类/枚举字段（`channel/mode/scope/type/side/status` 之类）出入参统一小写**（`orders` 非 `Orders`）；内部枚举可首字母大写，只在边界一处转小写。⚠️ 此类大小写不一致隐蔽、联调期才炸。

### 5.8 接口/实现签名同步；导入用短名

- 接口与实现类**签名同步改**——改实现签名必须回改接口，不留漂移。
- 一律**文件顶部导入 + 用短名**，禁止在代码正文内联全限定命名空间。

### 5.9 项目决策项：只遵循项目统一约定

以下"项目决策项"**没有跨项目通用的正确值**，遵循**本项目的统一约定**、勿逐处自由发挥；框架强制某选择的属合理例外：

- **DI 生命周期**：遵循项目统一约定（不同项目可能约定 Transient 或 Scoped）；框架强制某生命周期的组件（如 ORM 工作单元/`SaveChanges` 拦截器需与 DbContext 同作用域）属合理例外。
- **对象映射库**（Mapster / AutoMapper 等）、**序列化命名风格**（对不同外部系统按其各自约定，在字段上显式标注）：以项目既有选择为准。

## 附录：规范检查清单

- [ ] 变更范围与 Plan 一致。
- [ ] 命名、目录和代码风格与邻近实现一致。
- [ ] 无硬编码密钥、真实账号或敏感数据泄露。
- [ ] 错误处理、日志和边界条件可诊断。
- [ ] 新依赖、新外部服务或高风险变更已说明并确认。
- [ ] 必要的文档、测试或配置已同步。
- [ ] 已执行项目声明的最小验证，或已说明未执行原因。

工程铁律（§5）核对：

- [ ] 开发前已找到 1~2 个同类端到端参考链路（§5.0）。
- [ ] 守卫/校验放对了层（单聚合→领域，跨聚合→应用，§5.1）。
- [ ] 未在内层重复 DTO 已保证的验证；未误删多入口共享守卫（§5.2）。
- [ ] 新能力优先扩现有抽象，未旁开第二套实现路径（§5.3）。
- [ ] 依赖只向内，接口在内层、实现在外层（§5.4）。
- [ ] 外部资源删除幂等（只吞 NotFound、真错误上抛，§5.5）。
- [ ] 枚举内部强类型、只在边界转串；对外契约分类字段小写（§5.7）。
- [ ] 接口与实现签名同步；无正文内联全限定名（§5.8）。
