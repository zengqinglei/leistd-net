# 规划与实现

## 需求与方案

1. 明确使用者、目标、范围、非目标、约束和可观察的成功条件。
2. 核对当前能力、依赖和已有实现；只比较会显著影响边界、成本或风险的方案。
3. 让每个验收条件对应实现位置和验证方式。
4. 用户只要求方案时，给出关键决策、风险和可执行步骤，并明确尚未实现。

短期方案保留在当前答复。只有需要跨会话、跨成员或长期追踪的决策才按 `documentation.md` 沉淀。

## 编码实现

1. 通过项目现有文档索引（及其任务读取清单）读取任务涉及的规范；没有索引或清单时从源码、配置和测试恢复约定。检查邻近代码和测试模式。
2. 实施满足目标的最小完整改动，保持依赖方向、公共契约和错误处理一致。只在没有合理替代时引入新依赖，并说明收益、成本和风险；不硬编码密钥、令牌或真实客户数据。
3. 为新增或变化行为补充风险匹配的测试，不删除有效断言或静默跳过失败。
4. 修改 API、权限、持久化或前后端流程时，同时核对调用方、配置、Mock、迁移和拒绝路径。
5. 运行相关格式化、静态检查、构建、测试和必要的真实宿主验证。

不要因规范入口缺失而停止低风险实现；以可验证事实继续，并只沉淀本次确认的长期规则。

## 任务协调

1. 重述目标和完成条件，将工作拆成可独立验证且有明确依赖的步骤。
2. 只维护一个当前计划，完成一步后立即记录实际产物和验证证据。
3. 恢复中断任务时以当前分支、diff、测试和外部系统状态为准，不以旧计划状态代替事实。
4. 范围或关键决策变化时更新计划；没有真实证据的步骤不能标记完成。

优先使用现有 issue、计划工具或需求文档。不为任务协调创建 context、handoff、registry 或例行验收报告。

## 提交

用户要求提交时，先确认本次变更与工作区其他修改的归属，运行受影响检查，核对暂存区只包含当前任务，然后按项目现有提交规范提交并报告 SHA。提交不自动意味着推送或部署；若推送会触发流水线，先核对目标分支及影响。
